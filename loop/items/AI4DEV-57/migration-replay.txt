================================================================================
WHAT THE FIRST REPLAY FOUND, and why this transcript is the second one
================================================================================

The migration was replayed once, introspected, and the introspection reported:

  {"proname":"complete_signup","grantee":"anon","can_execute":true}
  {"proname":"complete_signup","grantee":"authenticated","can_execute":true}
  {"proname":"has_platform_acknowledgment","grantee":"anon","can_execute":true}
  {"proname":"has_platform_acknowledgment","grantee":"authenticated","can_execute":true}

PostgreSQL grants EXECUTE on a newly created function to PUBLIC by default, and the
Data API roles inherit it. grant execute ... to service_role therefore locked
nothing down - it added a grant beside one that was already there.

Concretely, before the fix: anyone holding only the local publishable key could POST
/rest/v1/rpc/complete_signup with an arbitrary p_account_id and mint an 
go account,
an organisation and an admin membership against an auth user that is not theirs. The
platform_admin guard inside the function held throughout, so an administrator could
not be minted - but a write nobody authorised could.

The migration now REVOKES execute from PUBLIC on both functions before granting to
service_role, and the transcript above is the replay of the corrected file. The
migration had not left this machine, so it was corrected in place rather than with a
follow-up file (see supabase/migrations/README.md on when that is allowed).

This was found by MEASURING the replayed database rather than by reading the SQL. The
SQL reads correct either way, which is exactly why the step exists.

================================================================================
SEEN AND DELIBERATELY NOT TOUCHED
================================================================================

The grant listing above shows anon, authenticated and service_role each holding
REFERENCES, TRIGGER and TRUNCATE on all four new tables. Nothing in this migration
grants those: they come from Supabase's own default privileges on the public schema
and land on any table anyone creates here. They are not reachable through the Data
API (PostgREST issues no TRUNCATE and no CREATE TRIGGER), and none of the three roles
can open a direct database connection. Changing the platform's default privileges is
a repository-wide decision and is not this leaf's to make - recorded here so the next
reader does not have to rediscover it.
