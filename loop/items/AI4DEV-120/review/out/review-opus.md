## Findings

### 1. [warning] A malformed project id reaches the database and comes back as a 409 `refused` with a Postgres cast message
**Location**: `supabase/functions/_shared/need-intake.ts:80` and `:100` (`stringField(body.projectId)`); `supabase/functions/_shared/edge.ts:359-364` (the id shape guard) and `:372-377` (the RPC refusal mapping)
**Finding**: `decideProjectNeed` accepts any non-empty string as `projectId` and forwards it as `p_project_id uuid`. `writeRoute` shape-checks only `target`, `subject` and `from`, so `projectId` has no guard. PostgREST fails the uuid cast with SQLSTATE `22P02`; `rpcRefusalStatus` treats every five-character code as a refusal and answers 409; `parseWriteRefusalKind(null)` yields `refused`; the body carries `invalid input syntax for type uuid: "…"` as the reason.
**Evidence**: The comment at `edge.ts:359` states the rule this route breaks: "A malformed id is refused here, because PostgREST would fail the cast and answer like an outage." The read route `need-intake/index.ts:15-16` does validate the uuid shape, so the two routes for the same resource disagree on a client-shape error: one answers 400 `invalid-request`, the other 409 `refused` with a database sentence. Reachable from any admin session with `{"action":"save","projectId":"x","patch":{}}`.
**Suggestion**: Add a `uuidField(value): string | null` beside `stringField` in `write-routes.ts` (the pure module every route imports) and use it in `decideProjectNeed` for `projectId`. The private `UUID` regex in `need-intake/index.ts` and `project-workspace/index.ts` can then go too.

### 2. [warning] The assigned-volunteer policy is the one policy shape the design forbade: a table-reading subquery in USING
**Location**: `supabase/migrations/20260917120000_project_need_intake.sql:29-33` (`need_intakes_select_assigned_volunteer`)
**Finding**: The policy reads `public.projects` inside `exists (select 1 …)` in USING, calls `auth.uid()` and `public.viewer_is_volunteer()` bare, and admits a reader this item never creates.
**Evidence**: The intent says "RLS with the viewer_ helpers, no subquery in USING". The design of record denormalised `org_id` onto `need_intakes` with a composite foreign key precisely to avoid a policy subquery (`design/SYNTHESIS.md` correction 1, `decisions.tsv` line 16), then reintroduced one for the volunteer arm. The tree's own volunteer policy on `projects` (`20260907120000…sql:113-117`) is a column comparison plus `(select …)`-wrapped helper calls, no other table. Here the inner `projects` read runs as `authenticated`, so `projects`' three policies (`viewer_is_org_member`, `viewer_is_platform_admin`, `viewer_is_volunteer`) fire again per candidate row, on top of the outer `viewer_is_volunteer()`: a hidden fan-out of four definer calls per row, and a coupling where any change to `projects` policies silently changes who can read intakes. The static scan (`_policy-scan.ts:160-162`) passes it only because the text names `auth.uid(` and a `viewer_` function; it does not see the subquery. Finally, nothing in this item seats a volunteer, and the intent names the read audience as "any member of the organisation", so the policy is speculative.
**Suggestion**: Drop the policy in this item and add it with the requirement that seats a volunteer. If it must stay, write it as the tree writes such rules: a `viewer_holds_project_seat(p_project_id uuid)` SECURITY DEFINER helper with `set search_path = ''`, execute to `authenticated`, and `using ((select public.viewer_holds_project_seat(project_id)))`.

### 3. [warning] `applyNeedPatch` reads the wall clock inside a pure shared module, and the fixture ends up with two clocks
**Location**: `supabase/functions/_shared/need-intake.ts:166-172` (line 171: `updatedAt: new Date().toISOString()`); `tests/at/suites/req-003/_fixture.ts:44-46`
**Finding**: Every other timestamp the fixture mints comes from `opts.clock.now()` (start at `:30`, attach at `:49`, submit at `:63`). A changed save takes its `updatedAt` from the real clock through the shipped function.
**Evidence**: `memberships.ts:16-17` states the rule for `_shared` pure modules: "NO I/O, NO CLOCK, NO RANDOMNESS." A grep over `_shared/` finds this line as the only wall-clock read in a pure module. `ControlledClock` starts at `2026-01-01T00:00:00Z` (`harness/clock.ts:12`), so in the fixture a start carries a January timestamp, the next save carries today's, and a later attach jumps back to January. No current assertion orders these, which is why nothing fails; the first test that compares `updatedAt` across two actions will fail for a reason that has nothing to do with the product. The function also has no production caller: the edge path takes `updated_at` from the database.
**Suggestion**: Either pass `now: string` into `applyNeedPatch` and let the fixture supply `opts.clock.now()`, or return `{ patch, changed }` and let the fixture stamp the row. Both keep the module pure.

### 4. [warning] The reference-file record shape is checked and mapped in four places, and `ProjectNeedArgs` loses the action-to-payload correlation
**Location**: `need-intake.ts:54-64` (`needViewFromSql`), `:181-191` (`intakeSnapshotOf`), `:192-214` (`intakeSnapshotFromDetail`), `:34-38` (`ProjectNeedArgs`), `:166-172` (`applyNeedPatch`), `:163-165` (`submitTransition`); `tests/at/suites/req-003/_fixture.ts:26,44,48,59-72,173-184`
**Finding**: The seven-field `{id, file_name, media_type, byte_size, description, added_by_account_id, added_at}` guard at `:55-58` is repeated verbatim at `:200-203`; the camelCase-to-snake_case mapping at `:185-188` is repeated verbatim in the fixture's `sqlRow` at `:176-179`. `IntakeSnapshot['reference_files'][number]` is structurally the same record, yet `NeedIntakeSqlRow.reference_files` is typed `unknown`. `ProjectNeedArgs.p_payload` is `StartPayload | NeedPatch | ReferenceFileInput | Record<never, never>` with no tag, so the fixture casts at `:26`, `:44` and `:48` and asserts `args.p_project_id!` at `:39`. `applyNeedPatch` re-runs `parseNeedPatch` on args that `decideProjectNeed` already validated and throws on a state the type says cannot occur. `submitTransition` returns `changed: stage === 'draft'`, but its only caller checks `stage === 'discovery_in_progress'` two lines earlier (`_fixture.ts:60`), so `transition.changed` at `:66` is always true and the `if` is dead.
**Evidence**: The rubric's type-boundary lens: validate once where data enters, then trust the type. Four statements of one record shape have nothing that notices them diverging; the tree already paid for that lesson once (`accounts.ts:324-329`). An untagged union with a sibling discriminant is the pattern "make illegal states unrepresentable" exists to remove.
**Suggestion**: One `ReferenceFileRecord` type (snake_case, the wire shape) and one `parseReferenceFileRecord(value: unknown): ReferenceFileRecord | null`, used by `needViewFromSql` and `intakeSnapshotFromDetail`; `NeedIntakeSqlRow.reference_files: readonly ReferenceFileRecord[]`; `IntakeSnapshot.reference_files` reuses it. Make `ProjectNeedArgs` a discriminated union on `p_action` with `p_project_id: null` only for `start`. Delete `submitTransition` and the re-parse in `applyNeedPatch`.

### 5. [warning] `start` is inlined in the dispatcher three times over while the other three actions are helpers
**Location**: `supabase/migrations/20260917120000_project_need_intake.sql:119-155`, `20260917130000_project_need_save_and_submit.sql:112-145`, `20260918120000_project_need_attach.sql:80-113`
**Finding**: The final `project_need` (the attach migration) carries about 35 lines of `start` validation and two inserts inline, then dispatches `save`, `attach` and `submit` to `need_intake_*` helpers. The same 35 lines appear verbatim in each of the three definitions.
**Evidence**: The intent says the definer "dispatches start, save, attach, submit to private plpgsql helpers"; the code does that for three of four. A reader of the migration history reads the start arm three times to learn it did not change. The asymmetry also means the start arm is the one place where the dispatcher, not a helper, owns field validation.
**Suggestion**: `need_intake_start(p_organization_id uuid, p_payload jsonb) returns public.need_intakes`, so the dispatcher is the four guards plus a `case`. Since the branch is unmerged, the two earlier `create or replace` bodies could also collapse into their first definition; that is the lead's call on the one-migration-per-unit convention.

### 6. [warning] The new read route has no negative test, and the Tier-2 trigger never runs against the stack
**Location**: `tests/at/suites/req-003/*.test.ts` (every `readNeed` call), `tests/at/suites/req-003/d-reference-files.test.ts:68-107` (AT-003.10), `supabase/migrations/20260917120000_project_need_intake.sql:37-55` (the trigger)
**Finding**: (a) Every one of the ten `readNeed` calls in the suite is by the admin who created the need. Nothing calls `need-intake` unauthenticated, as another organisation's admin, as a volunteer, or as a non-admin member of the owning organisation (the audience the intent names). The only isolation assertion on this resource is the save path (`b-gate-and-autosave.test.ts:58-61`). (b) `classifyTier2AsOperator` has one caller, AT-003.10's `default` arm, and AT-003.10 is `capability-pending` at integration. So `need_intake_classification_is_monotonic` and the `tier2-hardened` disclosure from a real row never execute against Postgres, and no test at any tier attempts to clear or rewrite `tier2_classified_at` to see the trigger refuse.
**Evidence**: AT-003.15 is retired to AT-REQ-001.21, but the req-001 suite only touches `need_intakes` through the static catalog scan (`_policy-scan.ts:25`); no test posts to `need-intake` with a foreign session. The rubric's verification lens: "If this touches an integration boundary: is the full path tested?" The trigger is an invariant the design grafted deliberately (`SYNTHESIS.md` correction 3) and it is the one SQL object in this diff with zero executions in the suite. Nothing in AT-003.10's `default` body needs the UI surface: it attaches metadata, updates a row as the operator, and reads through the deployed route, all of which are green at integration in other ids.
**Suggestion**: Add to an existing green id (AT-003.01 or 05) a foreign-admin read, a volunteer read and an anonymous read expecting 404/404/401, and a member read expecting 200. For the trigger, an operator-path assertion inside AT-003.10's `default` arm (`update … set tier2_classified_at = null` expecting SQLSTATE 42501), and run that arm at integration; keep the `capability-pending` red only where the body truly needs the surface.

### 7. [warning] The live adapter copies REQ-002's provisioning and mints a second Auth session per NGO to get a bearer the inner adapter hides
**Location**: `tests/at/suites/req-003/_live.ts:21-47` (`sessions`, `allowanceSessions`, `signIn`, `signup`), `:59-68` (`provisionNgo`), `:69-81` (`provisionVolunteer`), `:85-90` (`readAllowance`)
**Finding**: `provisionNgo` calls `inner.sut.organizations.provisionNgo(email, { emailVerified: true })`, discards that adapter's session, signs the same user in again to hold a token, maps the new session id to the old one in `allowanceSessions` so `readAllowance` can translate back, and then re-clears `email_confirmed_at` itself, which the inner adapter would have done had it been given `options`. `provisionVolunteer` (`:69-81`) is a verbatim copy of `req-002/_live.ts:251-279`; `signIn` copies `storePasswordGrant`; `postNeed` copies `postWrite`.
**Evidence**: The root cause is that `req-002/_live.ts` keeps `sessions` private and returns only `sut`, `fixtures`, `teardown`, so a composing adapter cannot obtain a bearer for a session it received. The workaround costs three session registries for one user (inner `sessions`, outer `sessions`, `allowanceSessions`) and about 60 duplicated lines. `provisionNgo` and `provisionVolunteer` even solve the same problem two different ways in the same file (re-sign-in versus copy).
**Suggestion**: Have `req-002/_live.ts` return a test-only `bearerOf(session)` (or `postWrite`) beside `sut`, so this adapter reuses the inner sessions and drops `signIn`, `signup`, `provisionVolunteer`, `allowanceSessions` and the second confirmation clear.

### 8. [warning] Autosave is last-write-wins on whole fields with no base version, so out-of-order requests regress the text
**Location**: `supabase/migrations/20260917130000_project_need_save_and_submit.sql:32-34` and `:49-50` (`need_intake_save`, description replacement and the unconditional update), `need-intake.ts:98-110` (the save request shape)
**Finding**: A `save` replaces `description` with the request's value. The `for update` lock serialises concurrent saves but does not order them by the client's intent. Two saves fired from one browser during typing can commit in the reverse order of sending; the earlier, shorter text then overwrites the later one, and the response `changed: true` gives the client no signal that it lost.
**Evidence**: The intent is "autosaved on every change with no explicit save action", so the client will issue many small saves under variable latency. The route already returns `updatedAt`, so a precondition costs one field.
**Suggestion**: Accept an optional `ifUpdatedAt` on `save`; in `need_intake_save`, when it is present and differs from `v_need.updated_at`, return the current row with `changed: false` (or refuse with a `stale-draft` kind). Alternatively state in the route contract that the client must serialise saves; that is a convention, and the rubric prefers a check.

### 9. [warning] `edge.ts` now imports a feature module to type its shared reads, and `need-intake.ts` re-declares a type `tenant-reads.ts` already owns
**Location**: `supabase/functions/_shared/edge.ts:34,399`; `need-intake.ts:216-217`
**Finding**: `callerReads` returns `TenantReads & NeedReads`, with `NeedReads` living in `need-intake.ts`. `NeedIntakeAnswer` spells out `{ status: 200; body: … } | typeof TENANT_NOT_FOUND | typeof TENANT_READ_FAILED`, which is `TenantReadAnswer<{ ok: true; need: NeedIntakeView }>` from `tenant-reads.ts:22`.
**Evidence**: `tenant-reads.ts` is the inventory of caller-bound reads and the plumbing file depended only on it. The next requirement that adds a read will either add a third intersection member to `callerReads` or move `need` into `TenantReads`; better to do the second now.
**Suggestion**: Add `need(projectId)` to `TenantReads`, keep `NeedIntakeSqlRow` in `need-intake.ts` and import it there type-only, and use `TenantReadAnswer`.
