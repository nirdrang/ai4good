## Findings

### 1. [critical] `record_scope` uses `maxItems` under `strict: true`; the Anthropic API answers 400 to that, so no real scope generation can succeed
**Location**: `supabase/functions/_shared/scope.ts:65` (`causeLabels: { type: 'array', maxItems: 3, ... }` inside `RECORD_SCOPE_TOOL`, which carries `strict: true`), sent verbatim by `paramsFor` in `supabase/functions/_shared/anthropic-messages.ts:12-18`
**Finding**: The tool schema declares `maxItems: 3` on `causeLabels`. Strict tool use shares the structured-outputs JSON Schema limits. The current Anthropic docs (platform.claude.com, "Structured outputs", section on JSON Schema limitations) list under unsupported: "Array constraints beyond `minItems` of 0 or 1", and state "Both JSON outputs and strict tool use share these limitations" and "If you use an unsupported feature, you'll receive a 400 error with details." `maxItems` is therefore refused. `scopeAct` turns that into `failed(answer.reason)`, the row settles as `failed`, and every later `generate` reopens the failed row and hits the same 400.
**Evidence**: Every scope test that would reach the real model (`AT-004.20`, `.21` loop, `.22`, `.52`, `.58`, `.59`) is `integration: awaiting(AWAITED.anthropicLive)`, so the schema has never been sent to the API. `parseScope` (`scope.ts:158`) already refuses more than `SCOPE_CAUSE_LABELS_MAX` labels, and the skill text says "Emit at most three cause labels", so the schema keyword buys nothing. `minItems: 1` on the other arrays is inside the supported range and is fine.
**Suggestion**: Delete `maxItems: 3` from the schema and keep the bound in `parseScope` and the prompt. Add a harness self-test that walks `RECORD_SCOPE_TOOL.input_schema` (and the other two strict tools) and refuses any keyword outside the documented strict-mode set, so the next schema edit cannot reintroduce this.

### 2. [critical] The money word-list scans the NGO's own words, so any need about budgets, prices or costs can never get a scope, and each failed attempt is a free model call
**Location**: `scope.ts:246` (`SCOPE_MONEY`), `scopeMoneyProblems` at `scope.ts:248-260`, called from `scopeAct` at `scope.ts:483-489`; `renderScopeMarkdown` at `scope.ts:221-244`
**Finding**: The check runs over the whole rendered markdown. That markdown starts with `# ${need.title}` (the project name the NGO typed) and the `## User stories` section is the elicitation's `userStories`, which are the NGO's own statements echoed by the model (the fixtures do exactly this: `GRANT_TRACKER_SCOPE.userStories = GRANT_TRACKER_ELICITATION.userStories`). `\bbudget\b`, `\bcost\b`, `\bprice\b`, `\bestimate\b` are ordinary domain words for NGO tools ("programme budget tracker", "cost-sharing sheet", "charity shop price list", "estimate meals per week"). For such a need the generation fails deterministically: the model cannot avoid the word because the stories are the NGO's, the NGO cannot edit the elicitation, `regenerate` is refused because no `current` row exists (`scope-not-generated`), and `generate` just reopens the failed row and fails again. AT-004.21 asks that "no project/build-cost estimate appears"; the list checks vocabulary, not estimates.
**Evidence**: `scopeAct` returns `failed(money[0])`, so the NGO-facing 502 reason is the literal `line 3: budget`. There is no metering on the scope call (no reservation, no debit; AT-004.20 asserts the allowance is unchanged), the failed row is settled immediately (`discovery_scope_commit` marks it `failed` with `settled_at`), and `discovery_scope_begin` reopens "the latest failed row" on the next `generate`. So an NGO whose title contains "$" or "budget" can loop `generate` as fast as the model answers, each loop a full opus call at zero credits, with no bound anywhere.
**Suggestion**: Scan only the fields the model authored that could carry a build estimate (`summary`, `complexity.rationale`, `startSmallAdvice`, `riskFlags`, `suggestedStack`, `lovableRecommendation.rationale`, `buildSplit`), never the title or the stories; and match money figures (`\$\s?\d`, `\d[\d,.]*\s*(dollars|USD)`, `\b(cost|price|budget|estimate)\w*\s*(of|is|around|about|roughly)?\s*\$?\d`) rather than bare words. Store the failure reason on the failed row so an admin can see why, and bound failed re-generations (a small per-project cap or a cool-down) since the call is unmetered.

### 3. [critical] The scope prompt sends every settled turn, including empty assistant replies, which the Anthropic API rejects; the chat path already learned to skip them
**Location**: `supabase/migrations/20260924150100_discovery_retry_and_regeneration.sql:574-578` and `:623-627` (`v_context` in `discovery_scope_begin`), `contextFrom` at `scope.ts:417-427`, and the fixture mirror at `tests/at/suites/req-004/_fixture.ts:269` and `:296`
**Finding**: `v_context` emits `{role: 'assistant', content: t.assistant_message}` for every settled turn. A settled turn can hold `''` as its reply: `discovery_turn_settle` only refuses `null`, and three real paths produce `''`: the streaming cancel path (`stopped()` in `anthropic-messages.ts:74-77` returns `text` accumulated so far, which is `''` when the NGO cancels before the first delta), a `decline_off_topic` call with no sentence, and a `record_elicitation` call with no closing sentence. The chat path knows this: `contextMessagesFrom` (`discovery-turn.ts:79-86`) drops the pair when `assistant_message === ''`, and `tests/at/harness/discovery-elicitation.selftest.ts:53` pins it ("skips an empty assistant reply when preparing the next turn"). The Messages API refuses a non-final message with empty content, so once a conversation holds one empty reply, every `generate` and every `regenerate` returns a provider 400, settles `failed`, and the NGO is stuck.
**Evidence**: The scope path is the first product consumer of a SQL-assembled context (`discovery_turn_reserve` also builds `v_context`, but `discoveryAct` uses the `PREPARED_REQUEST` built by `contextMessagesFrom` and ignores it). The loop fixture builds the same unfiltered list, and the scripted port does not validate messages, so no tier can catch it. The record_elicitation case is the most likely trigger, and it is the turn immediately before a scope request.
**Suggestion**: Have `discovery_scope_begin` return the settled turn rows (or `user_message`/`assistant_message` pairs) and build `context` in TypeScript with `contextMessagesFrom`, deleting `contextFrom` and the SQL `v_context` assembly. That reuses the one place the rule lives and lets the existing selftest cover both callers.

### 4. [critical] The regeneration bound counts an in-flight or stale `generating` row before the in-flight check, so a double-submitted third regeneration escalates and notifies admins while the real regeneration is still running
**Location**: `supabase/migrations/20260924150100_discovery_retry_and_regeneration.sql:460-464` (`v_used` counts `status not in ('failed', 'escalated')`, which includes `generating`) versus `:558-566` (the in-flight check, which runs only after the escalation branch returns); the fixture mirrors the order at `tests/at/suites/req-004/_fixture.ts:231` and `:250`
**Finding**: With bound 3 and versions 2 and 3 settled, request A regenerates: `v_used = 2`, it inserts version 4 as `generating`, commits its transaction, and spends 10 to 60 seconds in the model call. A second click during that window runs `discovery_scope_begin` again: the project lock is free, `v_used = 3` (versions 2, 3 and the generating 4), so the function inserts an `escalated` row, emits `discovery.regeneration_exhausted` to every platform admin, and returns `escalated: true`. Request A then commits version 4 as `current`. The project ends with a current scope from a regeneration that succeeded, an `escalated` row beside it, a false admin notification, and every later `regenerate` answered by the `exists escalated` early return. The same order also punishes a crashed regeneration: a stale `generating` row (past the deadline) counts as used and can push the NGO into escalation one regeneration early, and because the escalation branch returns before the stale-row cleanup, that row is never marked `failed` (later `regenerate` calls exit at the escalated check, and `generate` raises `scope-already-generated`, which rolls back its own cleanup).
**Evidence**: The lock in `discovery_scope_begin` serialises begins, not begin-to-commit, and the model call happens outside the transaction by design. AT-004.38 (`proveExhaustion`) drives regenerations strictly one after another, so it cannot see this. The fixture computes `used` before checking `generating` exactly as the SQL does, so the loop tier shares the defect.
**Suggestion**: Move the generating-row block (raise `generation-in-flight` inside the deadline, mark `failed` outside it) above the `v_used` count, and count `status in ('current', 'superseded')` only. Add a loop-tier case that opens the third regeneration, does not commit it, and asserts the next `regenerate` is refused `generation-in-flight` rather than escalated.

### 5. [warning] The `retry` billing covers only turns the provider failed with a status; the timeout and network paths leave the turn open, charge the full reservation on abandonment, and bill the re-send as `free`
**Location**: `supabase/migrations/20260924150100_discovery_retry_and_regeneration.sql:98-107` (`retry` requires `t.status = 'failed'`), `:91` (an open turn past the deadline becomes `abandoned` with `charged_credits = reserved_credits`), `settleArgsFrom` at `discovery-turn.ts:163` (`answer.status === null` returns `args: null`), `edge.ts:426`
**Finding**: AT-004.39 reads "Given a system-error mid-turn, When the turn is retried, Then the retry costs zero credits." The most common system error mid-turn is the client timeout (`timeout: 120_000` in `anthropic-messages.ts:6`) or a dropped connection; the SDK raises without an HTTP status, `settleArgsFrom` answers `args: null`, the edge returns 502 and the turn stays `open`. The next send after 150 seconds marks that turn `abandoned` and charges the whole reservation, then bills the re-sent message as `free` because the max-seq turn is `abandoned`, not `failed`. The NGO pays twice for one reply. Only a provider 4xx/5xx or a refusal takes the `failed` path that the retry rule recognises.
**Evidence**: `settleArgsFrom` distinguishes `status === null` (uncertain) from a status (failed); `discovery_turn_reserve` writes `abandoned`; the retry predicate names `failed` only. AT-004.39 at both tiers drives `settleTurnAsOperator({ outcome: 'failed' })`, never the abandoned path.
**Suggestion**: Either treat `abandoned` like `failed` in the retry predicate (the reservation was already charged, so the re-send at zero is the fair outcome), or settle the turn as `failed` when the provider answered nothing (no `message_start` seen), which is the case where the platform paid nothing. Cover the abandoned path in AT-004.39 with `backdateOpenTurnAsOperator`, which already exists.

### 6. [warning] `scopeViewFromSql` throws on any stored contract `parseScope` refuses, which takes down the whole conversation read and answers 502 after the commit already succeeded
**Location**: `scope.ts:275-286`; callers `conversationAnswer` (`discovery-turn.ts:230`, inside a try that returns `TENANT_READ_FAILED`) and `renderDiscoveryScope` (`scope.ts:499-511`, called by `writeRoute` after `discovery_scope_commit` returned)
**Finding**: `parseScope` uses `exactKeys` at every level. The intent says PRD and backlog consumers "read by version", which means older versions must stay readable as the contract evolves. Adding one field to `Scope` (or one key inside `complexity`) makes every existing row fail `parseScope`, and the failure is not per row: `conversationAnswer` returns `TENANT_READ_FAILED` for the whole conversation, turns included, and `renderDiscoveryScope` throws inside `writeRoute` after the database has already stored the new version, so the NGO sees a 502 for a write that succeeded and then `scope-already-generated` on retry. `discovery_scope_commit` stores `p_contract` as opaque jsonb, so nothing at the boundary guarantees the stored shape matches what the reader demands.
**Evidence**: The row schema has no contract version column; the reader is the only place the shape is checked; and the throw is deliberate ("holds a contract parseScope refuses").
**Suggestion**: Validate at the write boundary (a `jsonb` check in `discovery_scope_commit`, or at least a documented invariant that only `scopeAct` writes it), and make the read side lenient: return the row with `contract: null` and a `problem` note rather than throwing, or key the parser by a `contract_version` column so old versions parse with their own shape.

### 7. [warning] Cause labels live in three places with different lifecycles, and `remove-label` edits only one
**Location**: `discovery_scope_commit` writes `discovery_scopes.cause_labels`, `p_contract.causeLabels` and `need_intakes.cause_labels` (`20260924150100...sql` commit body, lines 538-552 of the earlier `20260924130000_cause_labels.sql` definition); `remove-label` updates `need_intakes.cause_labels` only (`:424-427`); `renderScopeMarkdown` prints `## Cause labels` from the contract (`scope.ts:239`); `ScopeView.causeLabels` duplicates `contract.causeLabels` (`scope.ts:276-283`)
**Finding**: After the NGO removes a label, `need.causeLabels` no longer holds it, but `scope.causeLabels`, `scope.contract.causeLabels` and the rendered markdown still list it. The intent names the scope as "the contract that later PRD and backlog consumers read", so a downstream reader of the current version sees a label the NGO deleted. The `discovery_scopes.cause_labels` column is a copy of `contract.causeLabels` by construction (`stored = { ...parsed, causeLabels }` and `p_labels: causeLabels` are the same array), so the column exists only to carry a check constraint the parser already enforces.
**Evidence**: `proveRemoveLabel` asserts `need: { causeLabels: [] }` and nothing about the scope view, so the test encodes the inconsistency rather than deciding it.
**Suggestion**: Decide one owner. If the need owns the labels, drop the scope column and the `## Cause labels` section from the immutable markdown, and have `ScopeView` expose the contract's labels only as "labels proposed by generation". If the scope owns them, `remove-label` must also update the current row. Either way, delete the redundant column.

### 8. [warning] `normaliseLabels` is an identity in every reachable case, so "reuses the existing vocabulary" is enforced by prompt text only and AT-004.58 cannot tell reuse from lowercasing
**Location**: `scope.ts:111-128` (`normaliseLabels`), its only caller `scope.ts:481`; `parseScope` label handling `scope.ts:158-168`
**Finding**: `parseScope` already canonicalises each label with `canonicalLabel`, dedupes, and refuses more than three. `normaliseLabels` then canonicalises again (a no-op), dedupes again (a no-op), caps at three (a no-op), and maps each key to `vocabByCanonical.get(key) ?? key`. Every vocabulary entry satisfies `cause_labels_canonical` (`label = lower(btrim(label)) and label !~ '\s\s'`) and enters through `canonicalLabel` on the TypeScript side, so `vocabByCanonical.get(key)` is always `key` itself. The function returns its input.
**Evidence**: AT-004.58 scripts the model to answer `'Food Security'` and asserts `['food security']`; `canonicalLabel` inside `parseScope` produces that on its own. A model that answered `'hunger relief'` with `'food security'` in the vocabulary would pass through unchanged, and no test would fail, so the criterion's "rather than inventing a synonymous new one" is not verified anywhere.
**Suggestion**: Delete `normaliseLabels`. If vocabulary matching is meant to be code-enforced, it needs a real rule (for example, a label that is a substring or a stemmed match of a vocabulary entry snaps to it) plus a test whose scripted label differs from the vocabulary spelling. Otherwise state plainly that reuse is prompt-only and drop the vocabulary parameter.

### 9. [warning] No length bound on the regeneration reason or on model-minted labels; the label vocabulary is a cross-tenant channel
**Location**: `decideDiscoveryScope` at `scope.ts:381` (`stringField(input.body.reason)`, no cap), `discovery_scopes.reason text` and `cause_labels.label text primary key` with no length check, `buildScopeRequest` at `scope.ts:208` (vocabulary of every organisation goes into every organisation's prompt), `readJsonBody` in `edge.ts:522` (no body size limit)
**Finding**: A chat message is capped at `DISCOVERY_MESSAGE_MAX_CHARS` (4000) in both TypeScript and SQL. The regeneration `reason` has no cap, is stored on the row, and is interpolated into the admin email body (`notification-copy.ts:58`). A label is whatever the model emits; the skill says "short" but nothing enforces it, and a label minted from one organisation's private conversation is stored in the global `cause_labels` table, listed in the next organisation's system prompt, and can appear in that organisation's scope. A model that echoes a person's name or a place into a label moves that text across tenants with no review path (AT-004.60 forbids a curation surface, so nobody can delete it).
**Evidence**: `cause_labels_canonical` checks form, not length; `discovery_scopes_labels_are_bounded` checks count, not length; `scanLabelCurationSurface` proves no admin surface exists, which is the point of the criterion, but it also means a bad label is permanent.
**Suggestion**: Cap `reason` (reuse `DISCOVERY_MESSAGE_MAX_CHARS` or a smaller bound) in `decideDiscoveryScope` and with a check constraint; cap label length (for example 40 characters, two to four words) in `parseScope` and in `cause_labels_canonical`; and refuse labels containing digits or `@` as a cheap guard against identifiers. A platform-admin delete path for a label is not a curation surface and would give the cross-tenant risk an owner.

### 10. [warning] Three full rewrites of `discovery_scope_begin` and two each of `discovery_turn_reserve` and `discovery_turn_settle` inside one unmerged branch, plus a third copy of the notice-validation and admin fan-out block
**Location**: `supabase/migrations/20260924120000_discovery_scopes.sql`, `20260924130000_cause_labels.sql`, `20260924140000_discovery_guardrails.sql`, `20260924150100_discovery_retry_and_regeneration.sql`; the fan-out block at `20260924140000...sql:100-162`, `20260924150100...sql:250-312` and `:470-540`, copied from `20260914120000_org_vetting.sql:267-302`
**Finding**: About 1500 lines of migration SQL land for roughly 600 lines of final function text. Every earlier copy of `discovery_scope_begin` is dead the moment the next migration runs, but a reviewer must diff three versions to know what the shipped function does. The 70-line notice block validates that `p_notice.channels` equals `["email","inapp"]` in both directions and then overwrites `v_channels := v_authorized` anyway, so the validation only proves the caller sent a constant; it is now pasted three times, and the admin loop (query active `platform_admin` accounts, build recipients and deliveries, call `emit_notification`) is pasted twice. `to_jsonb(v_need) || jsonb_build_object('title', v_project.name)` appears eight times although `public.need_intake_view(p_project_id)` (`20260917120000_project_need_intake.sql:68`) already returns exactly that.
**Evidence**: All four migrations are new on this branch (`20260924…`), so squashing costs nothing in production history. The same block exists in three definers today and a fourth producer (fit decline, pending) will copy it again.
**Suggestion**: Before merge, squash to one migration per concern (table, then the final function bodies). Extract `public.notify_platform_admins(p_event text, p_actor uuid, p_payload jsonb, p_notice jsonb) returns void` that owns the notice checks and the fan-out, and call it from both definers. Use `need_intake_view` for the need snapshot.

### 11. [nit] `scopeSourceForPrd` and `scopeReferenceForScorer` are identical wrappers with no product caller
**Location**: `scope.ts:293-318`
**Finding**: Both return `resolveScopeContract(scopes, ref)` unchanged. `prd.authoring` and `backlog.derivation` are capability-pending, so the only callers are tests, and AT-004.52 asserts the two results are equal. Two names for one function is speculative surface; when a consumer arrives it may want a different shape (markdown for the scorer, contract for the PRD), and the split will be redone then anyway.

### 12. [nit] `DISCOVERY_STOP_RULE` is a product constant with no product caller; it exists so a test can pin skill text
**Location**: `discovery-prompt.ts:11-12`; callers only in `tests/at/suites/req-004/_source-pins.ts:52-53` and `e-guardrails.test.ts:133`
**Finding**: The stop rule reaches the model through `discovery-skills/index.ts` (generated from the markdown). The constant duplicates the sentence a third time and is imported by nothing under `supabase/`. A skill edit that rewords the sentence fails `stopRulePinProblems` until someone also edits the constant, which is a sync burden with no product benefit.
**Suggestion**: Keep the sentence in the test module (or read it from the markdown in the pin test) and delete the export.

### 13. [nit] The off-topic flag email names no project or organisation, and the flag is lost when no active platform admin exists at strike time
**Location**: `notification-copy.ts:52-55` (copy ignores the payload); `20260924150100...sql:307` (`if jsonb_array_length(v_recipients) > 0`) with the once-only pin at `:270-273` (`v_off_topic_count = strikes`)
**Finding**: The body is "A Discovery conversation was flagged after repeated off-topic requests. The NGO can keep talking." with no identifier, so an admin reading email cannot find the conversation; the payload carries `projectId` and `organizationId` but only the in-app delivery could show them. Separately, the notification fires only on the turn where the count equals the pin; if no active admin with an email exists at that moment, nothing is emitted and the count never equals the pin again, so the flag is silently gone.
**Suggestion**: Include the project and organisation ids (or the project name) in the body, as `regeneration_exhausted` includes the reason. Record the flag on the project or need (a `flagged_at` column) independent of delivery, so an admin joining later still sees it.

### 14. [nit] `ScopeBeginSnapshot` hides a two-state result behind optional fields and a non-null assertion
**Location**: `scope.ts:429-444` (`renderScopeBegin`), `scopeAct` at `scope.ts:446-460` and `:469` (`begun.scope!.id`)
**Finding**: `done: true` means `scope`, `elicitation` and `need` are irrelevant; `done: false` means all three must be present. The type carries `escalated?` and `changed?` as optional although `renderScopeBegin` always sets them, and `scopeAct` has to throw "returned no generating snapshot" and later use `begun.scope!` inside a closure because the type does not encode the invariant.
**Suggestion**: Return a discriminated union: `{ done: true; changed: boolean; escalated: boolean } | { done: false; scope: ScopeSqlRow; elicitation: Elicitation; need: NeedIntakeView; mission: string | null; vocabulary: string[]; context: ... }`. The throw and the assertion disappear, and `failed()` can close over `scope.id` directly.

### 15. [nit] `buildScopeRequest` hardcodes the client model and reuses the chat system prompt that tells the model to call `record_elicitation`
**Location**: `scope.ts:199` (`model: DISCOVERY_REQUEST_SETTINGS.model`) versus `discoveryPrepare` (`discovery-turn.ts:117`, `model: port.model`); `scope.ts:203` (`DISCOVERY_SYSTEM_PROMPT_TEMPLATE`, whose last line is "When elicitation is complete, call record_elicitation")
**Finding**: The real port ignores `request.model` and uses `servedModel()`, so the value is decorative, but the scripted port records it and the two request builders now disagree about where the model name comes from. The cached system block is shared with chat turns (a deliberate cache win), but its closing instruction contradicts the forced `record_scope` tool choice; the model obeys `tool_choice`, so this is a prompt-hygiene point, not a defect. `scopeAct` also folds `stop_reason: 'max_tokens'` into "the model did not record a valid scope", so a scope that outgrows the 4096-token chat cap is reported as a model fault.
**Suggestion**: Take `port.model` in `scopeAct` like the turn path. Name `max_tokens` in the failure reason when `answer.stopReason === 'max_tokens'`, and store the failure reason on the failed row.
