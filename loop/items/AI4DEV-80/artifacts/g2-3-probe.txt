METHOD
-----------------------------------------------------------------------------------------
Count 1 - every agent meta file under <projDir>\<sessionId>\subagents\ (recursive) is read.
Its `toolUseId` is grouped by the top-level session directory that holds it. A value counts
as a cross-session duplicate when it appears under two or more different session directories.

Count 2 - every top-level session transcript (<projDir>\*.jsonl) is scanned line by line with
the report's OWN regex, unchanged:
    '"(?:id|tool_use_id)"\s*:\s*"(toolu_[A-Za-z0-9]+)"'
An id counts as a cross-session duplicate when it appears in two or more different session
files.

Count 3 (supplementary) - for each duplicated id, the probe resolves the item the way the
report's pre-pass does (current branch, else the stamp, first sighting wins) in EACH file,
and compares the two answers. This separates a harmless duplicate from a real conflict.

Count 4 (supplementary) - the fix derives an agent's session from its directory path, so the
probe checks that every session directory holding a subagents tree has a session file of the
same base name. If that pairing failed, the fix would lose spawn context it has today.

Count 5 (supplementary) - how many root agents (no parentAgentId, so the spawn-context path
is the only one they have) resolve an item with the global key today, and how many still
resolve one with the per-session key.

WHAT THE NUMBERS SAY
-----------------------------------------------------------------------------------------
1. The provider does not mint the same id twice. All 580 duplicates sit in ONE file pair, and
   the reader's premise ("two sessions reuse a tool-use id") is satisfied by a different
   mechanism than collision: one session file holds a copy of the other's history, which is
   what a resumed or forked session writes. The ids are not reused; the RECORDS are copied.
2. The harm the reader named is real but small here: 5 of the 580 duplicated ids resolve to
   different items in the two files. In every one of the five the earlier-scanned file
   resolves nothing and the other resolves AI4DEV-2, so with a global key the first file
   scanned wins and a root agent of the second session would inherit nothing where the
   per-session key gives it AI4DEV-2. The direction of the error is loss, not a wrong item,
   on this store today. It is direction, not principle: nothing makes the reverse impossible.
3. The fix costs nothing measurable. Count 5 shows the same 7 root agents resolve an item
   before and after, so the per-session key removes the guess without removing any answer.
4. Count 4 makes the fix safe to derive: every subagents directory pairs with a session file
   of the same name, 7 of 7, so "the agent's session is its directory name" is a fact of this
   store, not an assumption.
