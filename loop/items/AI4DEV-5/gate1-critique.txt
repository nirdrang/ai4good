1. **BLOCKER — ownership guard can be removed by the PR it is meant to reject.**  
   **Plan claim:** “One pull request may not change both territories. Lovable owns `src/`; Claude owns … `.github/`.”  
   On `pull_request`, GitHub executes the workflow definition from the PR’s merge commit. Changing `actions/checkout` to the head SHA changes the workspace, not that already-parsed workflow. A PR can change `src/**` and `.github/workflows/ci.yml`, retain the `verify` job, and replace the inline guard with success. It then reports the required job as green. GitHub documents this workflow-source behavior for `pull_request` events and creates checks per job. 3. **BLOCKER — the plan does not put raw Vitest failure output in the CI log.**  
   **Plan claim:** “`bun run at:verify "$req" --tier loop --expect || code=$?`” and that the exit-code handling makes the failure legible.

4. **MAJOR — pushes to `main` are still cancelled under this concurrency configuration.**  
   **Plan claim:** “Pushes to main are NOT cancelled — every commit on main gets a verdict of its own.”  
   Every main push shares `CI-refs/heads/main`. With no queue setting, GitHub retains at most one pending run in a concurrency group; a third rapid main push cancels the pending run for the second push, even though `cancel-in-progress` is false. Thus some main commits receive no verdict.
