## Findings

### 1. [critical] An empty assistant reply poisons the conversation for good
**Location**: `supabase/functions/_shared/discovery-turn.ts` `settleArgsFrom` (line 107) and `discoveryPrepare` (line 79, the `context` build at lines 92 to 94); `supabase/functions/_shared/anthropic-messages.ts` `stopped` (line 45) and `answerFrom` (line 20); `supabase/migrations/20260920120000_discovery_turns.sql` `discovery_turns_settled_is_measured` (line 43)
**Finding**: A turn can settle as `completed` with `assistant_message = ''`. Every later request for that project then replays `{ role: 'assistant', content: '' }` in the middle of `messages`. The Messages API refuses a non-final message with empty content (`all messages must have non-empty content except for the optional final assistant message`). `countTokens` in `discoveryPrepare` has no try/catch, so the 400 becomes a 502 from `edgeHandler` before any reserve. The project can never receive another message. Nothing in the tree can repair the row: the immutability trigger forbids any update of a settled turn.
**Evidence**: Four product paths produce the empty text. (a) The stream cancel path: `stopped()` returns `text` accumulated so far, which is `''` when the client cancels before the first `text_delta`; `writeRoute` then settles it as `completed` with `p_assistant_message: ''`. The vendors selftest shows this exact shape (`text: ''`, `stopReason: 'user_stopped'`). A user pressing stop quickly is enough. (b) A tool-only reply: `discovery-elicitation.selftest.ts` enshrines "settles a tool-only record with empty text" as supported behaviour. With `strict: true` tools the model often emits the call with no text. (c) A final `refusal` after `fallbacks: 'default'` also declined: content is empty, `answerFrom` returns `ok: true, text: ''`. (d) Claude Opus 5 thinks by default and `max_tokens` caps thinking plus text (the claude-api reference states this for Opus 5); at the 512-token floor a turn can end with `stop_reason: max_tokens` and no text block. The SQL constraint only requires `assistant_message is not null`; `''` passes. `discoveryPrepare` maps every settled row into the context with `row.assistant_message!`, so the empty string reaches the API on the next turn. The loop tier cannot catch this: the sim accepts any history.
**Suggestion**: Decide what an empty reply means and encode it. The simplest safe rule: a completed turn whose text is blank is excluded from the context in `discoveryPrepare` (and in the SQL `v_context`, if that query stays). Better: settle a blank-text `user_stopped` turn as `failed` rather than `completed`, so it costs nothing and is never replayed. Make the sim refuse a non-final empty message the way the API does, so the loop tier exercises the rule, and add a test that sends a message after a blank turn.

### 2. [critical] The money path has never produced a settled turn, and the branch's own test-model override cannot run

The live verification report records zero completed turns, zero served models, zero charged credits, and a failed recording. The founder ruled that verification runs on Haiku for price, and the branch added `DISCOVERY_MODEL` for that, but `paramsFor` always sends `output_config.effort`, which Haiku 4.5 rejects (the claude-api reference table says `effort` errors on Haiku 4.5; the live report shows the 400). **Evidence**: `live-verify.md` checks 1, 2, 3 and the resume half of 5 fail on `This model does not support the effort parameter`; part 2 says "The recording did not land". `GRANT_TRACKER.source` is still `'handwritten'`. `anthropic-messages.ts` sits in the no-type-checker zone by the tree's own admission, so nothing else covers it. ### 3. [warning] Measured input excludes the cached prefix, so every turn undercharges
**Location**: `anthropic-messages.ts` `answerFrom` (line 24, `inputTokens: message.usage.input_tokens`) and `observe` (lines 51 and 54); `discovery-prompt.ts` `discoverySystemPrompt` (`cached: true` on the first block)
**Finding**: With `cache_control: ephemeral` on the system block, the API reports the cached prefix in `usage.cache_creation_input_tokens` and `usage.cache_read_input_tokens`, not in `usage.input_tokens`. The port reads only `input_tokens`. `countTokens` counts the whole prompt, so the reservation includes the prefix; the settlement does not. `charged_credits = least(reserved, ceil(actual))` is therefore systematically low by the prefix on every turn, and `overrun_micros` is under-reported.
**Evidence**: The claude-api TypeScript reference defines `usage.input_tokens` as "uncached tokens (full cost)" and lists the two cache fields separately. The prefix here is the tool schema plus template plus skills, about 600 to 900 tokens, and Claude Opus 5 caches from 512 tokens, so the cache engages on the pinned model. On Haiku 4.5 the minimum is 4096 tokens, so caching silently does not engage there; a Haiku live run would not show this defect. The metering constants price input at 5 micros per token with no cache tier, so the honest measured input is `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`.
**Suggestion**: Sum the three fields in `answerFrom` and `observe` (or price the cache tiers explicitly and store them on the row). Add the three fields to the sim's `ScriptedReply.usage` so the loop tier can assert the sum.

### 4. [warning] A client cancel charges the cap, not the measured usage
**Location**: `anthropic-messages.ts` `stopped` (lines 45 to 46, `outputTokens: sawDelta ? usage.outputTokens : request.maxTokens`) and `observe` (line 53, `sawDelta` set on `message_delta`)
**Finding**: The intent says a cancel "settles the turn with the measured usage". In the Messages stream protocol the only event that carries output usage is `message_delta`, and it arrives once, at the end of the message. A cancel during generation therefore never sees it, `sawDelta` stays false, and the turn settles with `output_tokens = max_output_tokens`. Because the reservation is `estimated_input * 5 + max_output * 25` and the measured input is close to the estimate, `charged_credits` equals `reserved_credits`: a cancel after one word costs the full reservation.
**Evidence**: `stopped()` is returned on every abort path (`if (signal.aborted) return stopped()` three times). The vendors selftest "settles an interrupted replay with partial text and the output cap" asserts exactly this outcome and calls it the cap. The SQL settle accepts it because `p_output_tokens = max_output_tokens` is not greater than the cap.
**Suggestion**: Either state the real rule in the intent and the UI ("stopping a reply costs the whole reservation"), or estimate output from the delivered text (`countTokens` on the partial assistant text, or a chars-per-token bound) and record `stop_reason = user_stopped` so the estimate is auditable. Do not describe the current behaviour as measured usage.

### 5. [warning] Thinking is on by default on Claude Opus 5 and is billed inside the output cap
**Location**: `anthropic-messages.ts` `paramsFor` (line 11, no `thinking` parameter); `discovery-metering.ts` `DISCOVERY_REQUEST_SETTINGS` (line 3, `minOutputTokens: 512`, `effort: 'low'`)
**Finding**: The request never sets `thinking`. On Claude Opus 5 an omitted `thinking` runs adaptive thinking, and `max_tokens` is a hard cap on thinking plus visible text. The NGO pays 25 micros per thinking token it never sees, and at the low-credit floor (`max_output_tokens` down to 512) the visible reply can be empty or truncated (which also feeds finding 1).
**Evidence**: The claude-api migration notes for Claude Opus 5, "Breaking change 1: thinking is on by default", state both facts. `effort: 'low'` reduces thinking but does not remove it. The 512 floor was chosen in the design without this in view.
**Suggestion**: Either pass `thinking: { type: 'disabled' }` (accepted at effort `low`) with the prompt adjustments the reference recommends, or keep thinking and raise `minOutputTokens` so a floor turn still has room for a reply. Record `thinking` in `request_settings` so the ledger says what was bought.

### 6. [warning] Near-zero credits refuse without the tier remedies
**Location**: `supabase/migrations/20260923120100_organization_discovery_switch.sql` reserve free path (lines 200 to 210, the `v_max_output := v_min_output` floor and the debit); `supabase/migrations/20260916120000_discovery_allowance.sql` debit arm (lines 172 to 194)
**Finding**: The reserve floors `v_max_output` at `min_output_tokens` even when the allowance cannot cover it, so the reservation can exceed `remaining` while `remaining > 0`. `discovery_allowance('debit')` then raises `debit-exceeds-remaining` ("still has N Discovery credits remaining today, this debit is larger than what remains") with no remedies. Only the `remaining <= 0` arm carries "get vetted / fund project fuel / wait for the next UTC day". A conversation whose context has grown reaches this state several credits before zero: at 60k counted input tokens the minimum turn costs 4 credits, so an NGO with 3 credits left is refused with a message that names no remedy.
**Evidence**: `proveBound` in `a-metering.test.ts` accepts `debit-exceeds-remaining` as an outcome of the last-credit turn, so the suite has seen this arm and let it through. The intent says "Zero-credit refusals carry tier-specific remedies"; this is the zero-credit refusal for a real conversation and it carries none.
**Suggestion**: In the reserve, when the floored reservation exceeds `remaining`, raise `daily-allowance-exhausted` with the tier sentence (call the same arm, or move the remedy sentence into one function both arms call).

### 7. [warning] The second streaming transport is dead code guarded by an error-text heuristic
**Location**: `anthropic-messages.ts` `stream` (lines 64 to 97: the `typeof client.beta.messages.stream === 'function'` check, the `incompatible` regex at lines 73 to 75, and the raw `create({ ...params, stream: true })` loop at lines 78 to 97)
**Finding**: The fallback sends the identical `params` (same `betas`, same `fallbacks`) to `beta.messages.create` with `stream: true`. If the API rejected those parameters once with a 400, it rejects them again; if the SDK helper threw a `TypeError` naming them, `create` receives the same object. There is no input on which the second path succeeds where the first failed. The 25 lines that accumulate `content_block_start`, `input_json_delta`, `message_delta` and `message_stop` by hand exist only to serve that path, and `stream.finalMessage()` already does all of it.
**Evidence**: `params` is built once by `paramsFor(request)` and reused verbatim (line 63 and line 78). The `incompatible` condition is `/betas|fallbacks/i.test(error.message)` plus an `instanceof` check, a string match the claude-api reference warns against ("use typed exception classes ... instead of string-matching error messages"). The `typeof ... === 'function'` guard tests a pinned SDK version for a method it ships.
**Suggestion**: Delete the raw path and the guard. Keep `client.beta.messages.stream(params, { signal })` plus `observe` for deltas and `finalMessage()` for the answer. The function shrinks by about half and loses its only heuristic.

### 8. [warning] The provider is called before any per-organisation check, and the stated refusal order does not hold on the route
**Location**: `discovery-turn.ts` `discoveryPrepare` (lines 79 to 101: email check, need read, turns read, `port.countTokens`); `edge.ts` `writeRoute` (lines 368 to 375: prepare runs before the reserve RPC)
**Finding**: `countTokens` ships the whole conversation to Anthropic before the reserve checks `discovery_disabled_at`, the allowance, the open-turn deadline, or the need stage. An organisation a platform admin switched off, or one with zero credits, can call the route in a loop; every call reaches the provider with the platform key. `count_tokens` is free but rate-limited, so the exposure is the platform's count-tokens window, and the switch exists to contain exactly this caller. Separately, the intent states "the reserve refuses `discovery-disabled` before the email floor"; on the only path a user takes, `discoveryPrepare` refuses `email-unverified` first, so an unverified admin of a switched-off organisation is told to verify their email. The SQL order is reachable only from `reserveTurnAsOperator`.
**Evidence**: `writePipeline` runs `decideDiscoveryMessage` (type, lifecycle, admin role), then `prepare` runs the email floor and `countTokens`, then `callDatabaseFunction('discovery_turn_reserve')`. The switch column is not in `TenantReads.organization`'s projection, so prepare cannot read it. The founder's unit 1 fix put the email floor before the count for the same reason (an unverified caller should not reach the provider); the switch and the allowance deserve the same treatment.
**Suggestion**: Add the switch, the allowance, and the open-turn state to `write_standing` (or a small `discovery_standing` read) so `decide` refuses before the count, and keep the SQL checks as the backstop. Then the stated order holds on the route and the provider sees only callers who can be charged.

### 11. [warning] The Discovery streaming protocol lives inside the shared write frame
**Location**: `edge.ts` lines 33 (`import * as discoveryStream`) and 382 to 423 (the `ReadableStream` block inside `writeRoute`); `write-routes.ts` `WriteRouteSpec.settle.stream` (line 242)
**Finding**: `writeRoute` is the one frame every write goes through. It now contains forty lines that know the Vercel UI message stream (`start`, `text-start`, `text-delta`, `data-turn`, `finish`, `[DONE]`), the SSE headers, an `AbortController`, and `EdgeRuntime.waitUntil`. That is Discovery's transport, not the write boundary's. The block also re-derives the settle outcome from `acted.args`/`acted.failure` with branches that differ from the JSON path four lines below (the JSON path answers 502 on `args === null`; the stream path emits a generic error and still finishes), so the two paths already disagree on the same result.

### 12. [warning] The prepared request is smuggled through the RPC args under a Symbol, and the settle result is two nullable fields
**Location**: `discovery-turn.ts` `PREPARED_REQUEST` (line 42), `DiscoveryReserveArgs` (line 46, `[PREPARED_REQUEST]?: DiscoveryModelRequest`), `discoveryPrepare` return (line 99); `write-routes.ts` `SettleActResult` (line 230); `edge.ts` lines 401 to 406 and 425 to 433
**Finding**: `prepare` returns `args` that are both the RPC payload and the carrier of the counted request, relying on `JSON.stringify` and `structuredClone` dropping Symbol keys. 'the provider outcome is uncertain'` default for the `(null, null)` state that no producer creates.
**Evidence**: `settleArgsFrom` produces `(args, null)`, `(args, reason)` and `(null, reason)`; the frame handles `(null, null)` anyway at line 426. The fixture's `sendMessage` decodes the same pair a third way (`acted.failure!`).
**Suggestion**: Type the side channel: `prepare` returns `{ args, carried }` and `settle.act(reserved, args, carried)`. Replace `SettleActResult` with a union, `{ kind: 'settle', args } | { kind: 'settle-failed', args, reason } | { kind: 'uncertain', reason }`, and decode it once.

### 22. [nit] A connection error that never reached the provider is treated as uncertain and ends in a full charge
**Location**: `anthropic-messages.ts` `failure` (lines 16 to 19, `status: error instanceof Anthropic.APIError ? error.status ?? null : null`)
**Finding**: `APIConnectionError` (request failed to send) and `APIConnectionTimeoutError` (request sent, no answer) both have no status, so both leave the turn open and the next reserve abandons it at the full reservation.
