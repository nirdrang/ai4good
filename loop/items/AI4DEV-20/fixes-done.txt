  *** THE D VERDICT: WHICH REVIEWER WAS RIGHT ***

  BOTH, about different points on the same path, and terra's finding was real at
  the line it cited.

  Verified at oracles.ts:685 as it stood: `createLiveTransport().send()` filtered
  and joined `message.content` and only then assembled the response object, so
  `stop_reason` was not consulted until after the content had been read. Terra
  was right, precisely and at the line.

  Kimi's statement — "stopReason is checked before parsing on the judge path and
  before writing on the recorder path" — was ALSO true, then and now: `judge()`
  raises its typed error before `parseJudgeAnswers` is ever called, and the
  recorder checks before it writes. Kimi was describing the layer above. Neither
  reviewer contradicted the other; terra found an ordering defect one layer below
  where kimi looked, and a reader of only kimi's report would have concluded the
  path was clean.

  HONEST SIZING: with the real SDK `message.content` is a plain array, so the old
  ordering could not actually throw. What was wrong was the ordering itself —
  work done on material the caller is about to discard, reading as though the text
  mattered when the call had not finished. It is a discipline defect, not an
  observed crash, and it is fixed rather than argued about.

  FIX: the shaping moved into an exported `liveJudgeResponse(message)` which reads
  `stop_reason` first and returns `text: ''` without touching `content` when the
  message did not finish. Extracting it is what makes the ordering testable at
  all — no client, no network.
  TEST: 'checks WHY the judge stopped before it touches a single byte of content'
  drives it with an object whose `content` getter throws, plus a control proving
  content IS read on a finished response.
  MUTATION: reading `message.content` one line early fails exactly that test.

  (terra 5) Local re-validation now enforces unknown-property rejection at the top
  level and per answer, mirroring `additionalProperties: false` in the schema the
  server enforces. The sharp case is an answer carrying BOTH `holds` and `value`
  — a judge that hedged rather than answered — which used to be read as whichever
  field its declared kind wanted.
  TESTS: 'refuses properties the verdict schema does not allow…' and 'applies
  that strictness on the live-shaped, replay and recording-read paths alike',
  the third of which writes real recordings and reads them back through the store.
  MUTATION: disabling the top-level check fails both.

PROPOSALS FOR YOUR RULING
-------------------------

Q1. `writeRecording` REFUSES TO OVERWRITE, ALWAYS — not only in the conformance
    test. Cluster F ruled the test's write exclusive-create; making the writer
    exclusive was the way to get that by construction rather than by a flag the
    test sets and the recorder does not, since such a flag is itself a seam. The
    consequence reaches the recorder: re-recording a key now requires deleting
    the file first, which I judged correct (the key is a hash of the complete
    request, so an existing file already answers it, and a silent replacement is
    a verdict moving with nothing in the diff to say so). The recorder skips
    already-recorded keys rather than failing. RECOMMEND KEEPING; flagged because
    it is slightly wider than the cluster's words.

Q2. THE DUPLICATE-KEY CHECK RUNS BEFORE THE FILENAME CHECK. Either alone closes
    the measured hole. I put duplicate first so the shadow attack produces its own
    error, and so that both rules have a case the other cannot reach — otherwise
    the second is untested code. Cheap, but it is an ordering decision that shapes
    which message a future reader sees.

Q3. `liveJudgeResponse` IS A NEW EXPORTED SEAM on oracles.ts. It exists because
    the ordering terra found could not otherwise be tested without a client. It
    is internal machinery, so by the ruled scope it is outside the alias probes —
    consistent with the residual you already ruled, but it is one more name in
    that unwatched set, so you may want the residual re-read rather than assumed
    unchanged.

Q4. THE SENTINEL RUBRIC'S CRITERION IDS were renamed (`sentinel-tolerance` →
    `sentinel-near`) because an id containing "tolerance" made the field-name
    assertion fail on the id instead of on a leak. Worth one sentence in the
    record because it is the same class of defect the cluster is about: a test
    that fails for a reason other than the one it names is as misleading as one
    that cannot fail.
