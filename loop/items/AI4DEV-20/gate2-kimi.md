• # Gate 2 review — AI4DEV-20 — Kimi (kimi-code)

  ## Verdict
  BLOCKING FINDINGS PRESENT — the replay store silently lets a second committed file shadow an existing recording by declaring the same key, so a flipped verdict can replace a real one with no refusal, which is exactly the quiet provenance failure F2 was ruled to make impossible.

  ## Findings

  1. [MAJOR] — `tests/at/harness/oracles.ts:581-593` (`readRecordings`) — two files in one directory may declare the SAME key; `entries.set(parsed.key, parsed)` silently overwrites, and because files are processed in sorted filename order, a file named `zzz-shadow.json` always wins over the real `<hex-key>.json`. Verified in the tree: I wrote an honest recording whose ballot says FAIL, then a second file declaring the same key (hash re-derivation passes — the stored request is unchanged) whose text says PASS; `readRecordings` returned one entry, the shadow, no error. The filename is also never checked against the declared key, so the shadow needs no particular name. Why it matters: the F2 ruling's claim is that a hand-edited recording becomes "a refusal instead of a silent hit"; that claim holds for editing a recording's key or request, but not for overriding it. One committed file flips what the loop tier replays, and the store's own doctrine ("refuses the whole directory on any bad entry") never fires. Minimal fix: in `readRecordings`, throw if `entries.has(parsed.key)` (duplicate declared key), and reject any file whose name is not `${parsed.key}.json`; add a conformance test writing exactly this shadow and asserting the refusal.
  2. [MINOR] — `tests/at/harness/oracles.ts:492-494` (`isCommittedRecordingsDir`) — the committed-dir test is a case-sensitive string compare of `resolve(dir)`. On Windows (case-insensitive filesystem) a path like `RECORDINGS` upper-cased resolves to the same physical directory but compares unequal, so the writer's synthetic-in-committed refusal is bypassable. Verified: `isCommittedRecordingsDir(RECORDINGS_DIR.toUpperCase())` is `false`. It fails closed downstream (the reader then refuses the synthetic entry and reddens the whole store rather than serving it), so it is not a false green — but the write-side guard F2 built is weaker on the platform this repo runs on. Minimal fix: compare case-insensitively on win32, or compare `realpathSync` results.
  3. [MINOR] — `tests/at/harness/oracles.selftest.ts:328` — `expect(prompt, 'the expected value reached the judge').not.toContain('10.5')` can never fail: `10.5` appears nowhere in the MEASURED rubric (expected is `10`, tolerance `0.5`, minimum `3`, and none of those literals is asserted absent). The `'tolerance'` and `'minimum'` assertions do catch a full comparator-object leak via the op/key names, so the test is not vacuous — but the one assertion aimed at the expected VALUE is inert, and a leak rendering only values (`expected 10, tolerance 0.5` without the words) would pass it. Minimal fix: assert on the actual rendered values (e.g. `not.toContain('expected')` plus a value-bearing shape), or drop the dead assertion.
  4. [MINOR] — `tests/at/harness/oracles.ts:416-421` (`renderMaterial`) — the comment "Slots are rendered in the RUBRIC's declared order, never the caller object's key order" is a load-bearing canonicalization claim that no test pins: `renderMaterial` is never imported by the selftest, and a mutation to caller key order fails nothing (all judged fixtures have one slot; the four-slot AT-033.07 rubric is never judged). The failure mode would be a loud replay miss rather than a false green, hence minor. Minimal fix: one test rendering a two-slot rubric with material supplied in reverse key order, asserting identical output.
  5. [MINOR] — `tests/at/harness/rubrics/at-033-07.ts:78-83` — the no-fabrication criterion requires every event to "appear in the recent-activity record quoted to you", but no material slot carries that record: `materialSlots` is only the four answers (`at-033-07.ts:40`), so the judge is asked to verify against text it never receives. It is a DISPOSABLE skeleton and conformance deliberately never judges it, so nothing green rests on it — but as the canonical demonstration of the no-fabrication KIND it teaches the pattern wrong. Minimal fix: add a `recent_activity` slot to the factory (parameter or fixed specimen text) so the reference material exists.

  ## Residual risks
  - The store has no authenticity beyond self-consistency: a hand-crafted committed file with `recordedFrom: 'live'` and a correctly derived key is accepted (finding 1 is the sharpest instance). Git review of the committed directory remains the real boundary; the README's "the store refuses them anyway" is true only for entries that honestly declare themselves synthetic.
  - The live path is entirely unexecuted — request shape is compile-checked only; whether the pinned model accepts `output_config`, returns `end_turn`, or produces schema-conformant verdicts is unknown until a keyed run, and the measured-stability record F1 conditioned its acceptance on does not exist. All four gaps are stated plainly in `live-smoke.md`, but they are gaps.
  - A `>=`-for-`>` mutation in the majority rule is unreachable by any test and also inert while the odd-k validation holds — the two guards protect each other with no third witness; if the odd-k refusal ever regresses, the tie breaks silently toward pass.
  - `parseJudgeAnswers` tolerates extra properties on an answer object (e.g. both `holds` and `value` present) that the server-side schema would reject; live and replay can therefore disagree in principle about the same bytes.
  - `oracles.ts`'s own exported types (`JudgeRequest`, `JudgeResponse`, `RecordingEntry`, etc.) are outside the F11 alias-protection list; the ruled scope was the contract aliases and that scope is met, but a future conversion of one of those to an interface has no probe watching it.
  - The replay miss test does not delete `AT_JUDGE_API_KEY`, so under a fallthrough regression a keyed developer's conformance run would attempt a real billed call before failing — the as-written code cannot reach it, but the safety net covers only one of the two tests that would be first to meet a live transport.
