# Gate 1 critique — AI4DEV-20

## Verdict

BLOCKING FINDINGS PRESENT — the hard integration gate remains nondeterministic, and the plan cannot prove that committed replay data came from the declared live oracle.

## Findings

1. [severity BLOCKER] — §3c determinism — Three live votes reduce random variance but cannot guarantee that identical input receives the same verdict on different days; correlated model or infrastructure changes defeat the stated `≈3p²` argument. Replay is restricted to loop while integration—the closing gate—uses live calls. Evidence: `plan.md:21-25,101-112`; `loop/bringup/AI4DEV-3-at-harness.md:32-35`; `registry.ts:617-619`. Fix: either use a genuinely deterministic pinned oracle at integration, explicitly change the tier/spec contract to permit reviewed replay, or narrow the guarantee with founder approval and add a measured stability bound. Majority alone is not determinism.

2. [severity BLOCKER] — §§4f, 4h, 5.6–5.7 — The plan requires committed recordings but defines no recording command or sole writer, while the only live generation step is optional. Without a key, the executor can satisfy the stated greens only by committing synthetic/canned “recordings,” which would not prove the declared live judge. Evidence: `plan.md:150-151,182-204,215-216`. Fix: define one explicit recorder that canonicalizes inputs, calls the live transport, validates the response, writes atomically, and records requested/served model provenance; require successful live recording before merge or remove live-backed grounding recordings from this item.

3. [severity MAJOR] — §4c tier wiring — The assertion that a real oracle makes `stubbedCapabilities()` empty above loop is false in this tree. `createHarness()` unconditionally registers the clock, fixtures, email vendor, and every SUT member as stand-ins. Integration is rejected before any suite can exercise the oracle. Evidence: `index.ts:117,128,141-145`; `registry.ts:617-619`; contrary claim at `plan.md:110-112`. The exact loop ledger at `conformance.selftest.ts:154-159` must also gain `oracles.judge`, which the plan does not name. Fix: state that only oracle provenance is being established, add direct loop/live oracle factory tests, update the exact loop ledger, and explicitly test that live mode never reads replay. Do not claim full integration reachability until the other stand-ins are replaced.

4. [severity MAJOR] — §§3c.2, 4a–4b — The extraction contract is not executable as specified. It says code performs minimum/tolerance comparisons, but the proposed criterion shape contains no expected value, comparator, tolerance, extraction result type, unit, or normalization rule; `judge()` receives only rubric and material. Evidence: `plan.md:96-100,124-129`; AT-033 requires minimum-event, no-fabrication, and runway-tolerance behavior at `.taskmaster/docs/acceptance/at-req-033.md:21`. Fix: define a serializable discriminated extraction criterion with typed expected values, comparison operations, tolerances, units, and normalization, then pin boundary cases in conformance tests.

5. [severity MAJOR] — §§2, 4f — The grounding-rubric mitigation is decorative for AT-004.10 and AT-033.07. Their fixture facts, event set, minimum, and tolerance do not exist yet, so a rubric authored now cannot be “derived line-by-line” into the final fixture-specific oracle. This conflicts with the parent’s just-in-time boundary and its warning against contracts built before consumers. Evidence: `plan.md:29-44,182-185`; `loop/bringup/AI4DEV-3-at-harness.md:58-64,168-172`; `.taskmaster/docs/acceptance/at-req-004.md:25`; `.taskmaster/docs/acceptance/at-req-033.md:21`. Fix: use requirement-neutral conformance rubrics now and leave requirement rubrics to their suites, or explicitly label these as disposable examples rather than proof of the final shape.

6. [severity MAJOR] — §§3c.4, 4b — The replay key omits behavior-changing request inputs: effort, thinking configuration, output schema, maximum tokens, canonicalization version, and the actual rendered prompt. A manually maintained `PROMPT_VERSION` does not make prompt edits invalidate recordings “by construction”; forgetting to bump it silently reuses stale data. Evidence: `plan.md:76-79,107-108,141-143`. Fix: hash a canonical serialization of the complete rendered request and schema, including material slot names and values, rather than relying on a hand-bumped prompt constant.

7. [severity MAJOR] — §3b API decision — `effort: "low"` is supported, but the settled claim that it is documented as strong for this task and reduces verdict variance is unsupported. Anthropic recommends starting at `high` and lowering effort where task-specific evaluations show quality holds. The plan has no consuming suite or mandatory live evaluation establishing that. Its statement that sending any sampling parameter causes a 400 is also broader than the migration documentation, which specifies non-default values. Evidence: `plan.md:49-56,76-79`; [Anthropic effort guidance](https://platform.claude.com/docs/en/build-with-claude/effort), [Anthropic migration guide](https://platform.claude.com/docs/en/about-claude/models/migration-guide). Fix: keep effort provisional, run a labeled effort sweep, and include the selected effort in the replay key.

8. [severity MAJOR] — §4d credential path — Passing `AT_JUDGE_API_KEY` to the Vitest child materially weakens the current leak model: the tree promises that provider secrets cannot reach tests, while the spawned test process inherits stdout/stderr directly and could print or misuse the key. Every test in every non-loop requirement receives it, not only semantic-oracle calls. Evidence: `.env.example:7-18`; `runner.ts:113-121,163-169,1121-1139`; `plan.md:165-172`. Fix: keep the key outside Vitest—prefer a bounded parent-side judge/recorder broker—or require an explicit, narrowly scoped live-oracle mode with a limited key and update the threat model.

9. [severity MAJOR] — §§4d, 4g — The proposed credential sentinel can green without testing the real spawn condition. `childEnv(extra)` accepts and spreads any caller-supplied value, so testing `childEnv({AT_JUDGE_API_KEY: ...})` proves only that generic mechanism, not that the Vitest call passes it exclusively for non-loop tiers. Evidence: `runner.ts:163-169,1137`; current real-child probes at `runner.selftest.ts:44-84`. Fix: extract the exact tier-dependent environment builder used by the spawn site and run real-child probes for loop, integration, and `ANTHROPIC_API_KEY` exclusion.

10. [severity MAJOR] — §§3c.3, 4e, 4g — The conformance plan does not prove the registry is the sole writer of vote count. A literal `3` could remain in `oracles.ts` while the registry entry and its self-test both pass. Overrides can also supply zero, negative, fractional, or even vote counts, leaving ties or no verdict undefined. Evidence: `plan.md:101-103,174-178,190-195`; `registry.ts:147-148`; `config.ts:42-48`. Fix: construct the oracle from `h.config`, validate a positive odd integer, and prove through overrides that transport call count and aggregation actually change. Add crossed multi-criterion votes and an explicit live-never-replay test.

11. [severity MAJOR] — §§4a, 5.1 — Merely keeping existing type-invention probes green does not protect the new exported oracle types. The current executable specification enumerates every protected alias; none of the proposed `Rubric`, criterion, verdict, provenance, or oracle types will be attacked unless both the probe and list are extended. Evidence: `contracts.ts:146-172`; `type-invention.selftest.ts:116-150`; insufficient criterion at `plan.md:208`. Fix: add every new reachable contract alias to `ALIAS_PROTECTED` and add matching declaration-merging attacks.

12. [severity MINOR] — §§4b, 4g — “Teardown leaves no state” has no implementation path or observable criterion. Current harness teardown releases only the adapter and fixture store; no oracle resource is registered. Evidence: `index.ts:165-169`; teardown accounting at `registry.ts:510-575`; promise at `plan.md:195`. Fix: declare the oracle stateless and prove fresh-instance isolation, or return a disposer from its factory, invoke it from harness teardown, and test that disposer failures make the run red.

No additional finding: the current model ID, `output_config.format` structured-output shape, refusal/max-token handling, lack of a seed option, and test-only SDK dependency placement are workable; the fixed dateless model ID is a pinned snapshot, although serving infrastructure may still vary. [Anthropic structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [model-ID guarantees](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions). Keeping `tests/at/expected/req-016.json` byte-identical is also achievable.

## Residual risks accepted if the plan proceeds unchanged

- Same-provider self-preference and systematic rubric bias remain correlated across all three votes.
- Provider availability, rate limits, model access, and cost can make the hard gate unavailable.
- The SDK officially documents Node.js 18+ rather than Bun as its supported runtime; an optional smoke leaves that compatibility unproved.
- One compliant and one violating specimen per rubric cannot expose criteria the judge silently ignores.
- Future rubric or request changes can leave committed recordings stale or require widespread re-recording.
