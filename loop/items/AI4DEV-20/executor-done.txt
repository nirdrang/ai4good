PROPOSED JUDGEMENTS — the item agent rules, the executor only proposes
---------------------------------------------------------------------

P1. THE SDK'S TYPE DECLARATIONS NOW JOIN THE STRICT ACCEPTANCE PROGRAM.
    oracles.ts carries `import type Anthropic from '@anthropic-ai/sdk'` beside a
    literal dynamic import for the value, so the client is still loaded lazily but
    its .d.ts is type-checked under `skipLibCheck: false`. Measured before
    choosing: it is clean today. The trade is real in both directions — this is
    the ONLY check that exists on the live request shape while no credential does,
    and an SDK upgrade whose declarations do not compile under ES2022-with-no-DOM
    would redden `bun run typecheck` for a reason unrelated to the harness. The
    alternative is a non-analyzable specifier (a variable, as loadAdapter() uses),
    which buys immunity and costs the shape check. RECOMMEND KEEPING AS WRITTEN;
    the version is pinned in bun.lock, so the failure mode arrives only on a
    deliberate upgrade.

P2. THE VOTE COUNT IS READ AT CONSTRUCTION, so an unusable override fails at
    createHarness() rather than at whichever test first judged something. The plan
    said the oracle constructs from h.config and this is the literal reading.
    Consequence worth naming: every harness reads that knob, including the
    twenty-nine suites that will never judge anything, and an unpinned or invalid
    value would break all of them at once rather than only the oracle's consumers.
    RECOMMEND KEEPING — an override that names a knob and gets it wrong should be
    loud — but it is a coupling the item agent should see rather than discover.

P3. VALIDATION PREDICATES LIVE IN oracles.ts, NOT guards.ts. Plan §4b puts them
    there and I followed it. The argument for guards.ts is real: that file exists
    because a bug in a centralized guard green-lights every suite at once, which
    is precisely this file's situation. The argument against is that guards.ts is
    scoped to checks EVERY SUITE would otherwise re-assert, and these are one
    capability's construction checks. They are exported and tested both directly
    and through the implementation, which is the standard guards.ts is held to.
    RECOMMEND KEEPING; flagged because it is a judgement, not a mechanical step.

P4. `createOracleCapability` GAINED A `recordingsDir` SEAM alongside the
    transport seam the plan blessed. Without it, "live mode never consults the
    replay store" could only be argued from the code rather than observed: the
    test needs a directory holding a MATCHING recording for every vote, handed to
    an integration-tier capability that must still refuse. The seam is consulted
    only at loop tier and the harness passes neither override. RECOMMEND KEEPING —
    it is what turns F3's live-never-replay clause into a real test.

P5. PROVENANCE CARRIES ARRAYS WHERE THE PLAN NAMED SINGULARS. §3c lists "model id
    requested, response.model served, request hash"; with k votes there are k
    served models and k hashes, so VerdictProvenance has `servedModels[]` and
    `requestHashes[]` in vote order. Collapsing them would hide exactly the case
    they exist for — two votes served by different infrastructure under one pinned
    id. RECOMMEND ACCEPTING as the faithful reading.

P6. THE 'source' FIELD WAS SPLIT IN TWO. §4b says recordings carry provenance
    including `source`. As built, JudgeResponse.source is where the bytes came
    from THIS RUN ('live' | 'replay') and RecordingEntry.recordedFrom is how they
    were produced ('live' | 'synthetic'). One field could not do both jobs: the
    replay transport must rewrite the source to 'replay', because a verdict
    replayed from a live recording that reported source 'live' would be claiming a
    call that did not happen this run — the exact lie provenance exists to
    prevent. RECOMMEND ACCEPTING.

P7. live-smoke.md WAS WRITTEN IN THE NO-KEY STATE. The plan conditions that file
    on having a credential. It is committed anyway, titled "NOT RUN" on its first
    line, because an absent file states nothing and a reader six months from now
    should find the boundary written down rather than infer it. If the item agent
    would rather the file not exist until it holds a measurement, deleting it
    costs nothing — but the boundary then needs to live somewhere else that the
    pull request points at.

P8. THE RECORDER STORES ONLY THE FIRST REPEAT. The five stability repeats send an
    identical request, so they hash to identical keys and only one set can be
    stored; the spread across repeats goes in the report instead. This follows
    from the key design rather than being a choice, but it is worth the item agent
    knowing that "recorded" and "measured" cover different numbers of calls.

P9. ONE CONFORMANCE TEST AIMS THE REAL WRITER AT THE REAL COMMITTED DIRECTORY, to
    prove the refusal on the path that matters rather than on a temp path. It
    cleans up in a `finally` — proven necessary, because the third mutation run
    made the refusal regress and the writer really did leave a recording behind.
