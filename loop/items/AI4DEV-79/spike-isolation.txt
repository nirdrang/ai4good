WHAT HAPPENED

`supabase db reset` was aimed at slot 2. It was given --workdir <slot-2> and it was run with
its working directory set to <slot-2>. It nevertheless removed and recreated the container
supabase_db_poancmeitlmxejofwzuu - the founder's personal database - and it bound the new
container to 56322, which is slot 2's port. The new container could not start, because slot 2's
own database already holds that port. The CLI said so in its own words:

  failed to start docker container "supabase_db_poancmeitlmxejofwzuu": Bind for 0.0.0.0:56322
  failed: port is already allocated
  Try stopping the running project with supabase stop --project-id ai4good-slot-2

One command, two projects: the personal project's container name with slot 2's port.

The two older personal volumes are the originals. The database volume is NOT: it was created at

The scratch schema question is moot: the database that held it no longer exists.

WHY IT HAPPENED - the root cause, measured

The tracked file `.env` at the repo root contains:

  SUPABASE_PROJECT_ID="poancmeitlmxejofwzuu"

The Supabase CLI treats SUPABASE_PROJECT_ID as an override of `project_id` in config.toml. It
therefore overrides the slot's identity while the slot's config.toml still supplies the ports.
The override reaches the CLI by TWO separate routes, and both must be closed:

  1. through the process environment. The spike program was started by `bun spike.ts` with its
     working directory on the repo, so bun auto-loaded the repo's `.env` into its own
     environment, and the CLI child inherited it.
  2. through the CLI's own working directory. The CLI reads a `.env` file from the directory it
     runs in. This is the earlier finding recorded in the S2 setup transcript, where
     `supabase --workdir <slot-1> status` run from the repo reported slot ports beside personal
     containers. That was the same override arriving by the other route.

THIS IS WHY THE SETUP STEP WAS SAFE AND THE SPIKE WAS NOT. The pool's own code calls the CLI
through `childEnv()`, an ALLOWLIST that does not carry SUPABASE_PROJECT_ID, and with the
working directory set to the slot, which has no `.env`. Both routes are closed there, which is
why setup created correct slot containers. The spike script called the CLI directly and closed
neither. The pool code was right by construction and the hand-written spike was not, so the
spike measured the hazard instead of the wall.

WHAT THIS MEANS FOR THE DESIGN

--workdir is NOT the isolation mechanism. A slot is isolated only when all three agree:
the config it reads, the environment it runs in, and the working directory it runs from. The
safe form is to state the identity positively rather than merely to avoid overriding it: pass
SUPABASE_PROJECT_ID=<the slot's project id> to every slot invocation, so the variable that
caused this becomes the one that enforces correctness, and add a guard that refuses when the
containers the CLI would act on do not carry the slot's project id.

THE WALL IS THEREFORE UNPROVEN. This transcript is evidence of a hazard, not of isolation. The
spike has to be run again, with the identity stated on every invocation, before anything is
built on it.
