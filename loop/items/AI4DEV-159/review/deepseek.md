## Findings

### 1. [critical] Stop reconciliation remounts the chat while the next send is in flight, aborting it
**Location**: `src/routes/discovery/$organizationId.$projectId.tsx:89-96, 126-131, 262-270` (remount at `:145-153`)
**Finding**: After Stop, the SDK moves `status` to `ready`, so `busy` is false and Send is immediately enabled, while `reloadAfterStop` is still polling for settlement (up to 10×500 ms). When that poll resolves it unconditionally does `setHistory(next)` + `setChatGeneration(v+1)`, which remounts `DiscoveryChat`. `useChat` stops the chat on unmount (`node_modules/@ai-sdk/react/src/use-chat.ts:139-147` → `ai/src/ui/chat.ts:616-622`), so if the user sent a new message during the window, its fetch is aborted, its optimistic bubble and any streamed text are dropped (the remount re-seeds from a conversation read taken before/around that send), the composed draft is wiped because it is component-local state, and the server still settles and charges the aborted turn. A second, related defect: `stoppingRef` (line 266) is only cleared inside the transition-to-`ready` branch, so an abort whose stream ends in `status: "error"` leaves the flag set and fires a spurious reconciliation on the next successful turn — the same remount/abort happens later out of nowhere.
**Evidence**: `busy = status === "submitted" || status === "streaming"` (line 272) is false after an abort (`ai/src/ui/chat.ts:825-843` sets `ready`); `onStopSettled` runs `readConversationOnceSettled`, whose termination condition is the server's settle finishing in `EdgeRuntime.waitUntil` (`supabase/functions/_shared/edge.ts:416-420`) plus a provider recount (`anthropic-messages.ts:62-75`) — nothing bounds that at one render tick. The live drive measured it landing after a read or two, i.e. a real race window, not a theoretical one.
**Suggestion**: Make reconciliation an explicit pending state that keeps Send disabled, and merge the settled turn into the existing message state (`setMessages`) instead of remounting; clear `stoppingRef` on `error` as well, or drop the ref and key the reload off the abort itself.

### 2. [warning] The displayed allowance regresses to the mount-time value during every later stream
**Location**: `src/lib/discovery-chat.ts:103-114` (`allowanceFromMessages`), used at `src/routes/discovery/$organizationId.$projectId.tsx:273`
**Finding**: The reverse scan returns `null` at line 112 as soon as the newest assistant message has no `data-turn` part, instead of continuing to earlier assistants. Once turn 1 has settled (assistant 1 carries `data-turn` with 9 remaining) and turn 2 starts streaming (assistant 2 is text-only), the function returns `null`, so `shown = null ?? allowance` falls back to the value read at page load (10). The line jumps 9 → 10 mid-stream and only corrects when turn 2 settles. The intent explicitly says "the allowance line from the last `data-turn` part", i.e. the last one anywhere, not the last message's.
**Evidence**: Lines 104-113: the outer loop takes the first assistant from the end (line 106), the inner loop searches only that message (107-111), and line 112 terminates the whole function before any older assistant is examined. If a later stream fails before its `data-turn`, the stale value persists indefinitely.
**Suggestion**: Replace the line-112 `return null` with `continue` (a one-line fix), or delete the scan entirely and capture the part in `useChat`'s `onData` callback into state. Add a unit test for `allowanceFromMessages` — it is pure, and three cases would have caught this.

### 3. [warning] A rejected `fetch` is unhandled; the page can sit on "loading" forever with no retry
**Location**: `src/routes/discovery/$organizationId.$projectId.tsx:111-124` and `:126-131`; fetch at `:44-52`
**Finding**: `readConversation` awaits `fetch` with no try/catch, and neither caller attaches a rejection handler: the load effect does `void readConversation(projectId).then(...)` and `reloadAfterStop` does `void readConversationOnceSettled(projectId).then(...)`. A network-level failure (functions down, CORS refusal, connection drop) rejects the promise, leaves `history` at `{kind:"loading"}` (rendered as "loading" at line 143) and reports nothing; after a stop it leaves the aborted view frozen. There is no retry control on the page, and the load effect's dependency on `session.kind` means a later token refresh never re-reads.
**Evidence**: `fetch` rejects only on transport failure, but that is exactly the case the page has no path for; the server's own shaped refusals (4xx/502) are handled, so the gap is only the exception path — and it is the one that silently strands the user.
**Suggestion**: Wrap the body of `readConversation` in try/catch and return `{kind:"failed", reason}`; give `readConversationOnceSettled` the same treatment; add a retry button on the failed state.

### 4. [warning] A refused send leaves a ghost user bubble that a reload erases
**Location**: `src/routes/discovery/$organizationId.$projectId.tsx:254-260` (`onError`), `:275-285` (`onSend`)
**Finding**: `sendMessage({text})` pushes the user message before the request (`ai/src/ui/chat.ts:436-442`). On a 4xx refusal the catch path calls `onError` and sets `status: "error"` without removing it (`chat.ts:860-864`), and the page only records the refusal. Since the server refused before reserving, no turn row exists, so the next conversation read has no such message — the bubble silently disappears on reload. The draft was already cleared (line 280), so that ghost is the only copy of the text. For a page whose job is to prove what the server did and did not accept, showing a refused message as if sent is actively misleading.
**Evidence**: Live-verify's zero-credit step ("user text stays, no assistant text") exhibits the shape; `readConversationOnceSettled`/reload reconciles it away, proving divergence between local messages and server truth.
**Suggestion**: On a refusal, reconcile: either drop the optimistic message (e.g. `setMessages` to remove the last user message) or re-read the conversation; and clear the draft only once the send is accepted.

### 5. [warning] The stop poll cap presents an open turn as settled, freezing the reply and allowance until a manual reload
**Location**: `src/routes/discovery/$organizationId.$projectId.tsx:89-96`
**Finding**: The loop polls at most 5 seconds and then returns whatever it has, even if the last turn is still `open`. Settlement after an abort runs in `EdgeRuntime.waitUntil` after the browser is gone, including a `countTokens` recount round trip with a 120 s client timeout; nothing bounds it at 5 s. When the cap is hit, `setHistory` + remount replaces the partial text the user just watched stream with a turn whose `assistant_message` is still `null` (the reserve inserts it null), and the allowance stays at the pre-turn value until another reload. A transient read failure inside the poll has the same effect but worse: it returns `{kind:"failed"}` and clobbers the good loaded history with a bare reason string.
**Evidence**: `readConversationOnceSettled` returns `next` unconditionally (line 95); `anthropic-messages.ts:72-75` performs a provider `countTokens` before `stopped()` resolves, and the settle RPC only runs after that. The live-verify report's own "one defect found and fixed" documents the stale-allowance half of this; the cap still re-opens it whenever settlement is slower than the window.
**Suggestion**: Poll with backoff and keep a visible "settling" state; do not remount onto an `open` turn — keep the client's partial text and the pre-settle allowance until the read shows a terminal status. Retain the previous `loaded` history when a poll read fails.

### 6. [warning] `fatal()` crashes inside its own transcript writer on every early failure
**Location**: `.claude/skills/verify-ai4good/scripts/prepare-chat-page.ts:55-59, 273-280` (ids declared at `:185`, `:203`; early `fatal` calls at `:85, :103, :112, :146`)
**Finding**: `fatal()` calls `flush()`, which reads module-scope `const organizationId`/`projectId` (and, for the very first failure, `email`/`orgName`) before those bindings are initialized. Any failure before `complete-signup`/`project-need start` therefore throws `ReferenceError: Cannot access 'organizationId' before initialization` from inside the `catch` block, so the promised `ABORT: ...` message and the evidence transcript — the script's whole purpose — are never produced.
**Evidence**: The simplest reachable path is the first doctor step: `stackFromLocalStatus` throws when the stack is down, the catch at `:82-86` calls `fatal`, and `flush` at `:277` evaluates `organizationId` in its TDZ.
**Suggestion**: Declare `let email = ''; let organizationId = ''; let projectId = '';` before the first fallible operation and assign as the run progresses, or make `flush` read them defensively.

### 8. [nit] The CRLF fix normalises one reader instead of the input, so the artifact comparison now depends on the bundler
**Location**: `tests/at/harness/discovery-skills.ts:7`; `.gitattributes:17-18`
**Finding**: `.gitattributes` deliberately leaves `.md` to the platform, so on Windows the skill files and the checked-out generated `index.ts` are CRLF. The reader now strips CR, but the imported `DISCOVERY_SKILLS` template literals are only equal after esbuild's transform normalises the module's line endings — i.e. the drift selftest passes because of loader behaviour, not because the on-disk artifact was compared. Any other byte-level consumer of a tracked text file will hit the same class.
**Evidence**: This worktree's `supabase/functions/_shared/discovery-skills/index.ts` and all `*.md` carry CRLF (every line matches `\r$`); after the change the reader yields LF while the raw file does not.
**Suggestion**: Pin the skill markdown to LF (`supabase/functions/_shared/discovery-skills/*.md text eol=lf` in `.gitattributes`) or explicitly compare normalised content in the test, so the invariant is enforced rather than incidental.

### 9. [nit] The conversation boundary is a hand mirror with blind casts and an unreachable guard
**Location**: `src/lib/discovery-chat.ts:12-43, 94-101`; `src/routes/discovery/$organizationId.$projectId.tsx:81-85`
**Finding**: `DiscoveryTurn` duplicates the server's `DiscoveryTurnView` by hand, and `readConversation` casts both `turns as DiscoveryTurn[]` and `allowance as Allowance | null` without checking the fields the page actually consumes (`id`, `status`, `userMessage`, `assistantMessage`, and the allowance numbers). The stream path validates with `isAllowance`, the read path does not, so a contract change or a malformed 200 flows straight into `messagesFromTurns` and the `status === "open"` poll. `allowanceFromTurnData`'s direct-allowance branch (line 95) is also dead: the shipped `data-turn` payload is always `{ ok, turn, reply, elicitation, allowance }`, so that check can never fire.
**Suggestion**: Validate the consumed subset once at the boundary (a small type guard over ids/strings/status membership, reusing `isAllowance` for the read) and fail closed to `{kind:"failed"}`; drop the direct-shape branch.
