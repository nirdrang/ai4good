### 1. [warning] Send stays live during the after-stop reread, and the remount then kills whatever it started
**Location**: `src/routes/discovery/$organizationId.$projectId.tsx:126-131` (`reloadAfterStop`), `:147` (the `key`), `:272` (`busy`), `:330` (Send)
**Finding**: After Stop, `status` returns to `ready` at once (client-side abort), so `busy` is false and Send is enabled. `reloadAfterStop` is still polling the conversation (up to ten reads at 500 ms). When the poll returns it bumps `chatGeneration`, which changes the `key` and remounts `DiscoveryChat`. If the person sent a second message inside that window, the remount aborts it: `useChat` registers an unmount effect that calls `chat.stop()` (`node_modules/@ai-sdk/react/dist/index.js:357-364`). The server treats that disconnect as a user stop (`supabase/functions/_shared/edge.ts:416-420` cancels, `anthropic-messages.ts:72-75` answers `user_stopped`) and settles and charges the partial turn. The new component then renders the history the poll read, which predates the second message. The second message vanishes from the page without a trace, and the draft was already cleared at `:280`.
**Evidence**: Path: Stop at `:288-289` -> `makeRequest` catch sets `ready` (`node_modules/ai/dist/index.js:21441-21446`) -> effect at `:263-270` calls `onStopSettled` -> `readConversationOnceSettled` runs (first read is a network round trip; the server needs a `countTokens` round trip plus a database write before the stopped turn leaves `open`, `edge.ts:399-403`) -> meanwhile `busy === false` -> person sends -> `setChatGeneration` -> unmount -> `chat.stop()`. If the stopped turn is still `open` when the second send arrives, the server answers 409 `turn-in-flight` instead (`supabase/migrations/20260923120100_organization_discovery_switch.sql:183-187`); the refusal is then wiped by the same remount, because `refusal` is component state. Both branches lose the message. The window is short (roughly 0.5 to 5 s), which is the only reason this is not marked critical.
**Suggestion**: Keep a `settling` state that is true from Stop until the reread has been applied, and fold it into `busy`. Or take the shape in finding 3, where no remount exists and the same flag is one line.

### 2. [warning] The settle wait checks the wrong predicate for a stop that lands before the first byte
**Location**: `src/routes/discovery/$organizationId.$projectId.tsx:89-96` (`readConversationOnceSettled`)
**Finding**: The loop waits while `turns.at(-1)?.status === "open"`. That predicate assumes the stopped turn already exists in the table. It does not exist during the `submitted` phase: the server reserves the turn only after the caller lookup, `write_standing`, the need read, the turns read and a provider `countTokens` round trip (`edge.ts:350-375`, `discovery-turn.ts:91-114`). A stop in that phase makes the first read return the previous settled turn as the last one, the loop exits at once, and the page remounts with an allowance that predates the reservation. The server then reserves the turn and, on the closed connection, settles it as failed (refund) or `user_stopped` (charge) after the page has already read. This is the exact defect `live-verify.md` records as found and fixed ("the page showed 4 of 10 while the ledger said 5 spent"), reopened on a different timing. The recipe's own lever, an in-page Stop 700 ms after Send, sits at the edge of that window on the local stack and inside it on any hosted deployment with more latency.
**Evidence**: `submitted` lasts from `makeRequest` setting the status (`node_modules/ai/dist/index.js:21351`) until the first stream byte; `stop()` aborts the fetch in that phase because `activeResponse` is assigned before `transport.sendMessages` is awaited (`:21369-21384`). The server handler keeps running after the client is gone; nothing in `edge.ts` reads `request.signal`. Whether the runtime invokes `cancel()` on a body it never began sending is not established anywhere in this tree; if it does not, the turn stays `open` for `DISCOVERY_TURN_DEADLINE_SECONDS` (150 s, `discovery-metering.ts:7`) and every send in that time answers `turn-in-flight`. The page has no handling for either case.
**Suggestion**: Remember the highest `seq` the page knows before the send. After a stop, poll until a turn with a higher `seq` exists and is not `open`, or a deadline passes. Keep Send disabled while polling (finding 1). If the deadline passes with the turn still open, say so on the page instead of showing a stale allowance.

### 3. [warning] The stop-and-reload machinery rebuilds two hooks the SDK already exposes, and the remount is what makes findings 1 and 2 hard to fix
**Location**: `src/routes/discovery/$organizationId.$projectId.tsx:102` (`chatGeneration`), `:126-131`, `:147`, `:225` (`stoppingRef`), `:262-270` (status-transition effect), `:287-290`
**Finding**: Five moving parts detect "the abort has landed" and then replace the message list: a ref set in `onStop`, a second ref holding the previous status, an effect that watches the transition, a generation counter, and a `key` that remounts the whole chat with a new initial `messages`. The SDK gives both halves directly. `onFinish({ isAbort })` fires from the `finally` of `makeRequest` after the status has been set to `ready` on abort (`node_modules/ai/dist/index.js:21440-21470`; typed at `node_modules/ai/dist/index.d.ts:5580-5587`). `setMessages` replaces the list on the live `Chat` without a remount (`node_modules/@ai-sdk/react/dist/index.js:417-425`). The remount also throws away `draft` and `refusal`, and it is the mechanism behind finding 1.
**Evidence**: The status-transition effect has an edge the SDK hook does not: if Stop is clicked after the stream has already reached `ready` (the button's `disabled` lags the status by one render), `stoppingRef` stays true and the next completed turn triggers a spurious reload. With `onFinish`, `isAbort` is computed from the abort signal of the request that actually ended.
**Suggestion**: One handler, no remount:

```ts
const [allowance, setAllowance] = useState(initialAllowance);
const [settling, setSettling] = useState(false);
async function onStop() {
  setSettling(true);
  await stop();
  const next = await readConversationOnceSettled(projectId);   // with the predicate from finding 2
  if (next.kind === "loaded") { setMessages(messagesFromTurns(next.turns)); setAllowance(next.allowance); }
  setSettling(false);
}
const busy = settling || status === "submitted" || status === "streaming";
```

`await stop()` returns before the status flips, but the first conversation read is a network round trip and every `write()` of the aborted request checks the abort signal first (`index.js:21395-21397`), so `setMessages` cannot be overwritten by a late delta. This deletes `chatGeneration`, the `key`, `onStopSettled`, `reloadAfterStop`, both refs and the effect, and `HistoryState` no longer needs to be rewritten after a stop.

### 4. [warning] The allowance path accepts a shape the server never sends and validates a payload the sibling path trusts
**Location**: `src/lib/discovery-chat.ts:81-115` (`isAllowance`, `allowanceFromTurnData`, `allowanceFromMessages`); `src/routes/discovery/$organizationId.$projectId.tsx:83-84`, `:273`
**Finding**: `allowanceFromTurnData` first tests whether `part.data` is itself an allowance, then whether it carries a nested `allowance`. The server emits one shape: `data-turn.data` is `{ ok: true, turn, reply, elicitation, allowance }` (`edge.ts:405` spreads `renderDiscoveryMessage`, `discovery-turn.ts:184-191`; the grounding at `loop/items/AI4DEV-159/how/explanation.md:280` says the same). The bare branch is dead. Meanwhile `readConversation` casts `body.allowance as Allowance | null` and `turns as DiscoveryTurn[]` with no check at all. The two boundaries to the same first-party server are validated to opposite standards, and the reason is that the stream path has to find the allowance by walking `messages` backwards from the last assistant message.
**Evidence**: `allowanceFromMessages` returns `null` as soon as the last assistant message carries no `data-turn` part, which is every message loaded from history and every stopped turn; the `?? allowance` at `:273` then papers over that. The rule "last data-turn, else the read" is a rule about *time*, and time is what state holds.
**Suggestion**: Hold the allowance in state. `useChat` takes `onData`, which is called for every data part including non-transient ones (`node_modules/ai/dist/index.js:7614-7628`): `onData: (part) => { if (part.type === "data-turn") setAllowance(part.data.allowance); }`. Type `data-turn.data` once as the JSON 200 body of `discovery-message` (the explanation says they are byte-identical), and either trust both boundaries or check both with the same guard. `isAllowance`, `allowanceFromTurnData`, `allowanceFromMessages` and the `??` go away.

### 5. [warning] Two wire types are hand-copied under a comment whose claim does not hold for types, with no drift check
**Location**: `src/lib/discovery-chat.ts:3-10` (`Allowance`), `:12-43` (`DiscoveryTurn`), `:45` (`Refusal.kind: string | null`)

A type-only import is erased by esbuild before Vite bundles, so the browser bundle never sees the Deno tree. **Evidence**: `elicitation.complete: true`, `requestSettings.effort: "low"` and the six micro-cost fields are copied verbatim and never read. `Refusal.kind` is `string | null` while the server's kinds are the closed union `WriteRefusalKind` (`write-routes.ts:80-114`).

If the app project must stay inside `src/` for a reason not stated here, keep the copy but add a harness selftest that asserts the two shapes are assignable both ways, and fix the comment.

### 6. [warning] `prepare-chat-page.ts` cannot write its transcript on any abort before complete-signup
**Location**: `.claude/skills/verify-ai4good/scripts/prepare-chat-page.ts:55-59` (`fatal`), `:273-280` (`flush`), `:185` (`const organizationId`), `:203` (`const projectId`)
**Finding**: `fatal()` calls `flush()`, and `flush()` reads `email`, `orgName`, `organizationId` and `projectId`. Those are top-level `const` bindings declared at `:89-91`, `:185` and `:203`. Every `fatal` before those lines runs (`:85` stack read, `:103` health, `:112` mail, `:146` docker mount, `:153` signup, `:159` no link, `:162` no redirect, `:168` no token) reaches `flush()` while the bindings are in their temporal dead zone. The access throws `ReferenceError: Cannot access 'organizationId' before initialization` from inside `flush()`, before `writeFileSync` and before `process.exit(1)`. The run prints `ABORT: ...` and then dies on an uncaught exception with no `transcript.json`. Every doctor failure, the most common abort in practice, takes this path.
**Evidence**: ES module top-level `const` and `let` are in the dead zone until their declaration is evaluated; a hoisted function declaration that references them throws when called earlier. Bun preserves `const`. The happy path never shows this because the final `flush()` at `:282` runs after every declaration. The shape is copied from `drive-discovery.ts:52-56` and `:585-592`, where `ngoEmail` (`:167`) and `organizationId` (`:277`) sit after the first `fatal` (`:163`) in the same way, so the sibling scripts carry the same latent defect; this review covers the new file.
**Suggestion**: Declare the ids as `let organizationId = ""` and `let projectId = ""` above the first `fatal`, or give `flush` the summary as a parameter and build it from what exists at the call site.

### 10. [nit] The session type lacks the state the page starts in, so the sign-in form flashes for a returning user
**Location**: `src/routes/discovery/$organizationId.$projectId.tsx:25` (`SessionState`), `:100`, `:133-135`
**Finding**: `session` starts as `signed-out`, and `onAuthStateChange` emits `INITIAL_SESSION` asynchronously after `initializePromise` and a `_useSession` call that can include a network refresh (`node_modules/@supabase/auth-js/dist/module/GoTrueClient.js:3640-3651`). **Suggestion**: `"unknown" | "signed-out" | "signed-in"` as a string union; render nothing or "loading" for `unknown`.

### 11. [nit] A rejected conversation read leaves the page on "loading" with an unhandled rejection
**Location**: `src/routes/discovery/$organizationId.$projectId.tsx:118-120`, `:127-130`
**Finding**: `readConversation` lets `fetch` and `getSession` rejections escape; both call sites use `void promise.then(...)` with no `catch`. A stack that is down, or a refused preflight, leaves `history` at `loading` forever and logs an unhandled rejection. The same read on the after-stop path leaves the old chat in place with `stoppingRef` already cleared.
**Suggestion**: Catch inside `readConversation` and return `{ kind: "failed", reason }`; it already returns that shape for every other failure.

### 12. [nit] The refusal is re-parsed from `error.message` when the error already carries the body typed
**Location**: `src/routes/discovery/$organizationId.$projectId.tsx:257-259`; `src/lib/discovery-chat.ts:66-79`
**Finding**: A non-2xx answer surfaces as `APICallError` with `statusCode` and `responseBody` (`node_modules/ai/dist/index.js:20668-20683`); the page reads `error.message`, which is the same body by coincidence of the SDK's fallback, and re-parses it. Stream `error` parts (`errorText`) arrive as plain `Error` and are text, not JSON.
**Suggestion**: `APICallError.isInstance(error) ? refusalFromResponseText(error.responseBody ?? "") : { kind: null, reason: error.message }`. The JSON parse then runs only on a body that can be JSON.

### 13. [nit] Three dead paths in the chat component
**Location**: `src/routes/discovery/$organizationId.$projectId.tsx:305`, `:241-248`, `:281-284`
**Finding**: (a) `if (!text && message.role !== "assistant") return null;` keeps an empty `<li>` for an assistant message with no text, which exists before the first delta and forever after a stream `error` that arrived before any text; `if (!text) return null` is the whole rule. ### 14. [nit] The line-ending fix lives in the reader; the tree already has the structural tool for this class
**Location**: `tests/at/harness/discovery-skills.ts:7`
**Finding**: The generator writes the skill bodies into template literals, and a template literal normalises CRLF to LF when parsed, so the generated `DISCOVERY_SKILLS` always holds LF while the reader returned the checkout's bytes.
