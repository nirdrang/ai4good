## Findings

### 1. [warning] After one transfer, the organisation can never be transferred or recovered again
**Location**: `supabase/functions/_shared/admin-operations.ts:88-97` (`decideContactTransfer`), `supabase/migrations/20260908120000_account_lifecycle_audit_and_contact_transfer.sql:329-337`, `tests/at/suites/req-001/_integration.ts:1796-1801` (`transferGiven`)
**Finding**: The transferee B is a completed NGO account (R5), so B already holds the seat of its own organisation Y. After the transfer B holds X and Y. Every later transfer out of B is refused with `holds-other-seats` (R6), because B always holds "another" seat. Transferring Y first is refused for the same reason (B still holds X). So the account that receives a seat can never hand it on, and lost-access recovery (AT-001.27) is impossible for any organisation from its second contact onward.
**Evidence**: `decideContactTransfer` computes `otherOrganizations = standing.orgSeatHolderSeats.filter((id) => id !== organizationId)` and refuses when it is non-empty; the definer does the same with `v_other_seats`. `transferGiven` builds B exactly this way (`completeSignup` with `organizationName`), so every acceptance body's transferee is in this state, and no body attempts a second transfer out of a transferee. The design lists this under "Open questions and risks" item 3 and ships without an answer or a test. The intent says recovery "is the same operation"; it is the same operation once.
**Suggestion**: This follows from two rulings (R5, R6) and needs the lead, not a code edit alone. Two shapes that keep R6's stated purpose (no silent blast radius): a request that names every seat the outgoing account holds and moves them all in one transaction; or a transfer that moves the seat and deactivates the outgoing account only when it holds no other seat, and otherwise records in the audit row that the account stays active. Either way, add a body that transfers out of a transferee.

### 2. [warning] The role-change trigger's UPDATE half is unverified at both tiers
**Location**: `tests/at/suites/req-001/_integration.ts:2476-2492` (`assertAppendOnlyAudit`), `supabase/migrations/20260910120000_org_membership_role_change_audit.sql:45-69`
**Finding**: AT-001.33's assertions about `org_role_changed` are all satisfied by the INSERT rows the Given writes before the act. The operator re-point and the transfer's seat move contribute nothing observable.
**Evidence**: `transferGiven` completes NGO A through `completeSignup`, which inserts A's membership and fires the trigger's INSERT branch with no actor, writing `{event_kind: org_role_changed, actor_account_id: null, actor_label: 'operator', subject_org_id: X}`. The body then asserts `orgEvents.some(kind === 'org_role_changed')` and `orgEvents.find(kind === 'org_role_changed' && actorAccountId === null && actorLabel === 'operator')`. Both are true before `repointMembershipAsOperator` runs. No assertion anywhere names `reason: 'seat repointed'`, `detail.old_account_id`, or a role-change row whose actor is the administrator (the transfer's own seat move under `set_config`). A trigger bound to INSERT only, or one whose UPDATE branch returns early, passes AT-001.33 at both tiers. The unit 3 report's open doubt 2 says the same and was not acted on.
**Suggestion**: Assert the exact rows: one `org_role_changed` with `reason: 'seat repointed'`, `actorAccountId === admin`, `detail: {old_account_id: A, new_account_id: B}` after the transfer; one more with `actorAccountId === null`, `actorLabel === 'operator'`, `detail: {old_account_id: B, new_account_id: A}` after the re-point. Count them, do not `some` them.

### 3. [warning] The SQL conformance scan forgets a definer's grant on `create or replace`, so a replaced definer that drops the gate passes CI
**Location**: `tests/at/suites/req-001/_policy-scan.ts:594-606, 640-647` (`scanWriteGateSql`)
**Finding**: On every `create [or replace] function`, the scan resets the entry to `executeRoles: new Set()`. Postgres keeps privileges across `create or replace`; the scan does not. A later migration that replaces `set_escalation_contact` (or any write definer) without the `perform public.assert_account_active(...)` line and without restating the grant is reachable by `service_role` on the live database and invisible to `definer-no-write-gate`.
**Evidence**: Line 642 requires `fn.executeRoles.has('service_role')`; after the replace the set is empty, so the check is skipped. The selftest `write-route-scan.selftest.ts` has no case for a replace. The only thing that catches a bare replace today is the other scan: `scanTenantMigrations` also resets `revokedPublic` and then raises `definer-no-revoke`, so an author is pushed to restate the revoke. Restating the revoke and not the grant is the natural minimal fix to that failure, and it is exactly the shape that slips past the gate check. The 20260908 migration's own comment says "`create or replace` keeps privileges, and the revoke and the grant are restated anyway", which documents the reliance and not the scan's behaviour.
**Suggestion**: On `create or replace`, carry the previous entry's `executeRoles` forward (`fns.get(name)?.executeRoles ?? new Set()`), matching Postgres. Add a selftest that replaces a gated definer with an ungated body and no grant line and expects `definer-no-write-gate`.

### 4. [warning] The audit record attributes every product membership grant to the operator, and the actor label lies about type
**Location**: `supabase/migrations/20260910120000_org_membership_role_change_audit.sql:6-10, 23-26`, `supabase/migrations/20260908120000_account_lifecycle_audit_and_contact_transfer.sql:206` (`append_audit_event`)
**Finding**: `complete_signup` and `create_organization` do not set `app.actor_account_id`, so the trigger writes `actor_account_id = null, actor_label = 'operator'` for every NGO signup and every second organisation. The intent's "who" (AT-001.26, AT-001.33) is wrong for the most common role change in the system: the record says a human with the database connection granted the seat. R9 made the operator sentinel for the operator path; using it for product paths is a misattribution the audit table cannot later repair (it is append-only by design). Separately, `append_audit_event` hard-codes the label prefix `platform_admin:` for any non-null actor, so the moment a product definer does set the actor (an NGO completing signup), the label will claim that NGO is a platform administrator.
**Evidence**: `create_organization` was restated in this same branch (20260908 lines 457-502) and still carries no `set_config`. Unit 3's report declines to touch it to avoid "reopening unit 1's writers" inside the same pull request, which is a lane boundary and not a product reason. The fixture mirrors the same nulls (`recordRoleChange(null, membership, null)` in `completeSignup` and `createOrganization`), so the loop tier grades the misattribution as correct.
**Suggestion**: One line in each of the two definers, before their membership insert: `perform set_config('app.actor_account_id', p_account_id::text, true);`. Derive the label from the actor's row (`'<account_type>:<id>'` via a lookup in `append_audit_event`), or store the actor type as its own column, instead of a fixed prefix. Update the fixture mirror to pass the caller as actor on the two product paths.

### 5. [warning] "No other way to reach the database" holds by naming convention; the scan does not look where a bypass would live
**Location**: `tests/at/suites/req-001/_write-route-scan.ts:33, 60-66, 167-193`, `supabase/functions/_shared/edge.ts:452-467` (`publicProjectReads`)
**Finding**: The scan reads only `supabase/functions/<name>/index.ts` (line 171 drops `_shared`) and checks `edge.ts` for one identifier, `callDatabaseFunction`. `edge.ts` already exports a second service-role RPC caller, `publicProjectReads`, which posts to `/rest/v1/rpc/read_public_project`. A new `_shared/whatever.ts` with a `fetch` to `/rest/v1/rpc/<write>` under the service key, imported by any route file, is outside every needle: the route file contains none of `writeRoute`, `callDatabaseFunction`, or `/rest/v1/rpc/`, and `_shared` is never read.
**Evidence**: `REACHES_DATABASE` is applied to `files` only; `exportsCallDatabaseFunction` is applied to `edgeModule` only. The design's table says `rpc-caller-exported` is "what keeps the first six honest"; it keeps one name honest. The existing `publicProjectReads` is a read and takes no function name, so it is not a bypass today; it is the template for one.
**Suggestion**: Read every `.ts` under `supabase/functions` and fail any occurrence of `/rest/v1/rpc/` outside `callDatabaseFunction`'s body and the one known read (`read_public_project`), or fail any `_shared` module other than `edge.ts` that names `/rest/v1/`. Add the selftest case: a `_shared/bypass.ts` with an rpc fetch, imported from a read route.

### 6. [warning] A PostgREST schema-cache miss is answered as `409 refused`, an outage dressed as a judgement
**Location**: `supabase/functions/_shared/edge.ts:399-405` (`writeRoute`)
**Finding**: Every PostgREST status in 400-499 becomes 409 with `kind: parseWriteRefusalKind(outcome.details)`. A 404 `PGRST202` (function not in the schema cache, the exact risk the design's item 7 names), a 401/403 from a rotated service key, or a 400 for a malformed argument all arrive at the client as a 409 conflict with `kind: 'refused'`, which the contract defines as "the adapter could not classify the refusal", and which a client reads as "the database judged this". The standing read on the same path answers 502 for the same failure (`loadWriteStanding`), so one request can be told two different things about one outage depending on which call hit the cache first.
**Evidence**: `PGRST202` bodies carry a string `details` ("Searched for the function public.x with parameters ..."), so `parseWriteRefusalKind` returns `refused`, and `status >= 400 && status < 500` maps 404 to 409. The `unreadable` doctrine in `write-routes.ts` ("a read that did not happen is not a judgement about the caller") is not applied to the write half.
**Suggestion**: Map to 409 only when the body is a raised exception (PostgREST `code` is a SQLSTATE, five characters, or `details` parses to a closed kind); answer 502 for `PGRST*` codes and for 401/403/404.

### 7. [warning] `_fixture.ts` carries the transfer, escalation, lifecycle, rename and create mirrors twice
**Location**: `tests/at/suites/req-001/_fixture.ts:1257-1276, 1300-1308, 1566-1606` versus `1608-1711` (`attemptWrite`)
**Finding**: The `attemptWrite` record re-implements five members line for line: the transfer mirror (seat re-key, `recordRoleChange`, `changeLifecycle`, `appendAudit`) appears at 1575-1583 and again at 1650-1658; the escalation upsert at 1590-1598 and 1668-1676; the lifecycle change at 1604 and 1685; rename and create likewise. The `discovery-message` entry re-implements `sendDiscoveryMessage` inline. Two copies of a mirror in one file is the drift the file's own header calls the defect it exists to delete, and the live adapter shows the cheaper shape: its `attemptWrite` is a map from route name to one `postWrite` call.
**Evidence**: `runWrite` already returns the typed `WriteRefusal`; each member already returns `ok | WriteRefusal`. `attemptWrite` needs only `{ ok: true }` or the refusal.
**Suggestion**: Implement `attemptWrite` as `Record<WriteRouteName, (session, subject) => Promise<WriteAttemptOutcome>>` whose entries call `sut.transferOrganizationContact(...)`, `sut.setEscalationContact(...)`, `sut.setAccountLifecycle(...)`, `sut.updateOrganization(...)`, `sut.createOrganization(...)` and `sut.sendDiscoveryMessage(...)`, mapping `{ ok: true, ... }` to `{ ok: true }`. `createOrganization` and `sendDiscoveryMessage` return `{ ok: false, reason }` without a kind; give them the `WriteRefusal` shape (both already come from `runWrite` or the gate) so the map is uniform. About ninety lines go away.

### 9. [nit] Three unreachable `standing.kind !== 'account'` branches, and a fourth route handles the same union a third way
**Location**: `supabase/functions/_shared/admin-operations.ts:55-57, 149-151, 187-189`; `memberships.ts:140`
**Finding**: For an `account-required` route, `writeGateDecision` has already refused `unreadable` and `no-account` before `decide` runs, so the 502 branch in each admin decision cannot fire through `writePipeline`. `decideOrganizationRename` instead folds the union into `null` role. The optionality is in the type: `WriteRouteInput.standing` is the whole `WriteStanding` union for every route.

Delete the three branches and the three selftest cases that cover them.

### 11. [nit] A seat removal leaves no audit row
**Location**: `supabase/migrations/20260910120000_org_membership_role_change_audit.sql:78-81`
**Finding**: The trigger is `after insert or update`. A membership deleted by cascade (organisation delete, or the `auth.users` cascade R3 keeps) is a role change to nothing and writes nothing. The intent's "role changes ... append rows" is stated without this residual.
**Suggestion**: Bind `delete` too (`old` carries the row; the actor is null on every path that deletes today), or state the residual beside R3's cascade note in the migration.

### 12. [nit] `fromAccountId` is the one id on the wire that is not shape-checked
**Location**: `supabase/functions/_shared/edge.ts:385-391`, `admin-operations.ts:59, 81-87`
**Finding**: `target` and `subject` are refused as `invalid-request` when not UUID-shaped, "because PostgREST would fail the cast". `fromAccountId` is read inside `decideContactTransfer` and compared as a string to the seat holder, so a malformed value answers `409 not-the-current-contact`, a semantic refusal for a syntactic error, and one that a client could read as "somebody else holds the seat".
**Suggestion**: Read `fromAccountId` through the same UUID check in `writeRoute` (a third selector on the spec), or check its shape in the decision and answer `invalid-request`.

### 14. [nit] The identity trigger is measured on the local CLI only
**Location**: `supabase/migrations/20260911120000_volunteer_github_identity_is_permanent.sql:33-37`
**Finding**: `auth.identities` is a vendor-managed table. Any vendor path that deletes identity rows at depth 0 for a volunteer with a GitHub identity (a GoTrue schema migration at container start, an admin identity delete added in a later GoTrue) fails inside Auth with a 500. The probe covered the user unlink and the `auth.users` cascade. Ownership of `auth.identities` on the hosted platform, and whether `postgres` may create the trigger there, is not in the measurements.
**Suggestion**: Record the residual in the migration header beside the two probe files, and add a line to the merge record that the hosted platform is unmeasured for this object.
