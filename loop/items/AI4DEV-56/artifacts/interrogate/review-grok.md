## Findings

### 1. [warning] A successful transfer makes the new contact ineligible for every later transfer
**Location**: `supabase/functions/_shared/admin-operations.ts` (`decideContactTransfer`, other-seats check); `supabase/migrations/20260908120000_account_lifecycle_audit_and_contact_transfer.sql` (`transfer_organization_contact`, other-seats check); transferee created by `complete_signup`
**Finding**: Lost-access recovery cannot run on a contact who already received a seat. Every completed NGO transferee already holds their signup organisation. The transfer then gives them a second seat. The other-seats rule then refuses any later transfer that names them as the outgoing account.
**Evidence**: NGO B completes signup and gets a membership in its own organisation. The transfer updates `org_memberships` for organisation A onto B and does not touch B's signup seat. After that, B holds two organisations. `decideContactTransfer` then does `standing.orgSeatHolderSeats.filter((id) => id !== organizationId)` and refuses `holds-other-seats` when that list is not empty. The SQL backstop does the same with `account_id = p_from_account_id and org_id <> p_organization_id`. Transfer of A from B is refused because B still holds the signup organisation. Transfer of the signup organisation from B is refused because B still holds A. `create_organization` produces the same trap for any NGO that already created a second organisation. The only way out is an operator re-point, which is not the audited recovery route this branch ships. AT-001.27 only recovers the original contact, once.
**Suggestion**: Either refuse a transferee who already holds a seat, or move every seat the outgoing account holds in one transaction, or stop deactivating on transfer unless the outgoing account is left with zero seats.

### 2. [warning] The transferee row and the outgoing account's other seats are read without a lock
**Location**: `supabase/migrations/20260908120000_account_lifecycle_audit_and_contact_transfer.sql` (`transfer_organization_contact`); `change_account_lifecycle`
**Finding**: The definer serialises two transfers of the same seat, and it serialises deactivation of the caller. It does not serialise deactivation of the transferee, and it does not serialise another seat landing on the outgoing account. Both races break the checks the function just made.
**Evidence**: The seat row is taken `for update`. The transferee is then read with a plain `select account_type, lifecycle into v_to_type, v_to_lifecycle from public.accounts where id = p_to_account_id` and no `for share` / `for update`. A concurrent `set_account_lifecycle` takes `for update` on that same row inside `change_account_lifecycle`, can commit `deactivated`, and the transfer still assigns the seat. The organisation's only contact is then a deactivated account. The other-seats query is also an unlocked read of `org_memberships` for `p_from_account_id`. A second transfer can move another organisation onto that account after the check and before `change_account_lifecycle` deactivates it. R6 is then false: a deactivated account still holds a seat this transfer never named. The TypeScript decision uses the same facts from `write_standing`, which is a separate HTTP read with no lock at all; only the definer can close this, and it does not.
**Suggestion**: Take `for update` on the transferee account before the lifecycle check, and take `for share` on every membership row of the outgoing account before the other-seats check. Keep those locks until the deactivation commits.

### 3. [warning] Product membership grants are recorded as the operator, and the audit label cannot name anyone else
**Location**: `supabase/migrations/20260910120000_org_membership_role_change_audit.sql`; `supabase/migrations/20260908120000_account_lifecycle_audit_and_contact_transfer.sql` (`append_audit_event`); `complete_signup` / `create_organization` (not restated)
**Finding**: Every NGO signup and every `create_organization` writes `org_role_changed` with `actor_account_id` null and `actor_label` `operator`. The audit table therefore cannot tell a product grant from an operator grant. The helper that writes the row also hard-codes the only non-null label as `platform_admin:<uuid>`.
**Evidence**: The membership trigger reads `current_setting('app.actor_account_id', true)` and passes that uuid into `append_audit_event`. Only `transfer_organization_contact` calls `set_config('app.actor_account_id', …, true)`. `complete_signup` and `create_organization` insert `org_memberships` and set nothing. `append_audit_event` then does `case when p_actor is null then 'operator' else 'platform_admin:' || p_actor::text end`. That label is not read from `public.accounts`. If a later change sets the actor on signup so the uuid is honest, the label still says platform administrator for an NGO. AT-001.26 filters to `org_contact_transferred`, so it never sees the lie. AT-001.33 looks for some operator row on the organisation and can use the signup grant (see finding 5).
**Suggestion**: Set `app.actor_account_id` in `complete_signup` and `create_organization`. Pass the actor label into `append_audit_event`, or derive it from the actor's account type. Keep `operator` only when the setting is unset.

### 4. [warning] AT-001.29 never drives `complete-signup`, which is also the only write definer without the SQL gate
**Location**: `tests/at/suites/req-001/_integration.ts` (`assertDeactivationGatesEveryWrite`); `tests/at/suites/req-001/_policy-scan.ts` (`WRITE_GATE_EXEMPT`); `public.complete_signup`
**Finding**: The body that claims every enumerated write is gated skips the one route whose database function does not call `assert_account_active`. A deactivated caller who reaches `complete_signup` as the service role is refused by the accounts primary key, not by deactivation.
**Evidence**: The loop is `if (row.standing.kind !== 'account-required') continue`. `complete-signup` is `account-absent-by-design`, so it never calls `attemptWrite`. The TypeScript gate does refuse a deactivated account on that route (`writeGateDecision` checks lifecycle before the exemption), and the selftest covers that. Integration never posts to the deployed function as a deactivated user. `complete_signup` is the exemption row in `WRITE_GATE_EXEMPT` and still has no `perform public.assert_account_active`. The stacked result is: the ungated SQL path is also the untested path. The active control for `set-account-lifecycle` in the same helper is a no-op (`lifecycle: 'active'` on an already-active transferee), and the active control for `transfer-organization-contact` deactivates `transferFrom` for every later row in `WRITE_ROUTES`.
**Suggestion**: Iterate every `WRITE_ROUTES` key, including `complete-signup`. Give each route its own subject so a successful transfer cannot poison the next control. Call `assert_account_active` from `complete_signup` when the account row already exists, or keep the exemption and test the deployed route as a deactivated caller.

### 5. [warning] AT-001.33 does not prove the membership UPDATE trigger
**Location**: `tests/at/suites/req-001/_integration.ts` (`assertAppendOnlyAudit`)
**Finding**: The assertion that an operator role change leaves a null actor labelled `operator` is already true from the signup insert. A trigger that fired only on INSERT would still pass.
**Evidence**: `transferGiven` completes NGO A through `complete_signup`, which inserts `org_memberships` and writes `org_role_changed` with a null actor (finding 3). `assertAppendOnlyAudit` then transfers, re-points the seat as the operator, and does `orgEvents.find((row) => row.eventKind === 'org_role_changed' && row.actorAccountId === null && row.actorLabel === 'operator')`. That find matches the signup row. It does not require `reason === 'seat repointed'`, it does not snapshot audit rows before the re-point, and it does not require a new row after the re-point. The re-point itself is asserted to succeed, so the UPDATE ran; the trigger's UPDATE half is not what the operator-actor assertion measures.
**Suggestion**: Snapshot `org_role_changed` rows before the re-point. After the re-point, require a new row with `reason` `seat repointed`, `actorAccountId` null, and `actorLabel` `operator`.

### 6. [warning] The two restated writers still raise without a kind in DETAIL
**Location**: `supabase/migrations/20260908120000_account_lifecycle_audit_and_contact_transfer.sql` (`create_organization`, `update_organization`); `supabase/functions/_shared/edge.ts` (`writeRoute`)
**Finding**: New definers put the closed kind in `RAISE … USING DETAIL`. The two existing writers this branch restated do not. A service-role caller that hits those backstops gets `kind: "refused"` on the wire.
**Evidence**: `transfer_organization_contact` and `set_account_lifecycle` raise with `detail = 'not-a-platform-admin'` and the other closed kinds. `create_organization` still raises `create_organization refuses account type %: creating an organisation is an NGO-only action` with no `detail`. `update_organization` does the same for the membership and admin checks. `writeRoute` maps a failed RPC with `parseWriteRefusalKind(outcome.details)`. A missing DETAIL becomes `refused`. The edge decision still returns the right kind when the request went through `writePipeline`. The SQL half of R10 does not, on the two functions this migration copied.
**Suggestion**: On the restated bodies, add `detail = 'not-an-ngo-account'`, `detail = 'not-a-member'`, and `detail = 'not-an-admin'` to match the TypeScript kinds.

### 7. [warning] The fixture writes the same admin operations twice
**Location**: `tests/at/suites/req-001/_fixture.ts` (`transferOrganizationContact`, `setEscalationContact`, `setAccountLifecycle`, `attemptWrite`)
**Finding**: The named SUT methods and `attemptWrite` each contain their own copy of the Map writes. `attemptWrite` for `complete-signup` runs the pipeline and then calls `completeSignup`, which runs the pipeline again. The two Discovery paths also disagree on shape: `sendDiscoveryMessage` drops the gate's kind; `attemptWrite` keeps it.
**Evidence**: `transferOrganizationContact` re-keys the seat, calls `recordRoleChange`, `changeLifecycle`, and `appendAudit`. The `attemptWrite` entry for `transfer-organization-contact` repeats that block. Escalation and lifecycle are the same split. `complete-signup` in `attemptWrite` calls `runWrite(SIGNUP_COMPLETION, …)` and then `completeSignup`, which starts with `runWrite(SIGNUP_COMPLETION, …)` again. `sendDiscoveryMessage` returns `{ ok: false, reason: gate.reason }` after `writeGateDecision`. The Discovery `attemptWrite` entry returns `kind` and `status` as well. A later edit to one mirror will not fail the other until an acceptance body happens to use both.
**Suggestion**: Make `attemptWrite` call the named methods. Drive Discovery through one `writePipeline` spec. Stop dropping `kind` on `sendDiscoveryMessage` and `createOrganization`.
