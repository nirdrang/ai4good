The write path, privilege overlay, and two-tier harness are coherent for the three NGO writes that exist today. The problems below are the places that architecture will make the six admin-operations units wrong, brittle, or double-stated.

## Findings

### 1. [structural] Lifecycle is a caller rule; the existing “any path” trigger pattern cannot express it
**Components**: `org_memberships_grantee_must_be_ngo` / `project_seat_holds_a_volunteer` (BEFORE triggers); `public.complete_signup` / `create_organization` / `update_organization` (definers); `resolveCaller` + `Caller`; operator SQL in `_live.ts`
**Finding**: AT-001.29 refuses writes **the deactivated caller attempts**. AT-001.31 then **writes the deactivated row** to re-enable it. Those are opposite questions. Every trigger in this tree answers a question about `NEW`/`OLD` (grantee type, seat occupancy). None sees the JWT. On the operator and service-role connections `auth.uid()` is null, which is why `viewer_is_platform_admin()` is a SELECT-path helper and not a write check. A BEFORE trigger of the AT-001.37 shape (“refuse if the row belongs to a deactivated account”) will block the transfer’s seat UPDATE, block re-enable, and still miss Auth’s own endpoints. A trigger “refuse if the writer is deactivated” cannot see the writer on the paths the operator tests use. The established trigger pattern is the wrong tool for unit 2.
**Evidence**: Trigger comments state they exist because AT-001.37 says “any path including an operator insert” (`20260811125000_...sql` lines 35–40). `repointMembershipAsOperator` is a raw `UPDATE org_memberships SET account_id` (`_live.ts` 552–558). Transfer is that same UPDATE plus a deactivation of the old account. `Caller` is only `{ id, githubHandle }` (`caller.ts` 58–69). Ban probe: after `ban_duration`, `GET /auth/v1/user` with the live access token is still HTTP 200; only refresh and a new password grant fail (`auth-ban-probe.txt` steps 5–7). `verify_jwt` and `resolveCaller` will still accept that token.
**Impact**: If unit 2 copies the membership trigger, unit 1’s transfer and unit 2’s re-enable fight the gate. If unit 2 only bans at Auth, AT-001.29’s “immediately” fails for the remaining 120 seconds of `jwt_expiry`. The gate has to be **caller lifecycle**, loaded from `public.accounts`, in the same TypeScript + definer pair `ngoOnlyActionAllowed` / `create_organization` already use — plus a registry so a fourth `index.ts` cannot skip it. Operator SQL must stay outside that oracle.

### 2. [structural] The product write inventory cannot cover “all global types”
**Components**: the three write functions; `ngoOnlyActionAllowed`; `org_memberships_grantee_must_be_ngo`; `sendDiscoveryMessage`; AT-001.29
**Finding**: AT-001.29 needs, for each global type, a write an **active** account of that type **succeeds** at, then the same write refused after deactivation, so the refusal is not an ordinary role check. Today’s mutating product surface is NGO-shaped.
**Evidence**: After signup, a volunteer cannot call a deployed write that would succeed: `create-organization` refuses non-`ngo` (`accounts.ts` 336–345; `create_organization` SQL backstop); `update-organization` needs a membership, and the trigger refuses any non-`ngo` grantee; `complete-signup` refuses a second completion on the primary key. `sendDiscoveryMessage` is the only volunteer-shaped write, and it is a loop-only stand-in: the live adapter throws `CapabilityPending(['sut.accounts.sendDiscoveryMessage'])` (`_live.ts` 823; `_contract.ts` 721–735). A platform admin is refused by the same NGO-only decision, cannot hold a membership, and cannot complete signup as `platform_admin`. There is no admin write until unit 1’s transfer exists. For `complete-signup` itself: a user with no `accounts` row has no lifecycle column; a user who already completed cannot succeed at completion. It cannot be the “active control succeeds / deactivated fails” pair.
**Impact**: A loop-green AT-001.29 that drives `createOrganization` / `updateOrganization` for a volunteer proves the ordinary type refusal, not deactivation. Integration cannot use Discovery without inventing REQ-002’s route (the last merge already refused that). Unit 2 either (a) registers the transfer route as the platform-admin write and treats volunteer as `capability-pending` on the Discovery stand-in, or (b) invents a volunteer write this requirement does not own. Quietly listing the three current functions as “all endpoints” makes the all-types clause false.

### 3. [structural] Sign-in and GitHub unlink live on Auth, not on the write-route machine
**Components**: `authPost` (POST-only); `config.toml` `[auth.rate_limit]` / `enable_manual_linking`; GoTrue `/auth/v1/token` and `DELETE /auth/v1/user/identities/{id}`; first migration’s ban on `auth.users` triggers; `callDatabaseFunction` import as the write discriminator
**Finding**: Units 3, 5, and 6 are being designed next to a subsystem whose mechanical mark of a write is “`index.ts` imports `callDatabaseFunction`”. Sign-in and unlink never enter that path. A registry-plus-scan over `supabase/functions/*` cannot see them. There is also no Auth hook that fires on unlink (hooks present in the file are `before_user_created` and `custom_access_token`, both commented). The one hook the CLI will push — `password_verification_attempt` (`hook-push-probe.txt`) — fires on a password grant for an **existing** user and does not wrap unlink.
**Evidence**: `authPost` is POST-only (`live-stack.ts` 82–99). No DELETE helper exists. Unlink is recorded as opened and unguarded (`config.toml` 206–212). The first migration refuses a trigger on `auth.users` because failure is “a 500 inside Supabase Auth” (`20260808120000_...sql` lines 8–12). Forty-five password grants against `/auth/v1/token?grant_type=password` returned 45× HTTP 400 `invalid_credentials`, zero 429 (`unit6-signin-rate-limit.txt`). The running container has `GOTRUE_RATE_LIMIT_EMAIL_SENT=360000` while the file says `email_sent = 2`, and `sign_in_sign_ups = 30` did not appear as a distinct env var (`unit6-auth-container-env.txt`). CORS on edge functions allows POST and OPTIONS only (`edge.ts` 72–76), so an edge wrapper cannot intercept Auth’s DELETE without being a different URL the browser is not required to call.
**Impact**: Implementing AT-001.34 as “another registered write route” will not run on sign-in. Asserting `config.toml` values against the local stack will green a limit the process does not honour — the exact failure unit 6 exists to prevent. Implementing unit 5 as an edge function leaves Auth’s unlink URL open. Implementing it as a BEFORE DELETE on `auth.identities` is the only in-tree placement, and it is the same class of Auth-500 footgun the first migration already refused. That has to be measured (does `postgres` hold TRIGGER, and does RAISE become 4xx or 500) **before** the design, not after. AT-001.34 at integration is a `capability-pending` (or a product counter that is not GoTrue’s limiter), not a greppable edge entry.

### 4. [concern] Replacement contact has no product path that yields an NGO account without a new organisation
**Components**: `public.complete_signup` (NGO branch always inserts `organizations` + admin membership); `org_memberships_one_seat_per_org_idx` (unique on `org_id` only); `org_memberships_grantee_must_be_ngo`; `provisionPlatformAdmin` (the only legal extra account mint, and it is `platform_admin`); AT-001.25 / AT-001.27
**Finding**: Transfer must UPDATE the one seat onto an account the NGO-only trigger will accept. The only product path that creates an `ngo` row also creates a new organisation and seats the caller as its admin. There is no “NGO account, no org” write. Admin provisioning inserts `platform_admin` and is deliberately not a service-role insert into `accounts`.
**Evidence**: `complete_signup` NGO branch (`20260808120000_...sql` 205–212, preserved in `20260811120000_...sql`). Unique index on `org_id` alone (`20260811130000_...sql` 41–42) — one seat per org, not one org per account. Trigger requires `account_type = 'ngo'` (`20260811125000_...sql` 79–84). `provisionPlatformAdmin` comments that granting `service_role` INSERT would open a hole past `complete_signup`’s `platform_admin` refusal (`_contract.ts` 794–806). Operator `createOrganizationAsOperator` creates an org **without** a seat, which is the opposite of what recovery needs.
**Impact**: Lost-access recovery that “creates the new owner” either (a) sends them through NGO `complete-signup` and leaves a surplus organisation, (b) mints an `ngo` row inside the transfer definer and skips the ToS acknowledgment `complete_signup` always writes, or (c) requires the new contact to already exist. (b) is a second account-creation path, which this tree has been careful not to grow. The design has to pick one and not pretend `complete_signup` is reusable as-is.

### 5. [concern] History preservation is a foreign-key fact, not an application rule
**Components**: `accounts.id` → `auth.users(id) ON DELETE CASCADE`; `acknowledgments.account_id` → `accounts(id) ON DELETE CASCADE`; `org_memberships.account_id` same; AT-001.25 (“projects, ledger, acknowledgments, audit” still attributed to the original humans)
**Finding**: Deleting the old Auth user deletes the acknowledgment rows AT-001.25 wants kept. There is no ledger table under `supabase/`. Projects hang off `org_id`, not the NGO account, so they survive a person change if the org row stays. The only transfer shape that matches the criterion is: keep `auth.users` + `accounts` for A, mark A deactivated, UPDATE the single membership row to B. That is already `repointMembershipAsOperator`. Deactivation and transfer have to land together because `accounts` today is only `id, account_type, created_at` — there is nowhere to record “old one deactivated” without the lifecycle column.
**Evidence**: `20260808120000_...sql` lines 38–42 and 72–79. `AccountRow` is `{ id, accountType }` (`_contract.ts` 57–60); live `account()` selects `id, account_type` only (`_live.ts` 648–652). `f-lifecycle-and-audit.test.ts` lines 10–14: a flag nothing reads enforces nothing. No `ledger` relation exists under `supabase/`. Architecture notes keep the two-layer role schema so v1.5 multi-member needs no migration; deleting the membership row to “move” the seat fights that.
**Impact**: A transfer that `DELETE`s A’s Auth user, or that DELETE+INSERT the membership row, will either drop acknowledgment history or drop the membership `created_at` that later multi-member work would want. Unit 1 should UPDATE the seat and leave A’s rows in place. Do not invent a ledger in this requirement to satisfy the word in AT-001.25.

### 6. [concern] Account facts are loaded in three untyped copies; lifecycle will become a fourth unless it joins that seam
**Components**: `accountTypeOf` in `create-organization/index.ts` (Deno, no typecheck); `roleIn` in `update-organization/index.ts`; `create_organization` / `update_organization` SQL re-reads; loop fixture Map lookups; `edge.ts` header (“NO TYPE-CHECKER COVERS THIS FILE”)
**Finding**: Who the caller **is** (Auth) and what the caller **may do** (accounts / memberships) are separate round trips, on purpose. The I/O half of the second trip is pasted into each write entry, not shared, and those files are outside `bun run typecheck`. `update-organization` never reads `accounts` at all — a deactivated admin with a live membership would still rename unless a new check is added. Wrapping `callDatabaseFunction` looks like “one mandatory boundary” but the loop fixture never imports `edge.ts`; loop green would not hit that wrapper. The shared seam that **does** run at both tiers is a pure function in `_shared/` (as `ngoOnlyActionAllowed` already is).
**Evidence**: `create-organization/index.ts` 55–72 (`select=account_type` as `service_role`). `update-organization/index.ts` 60–81 (`org_memberships.role` only). Fixture `createOrganization` reads `state.accounts` and calls `ngoOnlyActionAllowed` (`_fixture.ts` 1057–1063) without any SQL. `edge.ts` lines 11–20. `custom_access_token` is commented out (`config.toml` 330–333).
**Impact**: A lifecycle column that is only consulted in definers makes AT-001.29 loop-green only if the fixture grows a second copy of the rule — the defect `_fixture.ts`’s header exists to forbid. A check only in each `index.ts` is forgotten the moment a fourth write is added, which is why D6.L2 asked for a registry. Extract one pure `writeAllowed(lifecycle)` (or equivalent) next to `ngoOnlyActionAllowed`, have every product write and the fixture call it, and have every definer re-read the column as the backstop. Do not put lifecycle on `Caller` and do not reuse `viewer_is_platform_admin()` on the write path.

### 7. [concern] New tables will fail the catalog unless they copy a ritual the static scan only half-covers
**Components**: `TENANT_CATALOG` (`_policy-scan.ts` 21–28); `WRITE_PRIVS` (line 188); `assertTenantCatalog` / `SERVICE_ROLE_SELECT` (`_integration.ts` 164–182); default ACL (`unit4-privileges-after-reset.txt` lines 29–31); overlay `revoke all` (`20260906120000_...sql` 46–60)
**Finding**: Unit 4 is already true on the six existing tables: after `revoke all`, `anon`/`authenticated`/`service_role` hold no TRUNCATE, TRIGGER, or REFERENCES (`unit4-privileges-after-reset.txt` lines 10–27). The remaining hazard is **new** relations. The default ACL still hands `Dxt` (DELETE, REFERENCES, TRIGGER, plus `m`) to `anon`, `authenticated`, and `service_role` on a new `public` table. The static scan requires `revoke all … from anon, authenticated` after `create table`, and refuses `service_role` write privileges in `WRITE_PRIVS` — but that set is `insert, update, delete, truncate, all` and **omits `references` and `trigger`**. CI runs the static scan only. The live walk pins all seven privileges and will catch the gap, but only at integration.
**Evidence**: `_policy-scan.ts` 188 and 471–478. Live `tenantTableFacts()` queries all seven privileges (`_live-tenant-reads.ts` 268–288). `TENANT_CATALOG` is a handwritten map; an undeclared `create table` is `undeclared-table` (lines 444–447). PostgreSQL grants EXECUTE on new functions to PUBLIC; every existing definer revokes then grants (`20260808120000_...sql` 355–376).
**Impact**: An audit table or escalation-contact table that skips `revoke all`, or a definer that skips `revoke execute from public`, fails CI. A leftover REFERENCES grant to `service_role` passes the loop scan and fails only on the live exact-set assertion. Unit 4 should be a record plus, if a loop-tier proof is wanted, `references` and `trigger` added to `WRITE_PRIVS`. Do not ship a no-op “revoke leftover privileges” migration on tables that already have none.

### 8. [concern] Contact-transfer audit and role-change audit are one NFR table, two writers, and one of the writers does not exist
**Components**: `20260811125000_...sql` line 31 (role-change audit deferred); product paths that always insert `admin`; operator `grantMembershipAsOperator` (the only `member` writer); AT-001.26 and AT-001.33
**Finding**: AT-001.26 and AT-001.33 both require an append-only record of contact transfer. Role change is listed only in AT-001.33. No product path updates `org_memberships.role`. The `member` enum value exists for AT-001.36’s operator Given. Append-only against the operator (postgres owner, BYPASSRLS, FORCE RLS banned by the scan) needs a BEFORE UPDATE OR DELETE trigger that raises — grants alone will not stop the owner.
**Evidence**: First product writers insert `role = 'admin'` only. `_contract.ts` 658–661: “NOTHING IN THE PRODUCT WRITES `'member'`”. Scan refuses `force row level security` (`_policy-scan.ts` 306–311). Coverage map: “Audit owned here (role changes, contact transfer) | 26, 33”.
**Impact**: Two audit tables for the same transfer event will double-state AT-001.26 and AT-001.33. A definer-only insert covers transfer and misses operator role writes. A trigger-only table covers operator role writes and still needs the transfer definer to insert the who/when/why row in the same transaction as the seat UPDATE. Build **one** append-only table; write transfer rows from the transfer definer; let a trigger refuse UPDATE/DELETE (and optionally record role UPDATEs). Do not treat operator `grantMembershipAsOperator` as a product role-change API.

### 9. [observation] Escalation contact, virtual keys, and concierge onboarding have no home in this subsystem
**Components**: `organizations` (`id, name, created_at`); `create-organization` body (`name` only); AT-001.28, AT-001.30, AT-001.31; REQ-002 / REQ-009 / REQ-030 (no code under `supabase/` for keys or concierge)
**Finding**: AT-001.28’s moment is concierge onboarding (REQ-002). The only org-creation write is `create-organization` / NGO `complete-signup`, neither of which takes a non-login contact. The signer columns on `acknowledgments` are a different person. AT-001.30/31 name virtual-key revocation and “documented recovery” that this tree does not implement. The last merge already used `capability-pending` for a missing surface (AT-001.10, AT-001.24).
**Evidence**: `OrganizationRow` is `{ id, name }` (`_contract.ts` 63–66). `create-organization/index.ts` 90–106. Brief fact 7–8. `_live.ts` 33–37.
**Impact**: Stuffing the escalation contact into `create-organization` as a required field breaks existing AT-001.06 bodies that send only `name`, and still is not concierge onboarding. Stuffing it onto the acknowledgment signer conflates three people. Building a key-revocation table here pretends REQ-009 exists. The honest shapes are: optional stand-in on org creation or a new table with a founder-chosen moment, and `capability-pending` on named capabilities for keys/recovery — the same as Discovery.

### 10. [observation] The loop fixture’s SQL mirrors will silently diverge from a SQL-only lifecycle or audit rule
**Components**: `_fixture.ts` `grantMembershipAsOperator` / `repointMembershipAsOperator` / `assignVolunteerAsOperator`; `_live.ts` the same methods as raw SQL; fixture header (“no second copy of the product rules”)
**Finding**: Product decisions are imported from `_shared/`. Database invariants (NGO-only membership, one seat, one developer) are hand-mirrored in the fixture and graded for real at integration. That split is honest for what it covers. A lifecycle or append-only rule that exists only in SQL will either (a) be reimplemented in the Maps, becoming a third statement of the rule, or (b) be invisible at loop, so CI (loop `--expect`) will not catch a forgotten edge call.
**Evidence**: `_fixture.ts` 1138–1145 and 1202–1208 (explicit “PREDICTION of the database”). Live operator paths have no TypeScript (`_live.ts` 487–494). Loop `--expect` is what CI runs (brief fact 12).
**Impact**: Put caller-facing product rules in `_shared/` so both adapters execute the same function. Use SQL triggers for facts that must hold on operator SQL (append-only audit, NGO-only seat). Do not use the fixture mirror as the lifecycle gate.

---

The current write path is a good fit for what it does: Auth answers who, a pure module answers whether, a definer writes, client roles cannot. That shape should be extended, not replaced. What would make the six units fail is treating Auth endpoints as edge routes, treating caller deactivation as a row trigger, enumerating writes as if volunteers and admins already had succeeding product operations, and minting replacement NGO accounts through `complete_signup` as if it did not also create an organisation.
