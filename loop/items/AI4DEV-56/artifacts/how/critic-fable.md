## Findings

Read against the code, not the explanation. Line numbers are as of the branch head. Every finding is weighted toward what would make the six units wrong, brittle or double-stated.

### 1. [structural] The "one mandatory lifecycle-gate boundary" has nothing to attach to at the edge, and the tree's real universal write boundary is the definer layer, which the explanation steers away from
**Components**: `supabase/functions/*/index.ts` (three write entries), `_shared/edge.ts` (`edgeHandler`, `callDatabaseFunction`), the three SECURITY DEFINER write functions, `tests/at/suites/req-001/_policy-scan.ts`.
**Finding**: There is no write-route abstraction. `edgeHandler` (edge.ts 101 to 114) is CORS plus a 502 wrapper and wraps reads and writes alike. Each write entry hand-rolls its own pipeline: `complete-signup` reads no account row at all; `create-organization` has its own `accountTypeOf` (55 to 72); `update-organization` has its own `roleIn` (60 to 81). A gate added "at the edge" is therefore a fourth inline step copied into each `index.ts`, in files the header of edge.ts (lines 11 to 22) says no type-checker covers, and the "conformance check" becomes a naming oracle over untyped text, the same class as `_source-scan.ts`. Meanwhile the tree already has a boundary that every running service must pass: `service_role` holds no INSERT, UPDATE or DELETE on any public table (`unit4-privileges-after-reset.txt` lines 10 to 27), so every product write and every raw service-role RPC reaches a row only through a definer, and every definer already receives `p_account_id` and already reads `public.accounts` (`create_organization` 283 to 285; `update_organization` 160 to 163). A lifecycle predicate called first in each write definer covers every path a running service can take. And `_policy-scan.ts` already parses `create function ... security definer` statements and inspects their text (lines 356 to 372, `searchPath` regex at 366), so "every write definer calls `public.assert_account_active(p_account_id)`" is a check the existing loop-tier CI scan can make with one more regex and one more selftest case. The explanation's section 2 says the gate "has to sit where a caller's account row can be read" and concludes the TypeScript layer is natural; the definer can read that row and already does.
**Evidence**: Only import of `callDatabaseFunction` is in the three write entries. No shared function resolves account type; two copies exist in two `index.ts` files. `_policy-scan.ts` 362 to 370 records definers and regex-tests their text. `complete_signup` cannot be gated on the caller's own row (the row does not exist yet, and a second completion is refused by the primary key, migration 20260811120000 lines 283 to 290), so any registry must carry an explicit exemption with a reason, not silence.
**Impact**: If unit 2 builds an edge-level registry, the conformance check is a grep over untyped files and misses raw RPC callers; if it builds a definer-level gate only, the loop tier grades a fixture mirror (finding 9). The shape that keeps both honest is one rule stated twice, as every other rule in this tree already is (`ngoOnlyActionAllowed` plus the `create_organization` raise; `orgAdminActionAllowed` plus the `update_organization` raise): a pure `lifecycleWriteAllowed` in `_shared` for the readable refusal and the loop tier, and a SQL helper in every write definer for enforcement, with the scan pinning the SQL side and a second scan (import of `callDatabaseFunction` implies a gate call) pinning the edge side. The registry constant that names the write inventory must be the same object the AT-001.29 body iterates, or the check and the test enumerate different lists (finding 2).

### 2. [structural] AT-001.29 and AT-001.30 require a write per global type, and the tree has no volunteer write at all
**Components**: the six edge functions, `AccountsSut` in `_contract.ts`, `_live.ts`, `_fixture.ts`, `verification.ts`.
**Finding**: AT-001.29 says "Covers all global types (NGO, volunteer, platform admin)" and requires "an active otherwise-authorized control account of the matching type that succeeds". The only writes a running service exposes are `complete-signup` (once per account), `create-organization` (NGO only by `ngoOnlyActionAllowed`, accounts.ts 336 to 345) and `update-organization` (org admin only). A volunteer is authorised for none of them after signup. The one volunteer-capable write in the tree is `sendDiscoveryMessage`, which exists only in `_fixture.ts` (line 1008) over `discoveryMessageAllowed`, which no deployed function imports (`verification.ts` header, lines 9 to 24), and which `_live.ts` line 823 throws `CapabilityPending` for. Project assignment is operator SQL, not a product write. The platform-admin arm has no write until unit 1 lands the transfer route, which the brief's order already handles. The volunteer arm has no write at either tier that a deployed function backs. AT-001.30's "platform writes are rejected immediately" for a deactivated volunteer has the same hole.
**Evidence**: grep of `supabase/functions/` for `callDatabaseFunction` yields three files; none is reachable by a completed volunteer as a permitted write. `_integration.ts` line 1757 already declares `at00110 = refusesWith('sut.accounts.sendDiscoveryMessage')` for the same reason.
**Impact**: A unit 2 body that drives NGO and admin writes and calls the volunteer arm covered is a green over a type it never exercised, which is the exact failure the expected-manifest machinery exists to refuse. The honest shapes available are: loop green over the stand-in (the gate on `sendDiscoveryMessage` in the fixture, graded through the shared pure decision), and integration either `capability-pending` on the named missing volunteer write, or a partial body that drives the two types it can and then throws, the AT-001.24 shape (`_integration.ts` 1669 to 1711). Whichever is chosen, the write inventory (finding 1) must be typed by account type so the body cannot silently skip a type.

### 3. [structural] The cascade chain makes "history preserved", "append-only" and "no unlink" fight each other at delete time, and the vendor's own admin delete is the path they collide on
**Components**: `public.accounts` (`references auth.users (id) on delete cascade`, migration 20260808120000 line 39), `acknowledgments.account_id` (line 74, cascade), `org_memberships.account_id` (line 59, cascade), any audit table unit 1 and 3 add, any trigger unit 5 adds on `auth.identities`.
**Finding**: Three units each need a "cannot be deleted" property on a row that today cascades from `auth.users`. AT-001.25 wants acknowledgments still attributed to the original human; AT-001.33 wants an audit row that "cannot be altered or deleted"; unit 5 wants an identity row that survives. The tree's precedent for "any path" enforcement is a BEFORE trigger that raises (`org_membership_grantee_must_be_ngo`, AT-001.37). Cascaded deletes fire row triggers on the referencing table, so a raise-on-delete trigger on an audit table, or on `auth.identities` for volunteers, turns `DELETE /auth/v1/admin/users/{id}` (the vendor's own admin API, the authority `provisionPlatformAdmin` already uses) into a raised exception inside GoTrue, the exact footgun the first migration refused for `auth.users` (lines 8 to 12). Without such triggers, "append-only" is only a privilege statement (no client role holds DELETE, which is already true after the overlay) plus "no definer deletes", and the operator and the vendor delete can still erase the audit. Neither choice is wrong; the choice is invisible in the explanation and each unit would make it alone.
**Evidence**: `20260808120000` lines 39, 59, 74; `20260811130000` line 61 (`on delete set null` on the project seat, the one place a deliberate delete policy was chosen). `_live.ts` 785 to 808 provisions through `/auth/v1/admin/users`, so the admin delete route is the same authority.
**Impact**: If unit 3's append-only trigger lands and unit 5's identity trigger lands, an operator or the founder can no longer delete a volunteer or any account with history through Auth, and the failure mode is a 500 from GoTrue, not a refusal. If neither lands, AT-001.33's "cannot be deleted" is provable only as "no client role and no definer can", which the test text should say. This needs one decision for the whole subtree before the arena, and the audit table's foreign keys need `on delete restrict` or no foreign key at all, because `on delete cascade` on an audit row is a delete path by construction.

### 4. [concern] An NGO account cannot exist without an organisation and an acknowledgment, so the transfer's "new account" is either a second-org holder or an account that never acknowledged
**Components**: `public.complete_signup` (migration 20260811120000, 176 to 179 and 293 to 300), `validateCompleteSignup` (accounts.ts 224 to 228), `org_memberships_one_seat_per_org_idx`.
**Finding**: The only product path that creates an `ngo` account also creates an organisation and seats the account as its admin, in one transaction, and requires the acknowledgment with signer identity. There is no "NGO account with no organisation". So the transferee in AT-001.25 is one of two things. Either a completed NGO account, which already owns a placeholder organisation and after the transfer holds admin seats in two organisations (allowed by the composite key, but the placeholder is an orphan nobody asked for). Or an auth user with no accounts row, in which case the transfer definer must insert the accounts row itself, skipping `complete_signup`'s acknowledgment and signer capture, so the new acting human has no acknowledgment on record, which contradicts "acknowledgments are per named human" in the REQ-001 slice and AT-001.19's "every acknowledgment moment".
**Evidence**: `complete_signup` raises on an NGO completion with no organisation name (line 176). `repointMembershipAsOperator` (`_live.ts` 552 to 577) is the proven repoint shape, and it assumes the target already completed signup (trigger branch at `20260811125000` lines 72 to 77 refuses otherwise).
**Impact**: The AT-001.25 body's Given and the transfer definer's precondition depend on this choice; the explanation's section 4 table does not mention it. The cheaper honest shape is "the transferee is a completed NGO account", with the placeholder organisation named as accepted residual, because the alternative rebuilds half of `complete_signup` inside the transfer.

### 5. [concern] Two deactivation authorities exist and neither implies the other; the token-claim route the explanation mentions is wrong for this criterion
**Components**: `auth.users.banned_until` via `PUT /auth/v1/admin/users/{id}`, a product lifecycle column on `public.accounts`, `resolveCaller`, the `[auth.hook.custom_access_token]` block (config.toml 331 to 333).
**Finding**: The ban probe measured that a ban does not end a live access token at `GET /user` (`auth-ban-probe.txt` line 6, HTTP 200 after ban) and does end refresh and password grants (lines 7 to 8). A product column gates writes at the definer and the edge and does nothing at Auth. If unit 2 uses both, "deactivated" has two sources of truth in two schemas owned by two roles, re-enable (AT-001.31) must flip both, and a product definer cannot write `auth.users` without the same cross-schema reach unit 5 needs. If unit 2 puts the state into the JWT through `custom_access_token`, AT-001.30's "immediately" fails by up to `jwt_expiry`, because the claim is minted at token issue. The criteria (AT-001.29 to .31) speak only of writes.
**Evidence**: `callerFromAuthAnswer` (caller.ts 111 to 119) reads status and `id`; nothing reads `banned_until`. Ban probe lines 5 to 10.
**Impact**: One authority, the product column read at write time, satisfies every clause the three ids state. A ban is an unrelated session control and should be out of scope by decision, not by omission, or unit 2 will half-build it and unit 1's re-enable will miss half.

### 6. [concern] The static scan does not require the service_role baseline revoke, so every new table this run adds passes CI and fails only at integration
**Components**: `_policy-scan.ts` (`no-baseline-revoke` 457 to 460, `baselineAnon`/`baselineAuthenticated` 428 to 429, `WRITE_PRIVS` 188), `_integration.ts` `assertTenantCatalog` 181 to 182, `pg_default_acl`.
**Finding**: A new public table gets `service_role=Dxtm` by default ACL (`unit4-privileges-after-reset.txt` line 31: TRUNCATE, REFERENCES, TRIGGER, MAINTAIN). The scan tracks only grant and revoke statements, so a migration that writes `revoke all ... from anon, authenticated` and forgets `service_role` shows no `service-role-write` problem (nothing was granted) and no `no-baseline-revoke` problem (only anon and authenticated are tracked). The live check then pins `serviceRole` to `[]` and fails. `WRITE_PRIVS` also omits `references` and `trigger`, and neither check sees MAINTAIN at all (`TABLE_PRIVILEGES` in `_live-tenant-reads.ts` 33 to 41 lists seven).
**Evidence**: The overlay migration itself needed a separate statement for `service_role` (`20260906120000` lines 50 to 52), which shows the author had to remember it.
**Impact**: Units 1 and 3 add at least an audit table and an escalation-contact column or table; unit 3 may add a rate-limit counter table. Each one is a CI-green, integration-red trap unless the scan's baseline requirement grows to `service_role` and `WRITE_PRIVS` gains `references` and `trigger`. That one-line scan change with a selftest case is also the only durable artifact unit 4 can leave, since the privileges themselves are already revoked on `main`.

### 7. [concern] Unit 5's refusal lives outside every guard the tree has, and the product's own copy of the link is never re-checked after signup
**Components**: `auth.identities`, `public.volunteer_profiles.github_handle`, `complete_signup` step (b) (migration 20260811120000, 216 to 227), `_policy-scan.ts`, `tenantTableFacts`, `live-stack.ts`.
**Finding**: The product binds the handle to a real `auth.identities` row once, at completion, then stores a copy in `volunteer_profiles`. After that nothing reads `auth.identities` for a volunteer. A BEFORE DELETE trigger on `auth.identities` is the only in-tree placement (the explanation's four options are right), and it is invisible to both catalog guards: the static scan matches `public.` identifiers only (lines 285, 337, 356) and the live walk reads `nspname = 'public'` (`_live-tenant-reads.ts` 291, 305). The trigger function itself, if placed in `public` as a definer, is seen by the scan and must carry `revoke execute from public`, but the trigger binding on an `auth` table is checked by nothing. The harness has no HTTP DELETE helper (`authPost` is POST only, `live-stack.ts` 82 to 99) and no reader of a live `/user` body's `identities[].identity_id`, which the vendor endpoint needs. And the vendor already refuses deleting a user's only identity, so the guard matters only for the AT-001.04 shape (email or Google plus linked GitHub), which is the shape no integration body can build through the product today (AT-001.04 is `capability-pending` at integration).
**Evidence**: `_live.ts` 285 to 304 writes the identity row as the operator, so the integration Given is operator-built; the act (an HTTP DELETE with the identity id) has no helper.
**Impact**: AT-001.41's integration body needs a new helper, an identity-id read, and a decision about the status it pins: a raise inside GoTrue's delete path is the 500 class the first migration named, so the oracle must be "the identity row survives", never a status code. The scan's public-only reach means unit 5's object has no CI-time guard; its only guard is the id itself, so the id must be green at integration or the ruling is enforced by nothing mechanical.

### 8. [concern] AT-001.34 names a control the product does not own, and the local stack does not exercise it
**Components**: GoTrue `/auth/v1/token?grant_type=password`, `[auth.rate_limit]`, the `password_verification_attempt` hook, `signInWithEmailPassword` in `_live.ts` 240 to 254.
**Finding**: Sign-in is Auth's endpoint; no product code sits on it. The measurement is that 45 wrong-password grants answered 400 with no 429 and no rate-limit headers (`unit6-signin-rate-limit.txt`), and the container carries no `GOTRUE_RATE_LIMIT_HEADER`. The hook probe proves the CLI pushes `password_verification_attempt` (`hook-push-probe.txt` lines 11 to 13), so a product-owned counter is buildable, but it fires only for a user row that exists, so it cannot throttle guesses against unknown addresses, and its function runs as `supabase_auth_admin` writing a counter table that must then satisfy the catalog (a named posture, the baseline revokes of finding 6). A product counter duplicates a control the hosted platform enforces and the criterion's words are "the configured rate limit", which points at the vendor's, not at a product table.
**Evidence**: Probe script `unit6-signin-rate-limit.ts` sends no `X-Forwarded-For`, so which of the three explanations holds is still open.
**Impact**: Unit 3 either builds a counter that proves a product control the criterion did not ask for, or declares AT-001.34 red with a named capability (the AT-001.24 and AT-001.10 precedent, `expected.ts` shape `capability-pending`) and unit 6 records why. The second is the honest one on today's measurement; the first is a design with its own catalog and privilege consequences and should not be chosen by default.

### 9. [observation] Every SQL-side rule grows a hand mirror in the fixture, and the loop tier then grades the mirror
**Components**: `_fixture.ts` `grantMembershipAsOperator` (1156 to 1200, "hand-written PREDICTION"), `repointMembershipAsOperator`, `assignVolunteerAsOperator`.
**Finding**: The tree's stated rule is that judgements live in `_shared` and the fixture holds storage only, but triggers and indexes cannot be imported, so the fixture predicts them by hand, and the integration tier is named as the grader of the prediction. Unit 2's gate (if SQL-side), unit 3's append-only trigger and unit 5's identity trigger each add a mirror. Where the integration body is partly `capability-pending` (finding 2 for the volunteer arm, finding 7 for the linked-GitHub shape), the mirror is graded by nothing. A gate-2 review, not a test, found the last mirror-order divergence (R2a, recorded in the fixture's own comment at 1152 to 1154).
**Evidence**: `_fixture.ts` 1137 to 1145.
**Impact**: This is the reason finding 1 recommends a pure TypeScript statement of the lifecycle rule beside the SQL one: the loop tier can then import shipped code for the decision and mirror only the storage. For the append-only and identity triggers no such split exists; their loop bodies are predictions and should say so in the same words the fixture already uses.

### 10. [observation] The audit table will have two writer classes with different actor semantics
**Components**: the transfer definer (unit 1), an AFTER INSERT OR UPDATE trigger on `org_memberships` (unit 3, "role changes"), `grantMembershipAsOperator` and `repointMembershipAsOperator`.
**Finding**: AT-001.26 needs who, when and why on a transfer; the definer has all three (`p_account_id`, `now()`, a reason parameter). AT-001.33 adds "role changes", and no product path changes a role: the only role writes are the two admin inserts and the transfer's repoint. The only role-change events reachable at integration are operator grants and repoints, which carry no actor and no reason. A trigger writer is the "any path" shape the tree uses, and it has no actor to record.
**Evidence**: `20260811125000` line 30 ("no product path that writes the member role"), line 31 (audit deferred here). `_contract.ts` 649 to 678 are the only role writers besides the definers.
**Impact**: The audit row's actor and reason columns must be nullable or carry an "operator" sentinel, and AT-001.33's body must accept that a trigger-written row has no who. Deciding this before the arena stops units 1 and 3 from designing two incompatible audit shapes for one table.

### 11. [observation] The write-route inventory today has three different enumerations and none is a file
**Components**: `supabase/functions/*/index.ts` importing `callDatabaseFunction` (three), `config.toml` `[functions.*]` (six, 490 to 506), definers granted EXECUTE to `service_role` (five, two of which are reads: `has_platform_acknowledgment`, `read_public_project`).
**Finding**: "An enumerated inventory of write endpoints" (AT-001.29) does not exist as an artifact. A definer-level scan needs a discriminator between write definers and read definers (`stable` appears on the reads, `20260808120000` line 96 and `20260906120000` line 127; the scan does not parse it today). An edge-level scan needs the `callDatabaseFunction` import as its mark, which the loop-only `sendDiscoveryMessage` stand-in does not carry.
**Impact**: Whichever layer finding 1 lands on, the inventory should be one exported constant consumed by the AT-001.29 body and by the scan, and the scan should derive candidates from the tree and fail on any candidate absent from the constant, so a future route cannot be added without either registering or breaking CI. That is the manifest's sentence made mechanical; a list maintained beside the check is the drift it names.
