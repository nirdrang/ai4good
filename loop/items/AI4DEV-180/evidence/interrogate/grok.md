## Findings

### 1. [critical] A finished file read rewrites a confirmed brief
**Location**: `design/astra/src/fixture-world.ts` `finishRead` (503–528), `scheduleRead` (548–582), `pauseRead` (472–501)
**Finding**: Confirmation stops a file-chat question. It does not stop the read from changing the brief. `finishRead` marks the file ready, writes `tookFromIt`, appends a suggestion, and increments `brief.revision`, then commits that snapshot with the existing confirmation still set.
**Evidence**: `pauseRead` (485–487) and the pause branch of `scheduleRead` (560–572) add the file to `heldQuestions` when `state.confirmation` is set, and they return before any brief write. `questionStillOpen` (539–546) is false when the script has no pause, and it becomes false once the chat contains `TEXT.fileResumeReply`. `scheduleRead` then arms `delay.to70` and `delay.ready` together. `finishRead` has no confirmation check. The test pace reaches ready 2200 ms after that arming; the demo pace reaches it at 2400 ms. A person can confirm inside that window: start `kitchen-rules.docx` (its script pause is null), or answer the rota pause and then confirm before the ready timer. `finish` (406–427) stores `confirmation.revision` from the revision it approved. `commit` copies that confirmation onto the new state. `ServerChange` carries the new brief, and both screens accept it through `newerBrief` because the revision is higher. The finished review then shows the new revision in its header and `TEXT.review.doneBody(confirmation.revision)` for the old one. The contract says confirmation records one revision, later AI changes stop, and a file fact enters the brief only after the person agrees (`design/discovery-ui-contract.md` lines 100–105 and 272). The screen half of the file-chat acceptance test locks the panel while the read is paused, so this timer is outside what it asserts.
**Suggestion**: Give `finishRead` the same hold as `pauseRead`. Release it only from the path that clears confirmation.

### 2. [critical] A send labeled free can settle as a paid hold
**Location**: `design/astra/src/fixture-transport.ts` `FixtureChatTransport.sendMessages` (126–147) and `FixtureFileChatTransport.sendMessages` (218–244); `design/astra/src/fixture-world.ts` `charge` (124–141)
**Finding**: The two transports decide that a reply is allowed, count a model call, wait, and only then charge. They never record the free or paid label the button showed. A main-chat send and a file-chat send can both pass the free check, and the later `charge` can take fuel.
**Evidence**: Each transport reads `usage.nextReply === "unavailable"` and returns before `reportModelCall`. A free balance passes. The main composer then sets its own chat status to submitted, and the file chat sets a different status, so the other Send stays enabled. `pause` waits 20 ms in the test pace and 650 ms in the demo pace. `charge` runs inside `applyTurn` (203) or `applyFileAnswer` after that wait. `replyKind` is free only while `dailyLeft > 0` and `betaLeft > 0`. The first commit decrements both. The second commit takes `holdMicros` from `availableMicros`, adds that amount to `settledMicros`, and emits a paid receipt with `usageMicros` equal to the hold. The button for the second send still said Send. On the mid-interview fixture one free reply can be left on purpose: send the last free main reply and a file answer so their pauses overlap. The contract says a concurrent change must refresh the shown mode, and a submission labeled free cannot silently become paid (`design/discovery-ui-contract.md` lines 124–125). The same early `reportModelCall` also counts a turn when the pause is aborted (144, 242) or when `applyTurn` later refuses a finished Discovery (199), so the probe and the ledger already diverge.
**Suggestion**: Carry the mode shown on the button into `applyTurn` and `applyFileAnswer`. If the mode changed, refuse before `charge` and before the model-call probe.

### 3. [warning] Changing an earlier answer reopens dependents only on Save change
**Location**: `design/astra/src/fixture-world.ts` `markDependents` (106–112), `applyTurn` (219–248), `acceptSuggestion` (371–394)
**Finding**: `priority` should reopen `measure`, `booking` should reopen `rules`, and `owner` should reopen `info` when the earlier answer changes and the later topic already has an answer. Only `saveBriefEdit` calls `markDependents`. A normal Send and Use the suggestion agree the parent and leave the dependent settled.
**Evidence**: `applyTurn` sets `needsReview: false` on the answered topic and commits. `acceptSuggestion` does the same at 384–392, and it also leaves `confirmation` in place. A not-sure topic stays in `currentQuestions` because `topicSettled` requires `agreed`. That question uses Send, which builds a normal charged answer. `nextOpenQuestions` waits on booking rules only while booking `state.kind === "open"`, so a not-sure booking still lets rules be asked. Reachable path from the first reply: answer booking with I'm not sure, agree rules on a later send, then send a certain booking answer from the question that is still on screen. Rules stay agreed. The same hole exists for priority then measure, and for Use the suggestion on an open parent whose dependent was already agreed. The contract's edited-answer state says to mark dependent answers for review and invalidate the old approval (`design/discovery-ui-contract.md` lines 105 and 169). The acceptance flow covers Save change, which is the one path that does this.
**Suggestion**: Run `markDependents` from `applyTurn` and `acceptSuggestion` whenever a topic answer changes, and clear confirmation there too.

### 4. [warning] The last uncertain answers are described as the end of the interview
**Location**: `design/astra/src/fixture-world.ts` `applyTurn` (259–271); `src/components/discovery/DiscoveryScreen.tsx` `readyToFinish` (113–114)
**Finding**: If every required topic is agreed or not sure, and at least one is not sure, the reply says "Nothing is left to ask. Select Finish Discovery." The not-sure questions stay in the chat, and the ready invitation does not replace the composer.
**Evidence**: `stillOpen` is true only for `state.kind === "open"` or `needsReview`. A not-sure topic makes it false. `allRequiredAgreed` requires every required topic to be agreed and free of review, so the ready sentence at 268 is skipped and 270–271 runs. `currentQuestions` keeps every topic that is not settled, so `questions.length` stays above zero and `readyToFinish` stays false. The person sees an end-of-interview sentence beside questions that still accept Send. The contract replaces the composer with the ready invitation when the required topics are agreed, and it keeps an uncertain fact visible as uncertain.

### 5. [warning] A file fact is stored before agreement, and the confirm question can become unreachable
**Location**: `design/astra/src/fixture-world.ts` `finishRead` (503–517) and `pendingReports` (584–595); `src/components/discovery/DiscoveryScreen.tsx` (113–114)
**Finding**: The read writes the fact into the file and into a suggestion on topic `info` before the person agrees. The only confirm question is prepended by `pendingReports`, and that function runs only from `applyTurn`. After the brief is ready, or after confirmation, no main-chat turn remains to carry it.
**Evidence**: `finishRead` sets `tookFromIt` and pushes `{ topicId: "info", fact }` unconditionally. The review file block and the Discovery document render that string as "The AI took from it". Nothing in the screen applies the suggestion to the topic. `pendingReports` returns the scripted "Is that right?" line only when a later `applyTurn` builds a reply. `applyTurn` returns at 199 while `confirmation` is set. `readyToFinish` removes the composer when no questions remain and every required topic is agreed, and it does not look at an in-progress read. A read that completes in either state updates the brief and never asks the person to confirm. The contract says the next main-chat reply reports the file and asks for agreement, and that the fact enters the brief only after that agreement (`design/discovery-ui-contract.md` line 272). The acceptance test sends "What did the file show?" during the interview, so the ready and confirmed timings stay untested. The suggestion row labeled "Suggestion · waiting for you" matches the current test; the missing confirm question and the "took from it" line do not.

### 6. [warning] The usage card, Buy fuel, and the shell ledger disagree with the Discovery world
**Location**: `design/astra/src/fixture-world.ts` `charge` (124–141); `src/components/discovery/model.ts` `usageView` (596–622); `src/components/discovery/UsageCard.tsx` (61–67); `design/astra/src/screens.tsx` `Dashboard` (27–35, 61–66) and `Funding` (539–543, 612–616)
**Finding**: The paid footer says the shown fuel excludes the hold and that the hold is not a charge. `charge` subtracts the whole hold from available fuel and adds it to settled usage, and it never writes `reservedMicros`. Buy fuel renders a button with no action. The shell dashboard and fuel page still read the old mock confirmation and the old mock balance.
**Evidence**: `usageView` builds the paid footer at 601 from `availableMicros`, which `charge` has already reduced by `holdMicros`. There is no pending-usage state. The contract keeps a reservation separate from a settled charge, shows "Usage pending" when actual usage is missing, and shows a receipt of usage plus fee (`design/discovery-ui-contract.md` lines 118, 131–134, 149, and 206). While `nextReply === "free"`, line 622 paints the fuel segment with the free-reply color, so an empty fuel balance follows the free counters. `UsageCard` shows Buy fuel when both free counters are zero and gives that button no `onClick`. The contract points that action at the existing project checkout with a $50 minimum (lines 127 and 205). `finish` records confirmation only inside the fixture world. `Dashboard` still chooses Continue from `state.confirmation`, so after a real confirm it still opens Discovery and says to continue shaping the first version. `Funding` adds the purchase to `state.usage.allocation` or `nextGate` from that same mock flag, while the Discovery card reads the fixture world's `DiscoveryUsage`. A purchase on the fuel page never appears on the Discovery card, and Return to your project still opens Discovery.
**Suggestion**: Settle a paid reply only when actual usage exists; until then move the hold into `reservedMicros` and show it as pending. Point Buy fuel at the fuel page. Drive the shell's confirm copy and navigation from the Discovery port.

### 7. [warning] The open-questions acknowledgment can stay ticked for a sentence the person did not tick
**Location**: `src/components/discovery/use-discovery.ts` `useDiscoveryReview` (698, 792–833); `design/astra/src/fixture-world.ts` `removeCauseLabel` (395–404) and `acceptSuggestion` (371–394)
**Finding**: The review tick stores the revision it approved, so a new revision clears it. The open-questions tick stores a bare boolean. Use the suggestion changes the open set and the sentence, and the box stays checked. Remove label has no in-flight guard and does not clear confirmation.
**Evidence**: `setReviewed` (743–745) stores `briefRef.current.revision`. `openGaps` is `useState(false)` and `setOpenGaps` writes that boolean through. `ConfirmCard` renders `TEXT.ack.gaps(open)` from the current open count. `accept` bumps the revision through `acceptSuggestion`, which lowers the open count. The review tick clears because the stored revision no longer matches. `openGaps` remains true, so the new "N questions remain open" sentence is already checked. Finish then sends `acks.openGaps` from that stale boolean (825). The acceptance test expects this tick to survive an edit of The need, and that edit does not change the open set; the failure is the tick surviving a changed open set. `busy` is also React state, checked before `await` in `saveEdit`, `accept`, and `finish`. `removeLabel` never reads it. The fixture methods resolve without an internal wait, so two clicks do not interleave today. The port is the phase-3 boundary. Once those methods wait on a network, Remove label can commit after Finish: `removeCauseLabel` checks the base revision, increments `brief.revision`, and leaves `confirmation.revision` on the approved revision. `ServerChange` (`port.ts` 16–22) also omits confirmation, so the mounted chat learns it only from `port.load` when `active` becomes true (`use-discovery.ts` 233–248). That load assigns `usage` and `files` with no newer-version check. The world refuses a later send before charging, but the transport has already counted the model call.
**Suggestion**: Store the open count or the gap sentence in the tick, and clear it when either changes. Guard every review mutation with the same ref the chat uses for Save change, and clear confirmation in `removeCauseLabel`.

### 8. [warning] The screen acceptance file is now a second application
**Location**: `tests/at/suites/req-004/j-need-brief.test.ts`
**Finding**: This file grew from a short stub list to about 1280 lines. The scenario scripts, viewport loops, and assertions for ten acceptance ids sit in one module, beside a page driver that is already 541 lines in `tests/at/suites/req-004/_screen.ts`.
**Evidence**: The quality bar treats crossing 1000 lines as a structural problem. The new length is mostly `expectFinishFlow`, `expectPausedFileChatLocks`, `expectChangeReopensDiscovery`, `expectDocument`, `expectEditClearsReview`, and the usage and file-chat scripts. Those scripts are the specification of the screen. A failure in one id forces a reader through the whole file, and the hole in `finishRead` survives because the assertions never leave the paused state. The source modules stayed under 1000 lines.
**Suggestion**: Keep one acceptance id, or one screen behavior, in each file, and leave the shared clicks in `_screen.ts`.
