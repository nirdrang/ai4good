THE RESULT: AT-016.09 fails on ATOMICITY at all 11 guarded rows — transition=true
notificationEvent=false delivery=false opsItem=false, the transition committed and nothing that
belongs to the event did. It does NOT fail on CapabilityPending, and that distinction is the whole
proof: a capability-pending red would show only that a seam still throws, whereas this one shows the
fault genuinely fired and the oracle discriminates between a rolled-back write and a half-committed
one.

NOTE ON THE EVENT ID, because this revert reaches it too. With the rollback gone the `try/catch` goes
with it, and the id allocation — which sits after that block — is never reached on a crashed fire.
So the ids stay contiguous even here, and this transcript is not evidence about them either way.
What IS evidence about them is the conformance case `consumes no event id when the crash rolls the
emit back`, which fails with `event-2` if the allocation is moved back above the fault point.

RED (this file) and GREEN (proof-green.txt) therefore differ ONLY by that rollback — same test, same
tier, same commands, one behavioural change between them. Whether the oracle itself is strong enough
to notice is a separate question, answered in proof-oracle.txt; whether AT-016.07's restart is
causal is answered in proof-restart.txt.

HOW THESE TRANSCRIPTS WERE CAPTURED. stdout and stderr are redirected to separate files, and the
redirection is done by `cmd` rather than by PowerShell. PowerShell 5.1 wraps a native command's
stderr in its own ErrorRecords even when redirecting to a file, so a capture taken that way carries
NativeCommandError text the command never emitted, and vitest's lines arrive hard-wrapped at the
console width. Routing through `cmd` writes the child's bytes untouched.
