WHY THIS FILE EXISTS. Gate 2 (terra, finding 1) found that `processRestart()` assigned an epoch
string that NO code on the delivery path read, so deleting `await h.faults.processRestart()` from
AT-016.07 left the test passing identically. A step whose removal changes no outcome did not
participate in the result, and the green was unearned. AT-016.09 had been held to a captured
falsification (`proof-oracle.txt`) and AT-016.07 had not; that asymmetry is the finding. This file
removes it — the same standard, applied to the other test.

WHY THERE ARE NOW TWO RUNS. Terra's confirmation closed the finding only PARTIALLY, and the residual
was real. Round 2 proved something true but conditional: WHEN the scenario restarts, a delivery path
that ignores the new identity fails. It never pinned the antecedent. The harness guard that judges a
no-op restart (`processEpochProblem` in harness/guards.ts) runs from INSIDE
`faults.processRestart()`, so deleting the call skipped the guard entirely — both epoch reads
returned `delivery-process-1`, `drainDeliveries` stamped exactly that, `[...new Set(stamps)]` still
equalled `[afterRestart]`, and the test passed. The step whose removal changes no outcome was back,
one level up: not the epoch this time, but the restart call itself.

So RUN 1 falsifies the COUPLING — does the delivery path read the identity? — and RUN 2 falsifies the
ANTECEDENT — did a restart happen here at all? Neither run alone closes the finding, which is why
round 2's single run left a residual for terra to find.

WHAT MAKES THE RESTART CAUSAL NOW. `Delivery` carries `deliveredByProcess`, created `null` and
stamped by `drainDeliveries` with the identity of the process that performed the send. AT-016.07
reads the epoch before and after the restart, REQUIRES THE TWO TO DIFFER, and requires every delivery
of the event to carry the POST-restart identity. So the delivery path has to read the process
identity, and the scenario has to actually restart, for the test to pass at all.

WHAT ROUND 2 CHANGED ABOUT THE STAMP, unchanged this round and restated because RUN 1 depends on it.
The FIRST send owns it: the drain writes the identity only into a row that is still `null`.
Re-stamping on every sweep recorded the identity of the last drain rather than of the process that
actually sent, which made `_contract.ts`'s claim about this field — a send after a restart carries a
different string than one before it — only nearly true. AT-016.07 cannot tell the two apart, because
it drains once and only after its restart; the conformance case `lets the process that first sent a
delivery keep it` is what tells them apart, and it fails if the guard is removed.

HOW THESE TRANSCRIPTS WERE CAPTURED. stdout and stderr are redirected to separate files, because
vitest prints the run header and the summary on stdout and the failure detail on stderr. The
redirection is done by `cmd`, not by PowerShell: PowerShell 5.1 wraps a native command's stderr in
its own ErrorRecords even when redirecting to a file, so a "verbatim" capture arrived carrying six
lines of NativeCommandError text and with vitest's own lines hard-wrapped at the console width.
Neither artifact is anything the test emitted. Routing the redirection through `cmd` writes the
child's bytes untouched. Every run below used

WHAT THIS PROVES, AND WHAT IT DOES NOT.

PROVES: the restart changes the delivery process's identity; the delivery path READS that identity;
and durable pending work was completed exactly once, by the identity that exists after the restart.
A `processEpoch` the delivery path ignores now fails AT-016.07 instead of passing it, which is the
mechanism terra named.

AND PROVES, NEW THIS ROUND: the scenario cannot silently drop its restart, because deleting the call
is itself a captured red (RUN 2). The harness guard cannot make that claim on the test's behalf — it
only ever runs when the call is there — so the obligation belongs in the scenario, where the
deletion is what trips it.

DOES NOT PROVE: that a restart loses and recovers in-flight work. At loop tier there is no volatile
in-flight state for a restart to lose — `drainDeliveries` is a synchronous sweep, not a process with
a lifecycle. Building a delivery worker with volatile state inside a stand-in fixture was FILED, not
built: inventing state whose only purpose is to be discarded would be staging the proof. Whoever
builds a real delivery process inherits that half.

AND ONE MORE THING IT DOES NOT PROVE, said in the test rather than only here. AT-016.07's
anti-duplication assertion — no recipient-channel pair receives more than one delivery — cannot fail
in this fixture at all: one delivery per pair is written by construction and the drain mutates those
rows in place, so nothing can make that list non-empty. The test states that beside the assertion
itself, with what it is waiting on, because a limitation recorded only in a rulings file is a
limitation nobody will meet again. The assertion is kept, unweakened, as the regression guard for
the tier where a real delivery process can send a pair twice.
