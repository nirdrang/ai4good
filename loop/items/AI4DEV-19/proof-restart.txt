RE-CAPTURED, and for a reason worth stating precisely because it is smaller than the ruling that
ordered it. `rulings-04.md` required this file re-taken on the grounds that round 2 "moves
`b-delivery-defaults.test.ts:58`", the line this transcript pins. It does not: round 2's comment
sits at line 66, below the assertion, so line 58 is exactly where it was and the pinned stack
reference below is unchanged. What DID change is the code the temporary edit is applied to — the
stamp is now taken once, on the first send — so the edit is spelled against the current line, and
the commit this file names is the current one. Both of those are reason enough on their own.

WHY THIS FILE EXISTS. Gate 2 (terra, finding 1) found that `processRestart()` assigned an epoch
string that NO code on the delivery path read, so deleting `await h.faults.processRestart()` from
AT-016.07 left the test passing identically. A step whose removal changes no outcome did not
participate in the result, and the green was unearned. AT-016.09 had been held to a captured
falsification (`proof-oracle.txt`) and AT-016.07 had not; that asymmetry is the finding. This file
removes it — the same standard, applied to the other test.

WHAT MAKES THE RESTART CAUSAL NOW. `Delivery` carries `deliveredByProcess`, created `null` and
stamped by `drainDeliveries` with the identity of the process that performed the send. AT-016.07
reads the epoch before and after the restart and requires every delivery of the event to carry the
POST-restart identity. The delivery path therefore has to read the process identity for the test to
pass at all.

WHAT ROUND 2 CHANGED ABOUT THE STAMP. The FIRST send now owns it: the drain writes the identity only
into a row that is still `null`. Re-stamping on every sweep recorded the identity of the last drain
rather than of the process that actually sent, which made `_contract.ts`'s claim about this field —
a send after a restart carries a different string than one before it — only nearly true. AT-016.07
cannot tell the two apart, because it drains once and only after its restart; the conformance case
`lets the process that first sent a delivery keep it` is what tells them apart, and it fails if the
guard is removed.

THE TEMPORARY EDIT, applied to tests/at/suites/req-016/_fixture.ts and then reverted — it breaks the
coupling and nothing else. In `drainDeliveries`:

    if (delivery.deliveredByProcess === null) delivery.deliveredByProcess = processEpoch;

becomes

    if (delivery.deliveredByProcess === null) delivery.deliveredByProcess = 'delivery-process-1';

which is exactly what a delivery path that ignores the process identity looks like: a constant that
happens to equal the identity the process had before the restart.

HOW THESE TRANSCRIPTS WERE CAPTURED, and this changed this round for a reason that is itself an
evidence problem. stdout and stderr are redirected to separate files, because vitest prints the run
header and the summary on stdout and the failure detail on stderr. The redirection is now done by
`cmd`, not by PowerShell: PowerShell 5.1 wraps a native command's stderr in its own ErrorRecords
even when redirecting to a file, so a "verbatim" capture arrived carrying six lines of

WHAT THIS PROVES, AND WHAT IT DOES NOT.

PROVES: the restart changes the delivery process's identity; the delivery path READS that identity;
and durable pending work was completed exactly once, by the identity that exists after the restart.
A `processEpoch` the delivery path ignores now fails AT-016.07 instead of passing it, which is the
mechanism terra named.

DOES NOT PROVE: that a restart loses and recovers in-flight work. At loop tier there is no volatile
in-flight state for a restart to lose — `drainDeliveries` is a synchronous sweep, not a process with
a lifecycle. Building a delivery worker with volatile state inside a stand-in fixture was FILED, not
built: inventing state whose only purpose is to be discarded would be staging the proof. Whoever
builds a real delivery process inherits that half.

AND ONE MORE THING IT DOES NOT PROVE, now said in the test rather than only here. AT-016.07's
anti-duplication assertion — no recipient-channel pair receives more than one delivery — cannot fail
in this fixture at all: one delivery per pair is written by construction and the drain mutates those
rows in place, so nothing can make that list non-empty. Round 2 states that beside the assertion
itself, with what it is waiting on, because a limitation recorded only in a rulings file is a
limitation nobody will meet again. The assertion is kept, unweakened, as the regression guard for
the tier where a real delivery process can send a pair twice.
