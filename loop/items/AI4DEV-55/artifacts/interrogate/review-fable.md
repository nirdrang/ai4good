# Adversarial review: tenant read path (AI4DEV-55 units 1 and 2)

Reviewer: Fable lane. Inputs: `diff-code.patch` in full, the design (`arena/design.md`), the rulings (`how/rulings.md`), and the surrounding code named in the prompt. I could not run the database or the suite (read-only lane, no stack), so every catalog claim below is a reading of the migration text, and I say so where it matters.

No finding questions the intent. The policy set, the caller-bound edge reads, the one refusal constant, and the two-tier harness are built as the design says. The findings are about places where the execution claims more than it proves, or where a guard has a hole its own header does not admit.

## Findings

### 1. [warning] The static guard cannot see a policy being removed, so the regression it exists to catch passes CI
**Location**: `tests/at/suites/req-001/_policy-scan.ts`, `scanTenantMigrations`, the statement loop (patch lines 2637-2737)
**Finding**: The module header says the scan "applies later statements over earlier ones". That is true only for `grant` and `revoke` on tables. `drop policy`, `alter policy`, `alter table ... disable row level security`, `alter table ... force row level security` and `drop table` match no branch and fall through. A later migration that contains `drop policy organizations_select_org_member on public.organizations;` or `alter table public.projects disable row level security;` leaves `rls` and `policies` exactly as the first migration set them, and the scan returns `[]`.
**Evidence**: Ruling 4 created this scan because "CI runs the loop tier only, so the live catalog check alone would never run after merge". The one class of change the CI guard therefore has to catch is a later migration that weakens the posture. The three weakening statements above are the natural way to weaken it, and none is modelled. The selftest `later statements overlay earlier ones` covers only the revoke-after-grant case, so the selftest agrees with the header and not with the code.
**Suggestion**: Model the four statement shapes on catalog tables: `drop policy` removes the entry from `policies`; `alter table ... disable row level security` removes from `rls`; `force row level security` and `drop table` on a catalog table are problems outright (the header says no table carries FORCE). Add one selftest per shape. The parser already splits statements and folds whitespace, so each is one regex and one Map operation.

### 2. [warning] The static guard treats "no grant statement" as "no privilege", which is the mistake this tree recorded twice
**Location**: `_policy-scan.ts`, the `unreachable-by-client-roles` branch (patch lines 2781-2791)
**Finding**: For an unreachable table the scan reports a problem only when a grant it has seen survives. A table created later, declared `unreachable-by-client-roles`, with no grant and no revoke, passes. On this stack it is not unreachable: Supabase ships `ALTER DEFAULT PRIVILEGES` for `public`, so the table arrives already granted to `anon`, `authenticated` and `service_role`.
**Evidence**: `supabase/migrations/20260809090000_...sql` lines 424-443 and `20260811130000_...sql` lines 112-123 both say, in capitals, "NO GRANT STATEMENT IS NOT THE SAME THING AS NO PRIVILEGE", record the measured catalog rows (REFERENCES, TRIGGER, TRUNCATE for all three roles on a fresh table), and conclude "THE REVOKE IS WHAT MAKES THE POSTURE TRUE". The scan encodes the opposite belief. The live half (`tenantTableFacts`) would catch it, but only at integration, which CI does not run, which is the gap ruling 4 set out to close.
**Suggestion**: For every catalog table require an explicit `revoke all on table public.<t> from anon, authenticated` to appear after its `create table` (the shape the new migration already uses for all six tables). Report `no-baseline-revoke` when it is missing. That turns the guard's expectation into "the revoke is present", which is the rule the tree learned.

### 3. [warning] The header says both checks test its posture paragraph; two of the four bullets are tested by neither
**Location**: `supabase/migrations/20260906120000_...sql` header lines 464-472; `_policy-scan.ts` isolated branch; `_live.ts` `tenantTableFacts`; `_integration.ts` `assertTenantCatalog`
**Finding**: The header states four bullets and says "The static catalog scan and the live catalog read both test this paragraph rather than a second copy of it". What is tested: `anon` holds nothing (both halves), `authenticated` has SELECT on isolated tables (both halves, presence only), RLS is on and a policy exists (both). What is not tested by either half: `authenticated` holds "SELECT and nothing else" (a later `grant insert on public.projects to authenticated` passes: the scan checks `has('select')`, the live query asks `has_table_privilege(..., 'select')` only); `service_role` "holds no INSERT, UPDATE or DELETE anywhere" (the role appears in neither half); "No table carries FORCE ROW LEVEL SECURITY" (unchecked). With `authenticated` holding INSERT and no insert policy, RLS still denies, so today this is a posture drift, not a data leak; but the header is the contract the guard claims to enforce and the contract is overstated.
**Evidence**: `_policy-scan.ts` lines 2761-2767 and `_live.ts` lines 2354-2363 name only `select`. No occurrence of `service_role` or `relforcerowsecurity` in either checker.
**Suggestion**: Either check the two missing bullets (the live query can select `relforcerowsecurity` and `has_table_privilege('service_role', ..., 'insert'|'update'|'delete')`; the static scan can refuse any table grant to `authenticated` other than `select`), or rewrite the header sentence to name which bullets the checks test. Do not leave a paragraph that says "tested" over bullets that are not.

### 4. [warning] The service role's default privileges on the four first-migration tables are never revoked
**Location**: `20260906120000_...sql` step 1 (patch lines 485-487); `20260808120000_...sql` lines 311-353
**Finding**: The new migration revokes from `anon, authenticated` only. The first migration created `accounts`, `organizations`, `org_memberships` and `acknowledgments` with no revoke of any kind for any role. The two later migrations that learned about default privileges revoked `service_role` on their own tables (`volunteer_profiles`, `projects`) and recorded that a fresh table arrives with REFERENCES, TRIGGER and TRUNCATE for `service_role`. By that same measurement, `service_role` today holds TRUNCATE on the four first-migration tables. TRUNCATE is a destructive write that row-level security does not cover; `20260811130000` line 115 says exactly this. The header's bullet "service_role ... holds no INSERT, UPDATE or DELETE anywhere" is literally true and misses the privilege that matters.
**Evidence**: I could not run the catalog. The inference is: same stack, same `ALTER DEFAULT PRIVILEGES`, same `create table` in `public`, no revoke in the first migration (read lines 311-353 in full: two grants, zero revokes). If the catalog shows otherwise, the finding falls; the migration header should then say what was measured.
**Suggestion**: Add `revoke all on table <the six tables> from service_role;` to step 1, then re-grant the two SELECTs the write functions need (`accounts`, `org_memberships`). Have `tenantTableFacts` return the service role's privilege set and `assertTenantCatalog` pin it to exactly those two SELECTs. That is the statement the header wants to make.

### 5. [warning] Integration bodies reach around the SUT to the raw stack
**Location**: `_integration.ts` `at00121` (patch lines 1739-1754), `at00122` (1817-1834), `at00124` (2054-2065); the new import at line 1612
**Finding**: Before this change `_integration.ts` imported nothing from `harness/live-stack.ts` (checked against `origin/main`). Now three bodies call `stackFromEnv()`, run a password grant with `authPost` to get a second token for an actor the SUT already holds, and call `restGet`/`functionPostRaw` directly. These calls skip `freshAccessToken`, skip `viewerRead`'s classification (a stale token would fail as a bare status instead of `session-refused`), and mint extra GoTrue sessions for actors the body has already signed in through `registerConfirmAndSignIn`.
**Evidence**: Ruling 2 put the viewer-shaped reads on the contract so "the integration adapter reaches the token through the same private map every other session-taking member uses". The listing probe, the volunteer-with-token public-page probe, and the anon probes are viewer reads by that definition, and they live outside the contract. `AccountsSut` is the one seam the fixture and live adapters both implement; logic beside it is logic one tier cannot see.
**Suggestion**: Add the three missing shapes to the contract: `organizationsAsViewer(session)` (an unfiltered listing), an optional `session` on `publicProjectPage`, and let the four `...AsViewer` members accept `session: Session | null` for the anon arm (the fixture throws `CapabilityPending` for them anyway). Then delete the live-stack import from `_integration.ts`.

### 6. [warning] The committed grok wrapper widens permissions beyond its stated purpose, silently
**Location**: `loop/work/grok-shim/grok` lines 34-46, 52-53
**Finding**: The intent says the wrapper "lets the Grok CLI start on a kernel without Landlock". Mapping `--sandbox workspace|read-only` to `devbox` does that. Two more rewrites do something else: `--permission-mode acceptEdits` becomes `bypassPermissions`, and `GROK_SANDBOX_AUTO_ALLOW_BASH=1` is exported unconditionally. Neither is about Landlock. A dispatcher that asked for a read-only, accept-edits lane gets a writable sandbox with no permission prompts and no bash confirmation, and nothing is printed to say so. The rulings file records that the grok critic lane, a read-only role, ran "through the sandbox wrapper".
**Evidence**: Lines 41-45 rewrite the permission mode; line 53 sets the auto-allow variable; no `echo ... >&2` anywhere. The probe result is cached under `~/.cache/grok-shim` forever, so a kernel that later gains Landlock keeps the widened mapping.
**Suggestion**: Remove the permission-mode rewrite and the auto-allow export, or gate them behind an explicit environment variable and print one line to stderr when they fire. Re-probe `/sys/kernel/security/lsm` on each run; it is one `grep -qs`.

### 7. [warning] The viewer parsers drop a malformed row in silence, so a denial assertion can pass on a row that leaked
**Location**: `_live.ts` `asStringRows` (patch lines 2146-2155) and the four `...AsViewer` mappers
**Finding**: A row that fails the shape check (`name` not a string, `role` not `admin|member`, `id` not a string) is skipped, and the read still answers `ok: true` with the survivors. Every denial in the tenant bodies is `expect(emptyViewerRows(...)).toEqual([])`. A leaked row of an unexpected shape therefore produces a green denial.
**Evidence**: Today the schema makes this unreachable (`name text not null`, `role` is an enum), and the positive controls (ruling 2) would catch a parser that drops everything. But a parser that drops some rows is exactly the case positive controls do not cover, and the cost of the false green is a passed isolation test. In a security assertion, "I could not parse this row" must fail the assertion, not shrink the list.
**Suggestion**: Have the mapper return a marker for a bad row and let `viewerRead` answer `{ ok: false, kind: 'refused', reason: 'row of unexpected shape: ...' }` when any row is bad. `emptyViewerRows` then fails loudly on it.

### 8. [warning] A privilege or token refusal at PostgREST becomes the outage constant, and the cause is thrown away
**Location**: `edge.ts` `restJson` (patch lines 108-119); `tenant-reads.ts` `organizationDashboard` / `projectWorkspace`; `TenantReads.ReadResult.detail`
**Finding**: Every non-2xx from PostgREST becomes `{ ok: false, detail }`, and both cores turn that into `TENANT_READ_FAILED` (502). `detail` has no reader anywhere in `supabase/functions/` (grep). So a token that expires between `resolveCaller` and the read, or a future grant regression that makes `authenticated` lose SELECT, answers "the read could not complete, so no decision was made" with nothing logged. Ruling 11 says a stale token "must stay distinct from an empty list"; at the function surface it is distinct (502, not 200), but it is also indistinct from a real outage, and nobody can tell which happened afterwards.
**Evidence**: `ReadResult` is `{ ok: false; detail: string }`; the only writers are `restJson` and `publicProjectReads.source`; no `console`, no header, no field carries `detail` out. The selftests construct `detail: 'outage'` and never assert on it.
**Suggestion**: Keep the body constant (ruling 6 is right that a fourth member is the wrong fix). Log `detail` and the status in `restJson` with `console.error`, once, before returning. If the field is not going to be read, delete it: a write-only field is a promise the code does not keep.

### 9. [warning] Duplicated helpers where one exists
**Location**: `edge.ts` `publicProjectReads.source` (patch lines 150-169); `_live.ts` `organizationDashboard`, `projectWorkspace`, `publicProjectPage` (2290-2346); `_live.ts` `expOf` (2117-2120)
**Finding**: `publicProjectReads.source` is `restJson` copied line for line with a POST. The three live function members share a 12-line parse-200-body block three times. `expOf` is the fourth copy of the JWT claims decode in the same file (`sessionIdOf`, `accountIdOf`, `lifetimeProblem` already carry it).
**Evidence**: The code-quality lens names "duplicates an existing helper" a presumptive blocker. `restJson` already accepts `RequestInit`, so the first case is one call: `restJson<PublicProjectSource>(url, { method: 'POST', headers, body })`.
**Suggestion**: Use `restJson` in `publicProjectReads`. In `_live.ts`, one `okBody<T>(answer): TenantReadOutcome<T>` for the three members, and one `claimsOf(accessToken)` the four decoders share. About forty lines go away and the token decode has one home.

### 10. [nit] Two independent reads run in sequence
**Location**: `tenant-reads.ts` `organizationDashboard` (patch lines 310-313)
**Finding**: `seatsOf` and `projectsOf` do not depend on each other. `Promise.all` halves the dashboard's tail latency for no extra code.

### 11. [nit] `emptyViewerRows` is also the positive-control reader
**Location**: `_integration.ts` line 1648 and every `emptyViewerRows(ownOrg).map(...)` call
**Finding**: The helper asserts the read was not refused and returns the rows. Half its call sites expect rows. The name says the opposite of what those sites do. `viewerRows` or `rowsOf` says what it is.
