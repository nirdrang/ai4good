## Findings

### 1. [critical] The contact transfer works exactly once per account, then deadlocks
**Location**: `supabase/functions/_shared/admin-operations.ts` (`decideContactTransfer`, the `holds-other-seats` refusal) and `supabase/migrations/20260908120000_account_lifecycle_audit_and_contact_transfer.sql` (`transfer_organization_contact`, the R6 check plus the unconditional `change_account_lifecycle(..., 'deactivated', ...)` call)
**Finding**: An account that holds seats in two organisations can never transfer either of them, and every successful transfer manufactures exactly such an account. The flagship admin operation is single-use.
**Evidence**: Three facts combine. First, one account holding several seats is reachable through the product and explicitly blessed: `create_organization` contains no per-account seat check, and the single-seat migration's own comment says a second organisation via `create_organization` is expected. Second, every completed NGO account holds at least one seat, because NGO `complete_signup` always creates an organisation plus membership; ruling R5 then requires the transferee to be such an account and lets it keep its own organisation. So after any transfer, the new contact holds at least two seats. Third, the transfer refuses whenever the outgoing account holds any other seat, and otherwise always deactivates the outgoing account. Trace the next handover: the holder now has seats in its own org and the transferred org, and a transfer of either one sees the other and refuses with `holds-other-seats`. Transferring "those seats first", as the refusal message instructs, is refused for the same reason in the other direction. There is no sequence of product calls that unsticks it; only direct operator SQL can. The test Given always uses single-seat accounts, so no body exercises this. The refusal message therefore promises a remediation path that does not exist.
**Suggestion**: Deactivate the outgoing account only when the moved seat was its last one, so a multi-seat transfer moves one seat and keeps the account active; keep the unconditional deactivation for the single-seat case the tests pin. Alternatively enforce one organisation per account at creation time, but that contradicts the blessed second-organisation path and R5, so the conditional deactivation is the smaller fix. Cover a two-seat holder and a second consecutive transfer of the same organisation in the transfer bodies.

### 2. [warning] The conformance scan proves less than the structural claim states
**Location**: `tests/at/suites/req-001/_write-route-scan.ts` (`REACHES_DATABASE`, `CONSTRUCTOR`, `loadWriteRouteTree`) and `tests/at/suites/req-001/_policy-scan.ts` (`scanWriteGateSql`, the `gated` and `stable` fields)
**Finding**: Three gaps separate "a write route is a value handed to `writeRoute()` and there is no other way to reach the database" from what CI actually checks.
**Evidence**: First, the scan reads only `supabase/functions/*/index.ts`, `config.toml`, `_shared/edge.ts`, the migrations, and the fixture. A new helper in `supabase/functions/_shared/` that wraps `fetch` to `/rest/v1/rpc/` and is imported by a route file never appears in any scanned input, and the route file itself contains none of the three trigger strings, so no code fires. Purity of `decide` functions is conventional: nothing forbids a `decide` module from importing fetch, and both runtimes that execute it (Deno at the edge, Node in the fixture) provide one. Second, the SQL half tests substring presence of `public.assert_account_active(`, so a call in dead code such as `if false then perform public.assert_account_active(p_account_id); end if;` satisfies the scan while gating nothing at runtime, and nothing checks the call is the first statement although every migration comment claims it is. Third, any function marked `stable` or `immutable` is exempt, but volatility markings do not stop a function from writing; the exemption is one keyword away from an ungated writer that stays green. No live hole exists today: all current routes go through `writeRoute`, table-level revokes block direct REST writes, and every non-exempt definer backstops. The gap is that the advertised CI guarantee is weaker than its statement.
**Suggestion**: Extend the scan to `_shared/*.ts` and refuse `fetch` outside `edge.ts`; make the gate check positional (first executable statement of each non-stable definer) or document why presence suffices; remove the volatility exemption or additionally require that exempt functions contain no `insert`, `update`, or `delete` on product tables.

### 3. [warning] The escalation-contact backstop does not re-check the email rule
**Location**: `supabase/migrations/20260908120000_account_lifecycle_audit_and_contact_transfer.sql` (`set_escalation_contact` validation block) versus `supabase/functions/_shared/admin-operations.ts` (`validateEscalationContact`)
**Finding**: The TypeScript decision refuses an email without `@`; the database function that is supposed to re-check every answer accepts any non-blank string. A service-role caller bypassing the edge stores a contact the product surface refuses.
**Evidence**: The definer trims the three fields and raises `invalid-contact` only when name or email is blank. There is no `@` test anywhere in the function. The shipped decision raises `invalid-contact` for `maya.example.org`. The design's backstop posture is that each definer re-checks the decision; here one conjunct was left out. Same class of drift, lower stakes: the transfer and lifecycle definers store the reason verbatim while the decisions hand over a trimmed reason, so a direct RPC call persists leading and trailing whitespace the edge path never stores.
**Suggestion**: Add a `position('@' in v_email) = 0` raise carrying `detail = 'invalid-contact'`, and either trim the reason before the checks in SQL or store the trimmed value, so both paths persist the same bytes.

### 4. [warning] The route scan is brittle as a text oracle in three small ways
**Location**: `tests/at/suites/req-001/_write-route-scan.ts` (`serveCount`, `NAME_LITERAL`, `REACHES_DATABASE`)
**Finding**: The scan counts `Deno.serve(` occurrences including comments, takes the first `name: '...'` match including comments, and recognises database reachability only through three literal strings.
**Evidence**: A comment containing `Deno.serve(` in a registered route pushes `serveCount` to 2 and fails a compliant file with `write-route-not-constructed`. A comment containing `name: 'example'` above the real spec makes the file register under the wrong name. A route that posts to `/rest/v1/<table>` directly, or builds the rpc path by concatenation, matches none of `writeRoute`, `callDatabaseFunction`, `/rest/v1/rpc/` and escapes `write-route-unregistered` and `write-route-bypasses-boundary` entirely. The table-write variant is mitigated today by the revokes the catalog scan enforces, which is why this is a warning and not a critical, but the scan is the component the design credits with failing an unregistered route in CI.
**Suggestion**: Strip comments before the structural checks; anchor the name literal to the `writeRoute({` argument object; either broaden the reachability pattern to `/rest/v1/` or state next to the pattern why rpc-only matching suffices given the revokes.

### 5. [warning] Success responses can carry null payloads after the render fallbacks were dropped
**Location**: `supabase/functions/complete-signup/index.ts` (`render`) and `supabase/functions/update-organization/index.ts` (`render`)
**Finding**: On any definer answer with an unexpected shape, both routes now return `ok: true` with null fields. The previous code fell back to values it already held.
**Evidence**: The old signup render answered `accountId: result?.account_id ?? caller.id` and `accountType: result?.account_type ?? accountType`; the old rename render echoed the requested organisation id and the judged name. The new renders answer `?? null` with no fallback. The live adapter coerces those nulls onward (`String(json.accountId ?? '')`), so a caller receives a success it cannot use and fails several calls later instead of at the route. The fixture always renders complete shapes, so the loop tier cannot exhibit the divergence. Reachable only on a definer anomaly today, but a success contract that can be null on its identifying fields is the wrong default.
**Suggestion**: Restore the fallbacks, or answer 502 when the definer value does not contain the fields the contract promises.

### 6. [warning] Seat deletion is unaudited and product grants are mislabelled as operator acts
**Location**: `supabase/migrations/20260910120000_org_membership_role_change_audit.sql` (trigger timing) and the lane record's own open doubt about product inserts recording `operator`
**Finding**: The audit trigger fires on insert and update only. Deleting a membership row ends contact standing with no audit row, although that is at least as significant as the role edits that are recorded. Separately, every product membership insert from `complete_signup` and `create_organization` records `actor_account_id null` and label `operator`, because neither definer sets `app.actor_account_id`; those rows are indistinguishable from genuine operator interventions in later forensics.
**Evidence**: The trigger header is `after insert or update`; there is no delete arm. The two product definers contain no `set_config('app.actor_account_id', ...)` call, while the transfer definer does, so the only membership rows attributable to a real administrator are transfer seat moves. Any future member-removal leaf inherits silence by default.
**Suggestion**: Add a delete arm that writes `org_role_changed` with reason `membership revoked` (or record the decision not to), and set the actor setting in the two product definers so their grant rows carry the acting account instead of `operator`.

### 7. [nit] Dead null-stats branch in the signup decision
**Location**: `supabase/functions/_shared/accounts.ts` (`decideSignupCompletion`, the `stats === null` disjunct)
**Finding**: `stubGithubStatsFor` returns a populated `GithubStats` unconditionally, so the `stats === null` half of the omission condition is unreachable and suggests a failure mode the stub does not have.
**Evidence**: The stub body has no null return on any path; it always yields at least one language, a positive count, and a summary. The condition therefore reduces to `githubHandle === null`.
**Suggestion**: Drop the `stats === null` disjunct and the `?? null` style that implies it, or type the stub as infallible where the decision reads it.

### 8. [nit] Unbounded input reflected in an error reason, and an unguarded cast in the audit trigger
**Location**: `supabase/functions/_shared/edge.ts` (`writeRoute`, the UUID-shape refusal embedding `JSON.stringify(value)`) and `supabase/migrations/20260910120000_org_membership_role_change_audit.sql` (`v_actor := v_actor_text::uuid`)
**Finding**: A arbitrarily long `organizationId` or `accountId` string is echoed verbatim into a 400 response body, and a malformed `app.actor_account_id` setting aborts membership writes with a cast error rather than a fail-closed audit decision.
**Evidence**: The refusal interpolates the full trimmed input with no length cap; `readJsonBody` imposes no body limit above it. In the trigger, any non-uuid setting value raises `invalid_text_representation` out of the trigger instead of degrading to the documented null-actor `operator` row.
**Suggestion**: Truncate the reflected id to a fixed prefix in the reason, and wrap the cast in a guarded block that leaves the actor null when the setting does not parse.

### 9. [nit] `fromAccountId` skips the UUID pre-check its two sibling ids get
**Location**: `supabase/functions/transfer-organization-contact/index.ts` (spec declares `target` and `subject` only) and `supabase/functions/_shared/admin-operations.ts` (`decideContactTransfer` reads `fromAccountId` inside the decision)
**Finding**: A malformed outgoing-account id is refused as 409 `not-the-current-contact`, while an equally malformed organisation or transferee id is refused as 400 `invalid-request`. One class of malformed input carries two kinds depending on which field it lands in.
**Evidence**: The edge pre-check iterates only `target` and `subject`; `fromAccountId` is parsed later by `stringField` inside the decision and can never equal the uuid-shaped seat holder, so it always exits through the seat comparison. No database mistreatment follows, which is why this is a nit, but a client distinguishing 400 from 409 reads field-shape errors inconsistently.
**Suggestion**: Either validate `fromAccountId` shape in the decision with `invalid-request` before the seat comparison, or note the asymmetry where the decision order is documented.
