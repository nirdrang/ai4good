## Flow

**AT-016.09 — atomicity (single body, runs at both tiers):**
1. Parameterized over all 11 guarded rows (`GUARDED_ROWS`); first asserts none dropped out (`c-reliability-guard.test.ts:37-40`).
2. **Control run**, its own world: `open()` → per-open harness → `w.fire(row.event)` → core.emit → `prepareWriteSet` (resolves role holders via the directory, renders copy, refuses an unresolved role or an email channel with no address, `notifications.ts:174-206`) → `outbox.append` (transition commit → fault point → event + deliveries + ops item) → `drainDeliveries()` → asserts the transition committed AND an event was written (lines 47–63). This kills the "silent no-op fixture" false pass.
3. **Fault run**, fresh world: `h.faults.at('notifications.between_transition_and_event_write','crash')` — `createFaults.at` → `faultPointProblem` against `seam.points()` → `faultAlreadyArmedProblem` → adapter `arm` → `createCrashSwitch.arm`: kind check, empty ledger `{reaches: 0}` (loop) / `{sequenceAdvances: 0, refusals: 0}` (live), set live.
4. `w.fire` under the fault: loop — `append` sets the transition, sees `armed`, RESTORES the transition's previous value, increments `reaches`, throws (`_fixture.ts:232-240`); the body catches. Integration — `append` reads `armed`, snapshots the sequence, calls `fixture_commit_transition_and_emit(..., true)`: the definer upserts `committed=true`, takes `nextval` (survives the rollback), raises P0001 with the distinctive `detail`; the whole transaction rolls back (transition, event, deliveries, ops item); the adapter counts the refusal (detail match) and the sequence delta.
5. `fault.clear()` in `finally`: disarms, releases the point, then judges — `faultFiredProblem` throws "never fired" unless `triggerCount() >= 1`. At integration `triggerCount()` = `sequenceAdvances` and the ledger itself throws first if `sequenceAdvances !== refusals` (`_live.ts:270-279`).
6. `drainDeliveries()` then the oracle reads FOUR things, all required absent: `w.transitionCommitted` (the ledger row), `sut.events({type})`, `sut.deliveries({type})`, and `sut.opsItems()` matched by `kind` (no event id exists to filter on). Asserting ALL false rejects a strict superset of the old two-read "unequal" form; the widening and the tightening each have falsification on file at `loop/items/AI4DEV-19/proof-oracle.txt` (comments at lines 80–107). At loop the reads are the memory store; at integration they are operator SQL over committed rows, scoped to the fresh world's actor ids so the control run's rows cannot satisfy them.
7. Problems accumulate across all 11 rows; `expect(problems).toEqual([])` (124–127).

**AT-016.11 — sent-only-on-acceptance (per-tier bodies):**

Loop body (default):
- (a) `h.vendors.email.rejectNext(1)` (count routes through `providerForceCountProblem`) → fire `access.key_issued` → `drainDeliveries({passes: 1})` — ONE pass so the unconfirmed state is observable; run-to-quiescence could reject-retry-succeed inside one call (`c-reliability-guard.test.ts:167-171`). The simulator consumes the forced outcome, records the attempt, returns `rejected`; `applyPassResults` sets the delivery `retrying`, the event `attempts=1`, state `retrying`. Assertions: the provider's own trace shows `['rejected']` (the fault was genuinely served, not just armed); no misdirected attempt (trace read on recipient+channel, lines 179–196); event exists in `pending|retrying`; the email delivery exists and is not `sent` (198–206).
- (b) Full drain: the retry physically reaches the provider (outcome sequence ≥ 2 attempts, last = `accepted`), and only then is the event `sent` with `attempts >= 2` (210–224). A rejected identity is not closed, so the retry is a first acceptance.
- (c) `acceptButLoseAck(1)` → fire `access.key_revoked` → one pass: the simulator records `['ack_lost']`, physically adds the identity to `accepted()`, returns `no_ack` (the port cannot lie in the sender's favor); the delivery stays not-sent, event `pending|retrying` (226–253). Integration body (`at01611`):
- (a) `h.faults.at('notifications.provider_send','reject')` → same fire/drain → the decorator refuses without calling the inner provider, records the attempt, answers `{rejected, null}`; delivery `retrying`. - (b) `h.faults.at(..., 'lose_ack')` → fire `access.key_revoked` → one pass: the decorator calls the inner provider (Mailpit stores ONE physical message), then answers `no_ack` and stores no receipt; delivery not-sent, event `pending|retrying`; catcher says exactly `[1]` physical message for the key (313–343). Retry: decorator disarmed → `withIdempotentReplay` asks the catcher, finds the message with this key, answers `accepted` without sending → outcomes `['ack_lost','accepted']`, delivery sent, exactly one logical event, pair oracles equal on deliveries and on `recordedProviderAccepted()`, and BOTH events end with exactly `[1]` physical message per key (345–381).

## Boundaries

- **Core ↔ storage**: the six-port seam (`OutboxPort` et al.); the loop binding is three arrays, the live binding is SQL + two definer functions. `WriteSet`'s brand (`prepareWriteSet` sole constructor) is the type half of "the emitter is the sole writer"; the privilege half is in the migration revokes, the schema half in the `emitted_by` check and the two unique constraints (`notifications.ts:18-23`, migration header 19–23).
- **Core ↔ provider**: `ProviderPort`; product code is `notification-provider.ts` (the documented exception to the `_shared` no-I/O rule). Above loop, the stack's Mailpit is reached via real SMTP on the port stated in `supabase/config.toml` (`smtpPortFromConfig`, `_live.ts:101-112`).
- **Test ↔ catcher**: `_mail-witness.ts` over Mailpit HTTP, through the same `live-stack.ts` client the auth suite uses; `messagesAddressedTo` per world-namespaced address.
- **Harness ↔ adapters**: tier chosen by `AT_TIER` (registry, no default); loop harness assembles `_fixture.ts` with clock/worlds/config/vendor sim (`index.ts:227-232`), integration loads `_live.ts` (234–249). One harness per `open()`, one world per open.
- **No production delivery worker exists**: the worker is `core.runPass` driven by the test process; `processEpoch` is an in-memory string and `processRestart` just replaces it. Grep finds no caller of `emit_notification` in `supabase/functions` — the fixture producer definer is the stand-in for real producers that "no requirement in this tree has built yet" (migration header 1–8).

## Non-Obvious Things

1. **The fault fired ≠ the fault was armed, by construction.** Arming writes nothing into the ledger (`_fault-switch.ts:13-14`); the count is incremented only AT the reach; `clear()` refuses a zero count in `faultFiredProblem`'s words (`guards.ts:111-119`). The header of `faults.ts` states the stakes: a handle counting "armed" as "fired" would green every atomicity test in the tree with no suite showing a symptom.
2. **The integration crash fault has TWO witnesses on different sides of the wire** and `triggerCount()` refuses when they disagree (`_live.ts:267-280`): the sequence advance (product side; only code executing inside the database can advance it; survives the rollback because `nextval` is non-transactional, migration comment 163–166) and the received refusal carrying the raise's own `detail` (wire side). A product that took the sequence but stopped raising, or an adapter that counted refusals it never received, both fail. At loop there is only ONE witness — the adapter's in-process counter — which the header of `_fault-switch.ts` admits is the only witness there can be when the binding IS the code path.
3. **The crash fault is an argument of the producer's own call** (`p_induce_fault`), not a control table or session GUC (`_live.ts:34-36`, migration header 13–17) — the live `append` reads the crash switch immediately before the one write that can crash and forwards the boolean.
4. **SMTP has no idempotency key, so duplicate prevention above loop is an adapter wrapper**: `withIdempotentReplay` asks the catcher whether the key already arrived and sends nothing if so (`_provider-faults.ts:87-103`). The product's contribution is the key minted once by `emit_notification` (SQL line 225) and read off the row verbatim on every retry (`notifications.ts:218-219`), plus DB uniqueness (`one_per_pair`, `one_per_key`). A replay that failed to skip would leave 2 physical messages and fail `physicalCountsByKey == [1]`.
5. **The sender cannot see a lost ack.** The simulator's port answers `no_ack`, never `ack_lost` (`vendors.ts:9-15`); the live decorator answers `no_ack` after the inner provider took the message. The trace knows the truth; the sender must not — a delivery marked sent on a lost ack "would still look correct, which is precisely the defect the clause hunts."
6. **Replays and rejections at the provider are asymmetric**: a replay of an accepted identity is acked without consuming a forced outcome; a rejected identity is deliberately NOT protected, so its retry can be a first acceptance (`vendors.ts:98-119`).
7. **The attempt log is a confessed single witness**: rejections and lost acks never arrive at the catcher, so `_provider-faults.ts`'s module-level log is the only record of them, and it "would be wrong if the decorator recorded a sequence it did not perform" (13–16). The catcher cross-checks only the physical side (reject → `[]`, lost ack → `[1]`, retry → `[1]`).
8. **The mail witness never de-duplicates** — two physical messages with one key stay two rows; de-duping by `Message-ID` on the way in would blind it to the exact defect it exists to catch (`_mail-witness.ts:10-15`). A catcher that doesn't answer is a refusal, never an empty list.
9. **`event.attempts` counts worker passes, not provider sends** — in-app passes increment it without any provider contact, so the test checks the SUT counter beside the provider trace precisely because the two can disagree (`_contract.ts:106-114`; asserted at `c-reliability-guard.test.ts:224,263`).
10. **`drain({passes: 1})` is the observability seam**: under run-to-quiescence a sender that wrongly marked sent on `no_ack` would be indistinguishable from an honest one, because both attempts happen inside one call (comments at 230–240). The pass-bound refusal for non-integer/zero budgets (`notifications.ts:386-391`) mirrors `providerForceCountProblem`.
11. **No retry cap, no backoff**: with a provider that rejects forever, an unbounded `drain` would loop forever (the `for(;;)` in `drain`); the tests arm exactly one forced outcome per arming and bound to one pass while the fault is live.
12. **`'failed'` is a dead state in v1** — declared in the enum and the row type, set by no code in either binding.
13. **The atomicity oracle is deliberately a superset**: "all four absent" (transition, event, delivery, ops item) rather than the old `transitionCommitted !== eventWritten`, which passed when a fault fired after BOTH writes. The ops item is matched by `kind` because the crashed fire threw and produced no event id. Both narrowings carry falsification transcripts (`loop/items/AI4DEV-19/proof-oracle.txt`).
14. **The pair oracle counts, never de-dupes**, and is checked as EQUALITY against the taxonomy-derived expected pairs on both the delivery rows and the provider-accepted record — checking only internal consistency would pass a retry mailed to the wrong recipient (`c-reliability-guard.test.ts:281-292`).
15. **Per-open adapter instances are what make one shared database behave like 22 private worlds**: `openWorld` builds a fresh harness (and live adapter) per open (`registry.ts:673`, `index.ts:241`), so `openedWorlds`/`scopedActors()` of one open never include another's actor ids; reads are `recipient_id = any(...)` filtered (`_live.ts:19-24` header).
16. **The first send owns the `deliveredByProcess` stamp** — re-stamping would record the last drain's identity instead of the process that actually performed the send (`_fixture.ts:292-296`); SQL keeps it with `coalesce(delivered_by_process, p_epoch)` (migration 260). `accepted_at`/`provider_receipt` are written in the same statement as the sent mark, "so a crash after acceptance and before the sent mark leaves something to recover from" — but they are explicitly NOT a way to skip the provider on a retry (migration 31–35).
