## Flow

**1. How an id becomes an executable test.** `_bind.ts:42` binds the suite once. Each body file calls `atTest('AT-016.NN', title, body|perTierMap)`. `registry.ts:atTest` (line 861): parse the id (`parseAtId`), enforce `requirementMismatch` (the id's requirement must equal the binding's — otherwise the types read off one adapter while the run loads another), refuse duplicates, register + emit a runtime registration jsonl, and for a per-tier map pick the body with `chooseTierBody(bodies, TIER)` (`bodies[tier] ?? default ?? loop`); `tierBodyProblem` refuses a map with a hole AT THE CALL SITE, because an uncovered tier would report the id MISSING, a state no declaration can describe. The single-function form is typed at the loop tier (the richest one); a per-tier map's `integration` body is typed `AtContext<..., 'integration'>`, whose `h` is `TierHarness<'integration'>` — `clock` has only `now()`, `vendors` is absent from the type.

**2. How `open()` builds the world.** `openWorld` (registry.ts:654): throw `AtPending` on unset/invalid `AT_TIER` (there is NO default — `TIER` is `Tier | null`); throw `AtPending('harness-missing')` if `./index.ts` exports no `createHarness`; **before building anything**, `aboveLoopStandInRefusal(TIER, harnessModule.liveAdapterExists('req-016'), 'notifications')` — above loop with no `_live.ts` file present, throw `CapabilityPending(['fixtures.worlds', 'sut.notifications'])`. Then `createHarness`:
   - **loop**: `ControlledClock`, `createEmailProviderSim()`, `loadAdapter('req-016', ...)` imports `tests/at/suites/req-016/_fixture.ts`, checks its exported `requirement` literal, calls `createFixtureAdapter({ clock, worlds, config, vendors: { email: provider.port } })`. Harness `vendors.email` is the sim; `static` is `refusing<StaticScan>('H3 static provider scan')`.
   - **integration**: `loadLiveAdapterModule` imports `_live.ts`, checks the same literal, calls `createLiveAdapter({ stack: stackFromEnv() })` with the five `AT_SUPABASE_*` coordinates the runner validated; `vendors` is a refusing proxy (`'vendors.email'`) and the clock is a `RealClock` cast into the shared shape.
   Then `h.sut.notifications` must exist (`AtPending('sut-missing')` with `_bind.ts`'s own words otherwise), `h.fixtures.world(fixture)` builds the world, and the context is returned — with one surviving cast at registry.ts:958 (see Non-Obvious).

**3. Loop tier: an event emitted and stored.** Body calls `w.fire(event)` → `NotificationFixtureWorld.fire` → `fireThroughCore` → `core.emit({ event, params: producerPayload(event, params) })`. In `notifications.ts:emit`: taxonomy lookup → `directory.resolve` (fixture: `currentWorld.actors`/`addresses`; live: SQL) → `prepareWriteSet` → `outbox.append(write)`. The memory outbox `append` (`_fixture.ts:230`) is the loop tier's one transaction: (1) commit the transition into `state.transitions`, (2) the fault point — if armed, restore the PREVIOUS transition value, increment `reaches` (the count happens at the reach, never at arming), and throw, (3) only then allocate the event id and write event row, deliveries (each with `idempotencyKey = ntf:<eventId>:<recipientId>:<channel>`), and the ops item. `emittedBy` is `notifications.emitter`; `deliveredByProcess` starts `null`.

**4. A delivery reaches a provider and is marked sent.** `sut.drainDeliveries()` → `core.drain` → per pass `outbox.pending()` (unsent deliveries, oldest first) → for each: in-app is accepted by the pass itself (never reaches a provider); email calls `provider.deliver` — at loop the harness sim's port (idempotency-first, forced outcome queue, `'no_ack'` never reveals `'ack_lost'`), at integration `bindProviderFaults(withIdempotentReplay(smtp))` → real SMTP to Mailpit. Then `outbox.applyPassResults(results, epoch)`: memory — first send owns the `deliveredByProcess` stamp (`null` = nothing sent it yet), `state = 'sent' | 'retrying'`, event `attempts += 1` per touched event, event state = 'sent' only when no delivery of the event is unsent. Live: `public.apply_delivery_results(jsonb, epoch)` does the same in one SQL transaction.

**5. Faults.** The crash fault (`crash` kind) is reached inside `append` between the transition and the event write:
   - memory: the adapter itself misbehaves (restore-then-throw), reach counted in `ledger.reaches` — the only witness there can be, because the binding IS the code path.
   - live: the armed flag is forwarded as `p_induce_fault` to `fixture_commit_transition_and_emit`; the reach is counted by TWO witnesses recorded on different sides of the wire — the product's `nextval('public.notification_fault_triggers')` (read via `pg_sequence_last_value` before and after the call, `_live.ts:284-289`) and the adapter's count of refusals carrying `detail = 'induced-fault:...'` (`_live.ts:291-292`). `triggerCount()` REFUSES when the two disagree (`_live.ts:270-279`).
   The provider fault (`notifications.provider_send`, kinds `reject`/`lose_ack`) exists only as a decorator around the SMTP port; above loop the DB does not record it, so the attempt log + the catcher are the witnesses.
   `h.faults.processRestart()` replaces the process epoch (guard: `processEpochProblem` refuses a restart that changed nothing).

**6. How a tier chooses its procedure.** Bodies registered as a bare function run identically at both tiers — the six ports just change what backs them (`_fixture.ts` header: "A loop green and an integration green run the same core"). Three ids fork, via the per-tier map form:
   - AT-016.01 (`a-emitter-and-taxonomy.test.ts:13-27`): `default:` shares `assertEmitterIsSoleWriter` with `integration: at01601`; what forks is the provider-side trace — the sim's `attempts()` at loop, the mail catcher above loop.
   - AT-016.08 (`b-delivery-defaults.test.ts:100-176` vs `_integration.ts:151-212`): loop commands `h.clock.freezeAt/advance`; integration waits real time (`waitMs`) against two short pinned windows (cap 2 / 3 s / no-coalesce and cap 4 / 5 s / coalesce) and reads the pins out of the world's own name.
   - AT-016.11 (`c-reliability-guard.test.ts:158-295` vs `_integration.ts:257-382`): loop arms `h.vendors.email.rejectNext(1)` / `acceptButLoseAck(1)`; integration arms `h.faults.at('notifications.provider_send', 'reject' | 'lose_ack')` (no `h.vendors` exists there) and counts physical catcher messages per idempotency key.
   `d-taxonomy-evidence.test.ts` instead uses ONE body plus a shared capture (`defineEvidenceCapture`, bound in `_bind.ts`): the producer runs every taxonomy row once, branches on `TIER` (`live = TIER !== 'loop'`, line 89) only for which out-of-band trace fills `providerAttempts`/`providerAccepted` (sim arrays vs `messagesAddressedTo` mapped through `traceFromCatcherMessage`), and five ids (AT-016.03/.04/.05/.06/.12) consume the frozen capture; `evidenceBuilds` is asserted to be 1 so the capture is produced once and asserted many times. `captureFailure` in registry.ts:452 deliberately does NOT wrap `CapabilityPending`/`AtPending`, so a refusal keeps its declarable first line.

**7. How an id is declared red by capability name, not by failure.** Two error shapes are the ONLY declarable reds: `CapabilityPending(capabilities)` prints `CAPABILITY PENDING — <names joined ", ">` and `AtPending(atId, phase, detail)` prints `<id> PENDING [<phase>] — ...` (`pending.ts`). Producers of these: `refusing()` proxies in `index.ts` (`'H3 static provider scan'` for `h.static` at every tier; `'vendors.email'` at integration), `aboveLoopStandInRefusal` (`['fixtures.worlds', 'sut.<key>']`), the live adapter's sentinel read (`CapabilityPending(['sentinels.scan'])`, `_live.ts:516-521`). `expected.ts` declares a red as `{ kind: 'capability-pending', capabilities: [...] }` — matched by REBUILDING the whole first line `CapabilityPending: CAPABILITY PENDING — <names>` and comparing EQUALITY — or `{ kind: 'pending', phase }`, matched by the anchored prefix `AtPending: <id> PENDING [<phase>] — ` only (the tail is free because `sut-missing` carries a suite-supplied string). Anything else — an ordinary `Error`, a vitest timeout, a teardown failure — is undeclarable and therefore fails. The parser also refuses capability names containing a comma (they'd be ambiguous against the joined line) and the redaction sentinel.

**8. What `--expect` actually compares.** `runner.ts:334-342` loads the manifest BEFORE any test runs and returns exit 2 with "DECLARATION REFUSED" on any malformation — a bad declaration never takes the stack lock, never resets a database. Then, after the run, two deviation sets are both computed and printed:
   - `expectationDeviations` (id level): every row must be declared; a declared green that reports red is a failure; a declared red that reports GREEN is a failure ("update the declaration in this same change"); a declared red's detail must match its declared shape exactly (capability-pending) or by prefix (pending); a redacted detail fails closed; `missing` rows and unexpected registered ids are deviations.
   - `reportAccountingDeviations` (report-level): `numFailedTests` must equal the number of declared reds, `numPassedTests` the number of declared greens, `total` their sum; `pending`/`todo` must be 0 (a skip must never hide inside a declared red); `success` must equal `red === 0`; with no reds declared the process exit must be 0; and `suiteFileDeviations` catches file-level failures (import failure, throwing hook) that change no test's status — a failing file with zero failed assertions, or a file-level `message`, is a deviation no AT id can claim.
   Exit 0 only when the run matches the declaration exactly.

**9. The manifest.** `tests/at/expected/req-016.json`: `{ requirement: "016", tiers: { loop: { green: [all 12 ids AT-016.01 … AT-016.12], red: {} }, integration: { green: [same 12], red: {} } } }`. Its shape asserts three things: the 12 P0 ids of the acceptance file are expected GREEN at both tiers (the `declarationBijectionProblems` check makes the manifest's ids an exact bijection with the acceptance file's P0 set — forgetting an id would let it go ungraded), NO reds are expected anywhere, and therefore the run must also add up arithmetically (12 passed, 0 failed, no pending/todo) at both tiers. There is no `red` entry to demonstrate the capability-name mechanism today; the mechanism is exercised by other suites and was used here historically (see Non-Obvious).

**10. How the live adapter reaches the database and the mail catcher.** Database: Bun's `SQL` client over `AT_SUPABASE_DB_URL` (`live-stack.ts:sqlClient`), opened once per process and refcounted (`acquireSql`/`releaseSql`, `_live.ts:134-149`) because one integration run opens twenty-two adapters for AT-016.09 (11 guarded rows × a control world + a fault world) and twenty-two ~10-connection pools left the auth service no slot — the last adapter to tear down closes it. Reads are plain `sql` tagged-template queries as the operator. Mail: `mailIdentification(stack)` probes Mailpit's `/api/v1/info` and refuses anything else (the Supabase CLI has shipped both Mailpit and Inbucket); the SMTP port comes from `supabase/config.toml`'s `[local_smtp] smtp_port` (`smtpPortFromConfig`, `_live.ts:101-112`) because the runner hands the adapter only the five coordinates — a config with no port is a refusal.

**11. How a world scopes its reads.** Every SQL read in the live outbox is scoped to `recipient_id = any(${scopedActors()}::uuid[])` — the union of every opened world's `knownActorIds` (`_live.ts:257`); events and ops items are reached through the deliveries' `event_id` (`where id in (select event_id from notification_deliveries where recipient_id = any(...))`), the pending set the same way, and the type filter rides along. A crashed emit writes no delivery, hence no event row, hence the atomicity id's scoped read finds nothing — which is exactly the answer it wants. `transitionCommitted` reads `notification_fixture_transitions` keyed by the world's `scopeId` (`req-016/<unique-namespace>`, timestamped + random), so a fresh world reads only its own transitions. The mail side is scoped by address: every world namespaces its four recipients' addresses (and role moves mint `label+namespace@example.test`), and `_mail-witness.ts` searches `to:"<address>"` per address. Addresses and actor ids are the two disjoint namespaces; the `knownActorIds` list also keeps a *reassigned-away* holder's already-written deliveries visible after the move.

## Boundaries

- **Runner → suite:** `bun run at:verify req-016 --tier loop|integration [--expect]` (package.json:14). Loop tier touches no database; integration tier takes a machine-wide lock, resets the one stack and replays migrations before spawning vitest with `AT_TIER`, the five `AT_SUPABASE_*` env vars and `AT_REGISTRATION_DIR`.
- **Runner → CI:** `.github/workflows/ci.yml` runs `at:check <req>` and `at:verify <req> --tier loop --expect` per landing requirement, and distinguishes exit 1 (deviation/red) from 2 (refusal, nothing graded) from 3 (infrastructure) from 4 (no report).
- **Suite → product:** the ONLY product code either adapter imports is `supabase/functions/_shared/notifications.ts` (`createNotifications`, `TAXONOMY_PORT`, the port/row types), `notification-taxonomy.ts` (`TAXONOMY`), and — live only — `notification-provider.ts` (`createSmtpProvider`). The core never learns that faults exist; a fault is an adapter that misbehaves.
- **Suite → harness:** `_bind.ts` alone imports the harness. Everything else in the suite touches it only through `h`/`ctx`.

## Non-Obvious Things

1. **`h.static` is dead weight for this suite, and its comment is stale.** `index.ts:214` says "AT-016.01 stays red on this one name; tests/at/expected/req-016.json declares it" — but the manifest now declares AT-016.01 green at both tiers, and the bodies never call `h.static` at all: the suite-local `_source-scan.ts` oracles (`providerClientImporters`, `strayNotificationWriters`) replaced the harness `StaticScan` capability, which remains a `refusing()` proxy throwing `CapabilityPending(['H3 static provider scan'])`. The capability-name red mechanism this question asks about is fully real (`expected.ts` builds and compares the exact `CapabilityPending` first line; other suites' manifests carry such entries) but req-016's manifest currently declares no reds.
2. **The per-tier body "cast" is a widening of a narrower type, and it is the one bridge between the tiers' context types** (registry.ts:893-899): an integration body is written against fewer capabilities, so the runtime object satisfies it; no tier's type names a member the loop type lacks, so the direction is always narrow-body/wide-object.
3. **`WorldOf<'req-016'>` resolves to the loop fixture world's concrete class** (`NotificationFixtureWorld`, derived from `_fixture.ts` in `suite-adapters.ts:137`), while at integration `open()` actually returns a `NotificationLiveWorld`. Both implement the suite's `World` intersection, and the relabelling happens in the single surviving cast at registry.ts:958 — stated there as the smallest remaining claim on trust. Bodies that annotate with `World['actors']` (e.g. `d-taxonomy-evidence.test.ts`) stay on the shared shape.
4. **The duplicate guard at the integration tier is Mailpit, not the sender.** SMTP has no idempotency key, so `withIdempotentReplay` asks the catcher whether a message with this `X-Notification-Key` already exists before sending (`_provider-faults.ts:91-103`). The `lose_ack` decorator genuinely sends and then lies (`no_ack`), so the retry physically reaches the provider again — and Mailpit's store answers the replay as already-accepted. The catcher-side counting in at01611 expects exactly `[1]` per key after the retry; two physical messages per key would remain two rows in the witness.
5. **The sim's forced-outcome queue is ONE queue in call order**, not two counters (`vendors.ts:67-81`) — mixed `rejectNext(1); acceptButLoseAck(1)` arming orders are what a single-kind implementation gets wrong. Replays consume no forced outcome; a rejected identity is deliberately NOT protected (only a physical acceptance closes an identity).
6. **In-memory, the "one delivery per pair" assertion cannot fail** — `b-delivery-defaults.test.ts:79-87` says so out loud: the reference fixture writes one delivery per pair by construction, so the assertion's worth is as a regression guard for the tier where a real delivery process exists. Its oracle is `countPairs`/`pairProblems`, which COUNT rather than dedupe, so a duplicate is a distinct problem string.
7. **AT-016.09's atomicity oracle asserts BOTH SIDES FALSE, not "unequal"** (`c-reliability-guard.test.ts:96-121`): the older `transitionCommitted !== eventWritten` form passed a fault that fired after both writes (both committed, compared equal). The current form also demands no delivery and no ops item, because `fire()` writes deliveries and ops items after the fault point too — a fault path that rolled back only the transition and the event while leaving a delivery committed used to pass and would then have been SENT by the drain.
8. **The fault reach is proven twice, on different sides of the wire, at integration only** (`_live.ts:34-53`): the product's `nextval` on `notification_fault_triggers` (survives the rollback; read from the relation, not the session) and the adapter's count of refusals carrying the raise's own `detail`. `triggerCount()` refuses when the witnesses disagree — covering both "took the sequence then stopped raising" and "a refusal raised by something other than the product's fault point".
9. **Real accounts, not stubs, at integration.** Each world provisions four confirmed auth users via `POST /auth/v1/admin/users` with `email_confirm: true` (no mail, so the auth service's per-hour mail limit is untouched) plus operator-inserted `accounts` rows, an organisation and a project. `reassignRole` mints a successor account and re-seats the real directory row the adapter's `resolve` reads (`_live.ts:561-575`).
10. **The guard's pinned numbers reach the live factory through the world name** — `req-016/guard?cap=<n>&window=<ms>&coalesce=<bool>` (`_live.ts:169-194`) — because the live factory receives only `{ stack }` and never `h.config`; the body then reads the same pins back from `h.config` and asserts the two are the same numbers (`_integration.ts:173-176`).
11. **Teardown is load-bearing, not housekeeping.** `runTrackedTest` fails a body that passed but left teardown failures (`AggregateError`, registry.ts:629-637) because state that leaked (frozen clock, armed fault, vendor counter, the shared SQL client) lands on the NEXT id. `atTest` also refuses a body that never opened a world or consumed a capture (`testUseProblem`, registry.ts:525-527).
12. **Evidence captures are deep-frozen and shape-checked**: `freezeEvidence` refuses Maps/Sets/Dates/class instances because `Object.freeze` leaves them mutable through their methods (registry.ts:386-419); a capture whose producer never called `open()` is refused (`captureProducerProblem`).
