# Astra fixture prototype

This interactive design belongs to Astra. Each screen's review status appears in `screens.json`.
The Design workspace is accepted for implementation. Other screens retain their individual review status.
The founder requested this separate fixture prototype on 2026-09-21.

## Run

Use the repository's installed dependencies and Node 22.18 or later.

```powershell
bun run design:astra
```

Open `http://127.0.0.1:4310/`.
The application reads no environment files from the repository root.
It uses the existing application theme without changing production routes.

If the Windows sandbox blocks Vite's dependency scanner, use the compiled preview:

```powershell
bun run design:astra:build
bun run design:astra:preview
```

Rebuild and reload the compiled preview after an edit.
Run `bun run design:astra:check` to check the prototype's TypeScript.

## This first pass

One NGO project connects these screens:

1. Dashboard and project list.
2. Project intake and reference file metadata.
3. Discovery questions, answers, and a live brief.
4. Scope review and explicit confirmation.
5. Submission for human review.
6. Project fuel and simulated top-ups.
7. The volunteer project view after PRD materialization, with PM and development boards.
8. The accepted Design workspace, with screen review, NGO handoff, and sign-off into sample Build items.

The assistant uses scripted replies for the volunteer scheduling example.
It does not run an AI model. It does not contact a database, payment service, or notification service.
Reference attachments store file names and sizes only. They do not upload file contents.
The earlier screens retain their stage labels. The new build view opens at `http://127.0.0.1:4310/#build`.
It is a separate, fixed snapshot of the same sample project after PRD materialization.
Discovery answers do not generate this snapshot. Switching between boards does not change the Discovery draft.

The build view has two PM parents, five child requirements, and one completed PRD setup item.
It opens after the first requirement is pulled. Its dev tree has one root, two deliverables, and three buildable leaves.
Five acceptance tests link to those leaves. Every test starts as Not run.
Tree and board layouts retain parent context. Pulling another ready requirement reviews and materializes its dev tree locally.
The PRD reference follows the same nested requirements. Materialization does not increase verified progress.
The conversation preview uses this same React screen, generated by `scripts/build-inline.mjs`.
The start action copies a prompt for the volunteer's work session. It does not pull an item or change its status.
See [the build review](build-review.md) for the design boundary and verification record.

Open **Design workspace** from the sidebar or review inventory to inspect the accepted mock in a new tab.
The [standalone Design preview](design-review-preview.html) also opens directly from disk.
It preserves the reviewed conversation mock without a rewrite.
Its local Build items are separate from the larger Build snapshot and reset on reload.
See [the Design review](design-review.md) and [Design contract](../design-ui-contract.md) for the accepted behavior and remaining work.

Use **Astra · fixture mock** in the header to open the review tools.
Review tools can set free, paid, exhausted, pending, failure, decline, and reopened fixtures.
Scenario changes preserve the conversation and reopen its approval. They reset funding to the selected sample values.
The reset control restores the original sample. Review notes survive the reset.

The prototype saves drafts, answers, usage, confirmation, and purchases in this browser's local storage.
It is a single-browser mock. Concurrent funding changes and backend enforcement need later implementation.
Money uses integer millionths of a dollar. Paid fixture replies use $0.040 plus a $0.006 fee.
The $0.25 reservation is an illustrative spending limit for a mock reply.
An approval moves available fuel once. Reopening this mock returns the unused next-stage allocation for review.
This reversal represents fixture editing, not a production transfer contract.

## Authorship

Astra and Claude both revise this one prototype. There is no separate Claude revision folder.
Each screen's review record names the author of every revision. Discovery revision 5 is Claude's.
`screens.json` records the screen inventory and the corresponding Claude Design references.
The original Claude Design exports stay unchanged in `design/screens/`.

To prepare a local handoff:

```powershell
bun run design:astra:build
bun run design:astra:export
```

The export includes a runnable static preview, Astra source, requirements, and clearly labeled Claude baseline files.
The command writes only to `design/astra/exports/`. It sends nothing to Claude Design.
The review page also downloads review notes and the current fixture as JSON.
Give both artifacts to a later design session when you want that review.
Keep behavior decisions and visual suggestions separate during comparison.
