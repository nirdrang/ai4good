# Take a PRD action

The Dev posts a question, confirms or reopens a topic, and closes the PRD. The NGO administrator marks an answer complete. Each action carries the token the snapshot offered for that control, so a stale screen cannot apply an old click.

## How to reach it

Send `POST /functions/v1/prd-action` with `{ projectId, kind, token, requestId }`. `projectId` is a uuid. `requestId` is a non-empty string. `token` is a non-empty string. `kind` is one of `post-question`, `complete-answer`, `confirm-topic`, `reopen-topic`, `close`, `close-anyway`, and `keep-working`.

## Drive and readback

Success is 200 `{ ok: true, ...result }`. The result is whatever that kind wrote. A posted question writes `prd_questions`, a side chat, and bumps the snapshot sequence. A completed answer writes a side-chat turn and a funds hold, and the settle step then runs that side-chat reply, which calls the model. Confirming a topic can start a completion check, which calls the model, or it can confirm the section when a current check already covers it. Reopening a topic writes the section state. Close and Close anyway write `prd_closes`, `prd_close_points` when closing anyway, `prd_records.closed_revision`, and a `prd_git_ops` row of kind `close-tag`, then ask GitHub to tag `prd-r` plus the revision. Keep working only bumps the check's ask version. Read those tables over the operator SQL connection. Read the tag only after that git row is `published`. The tag helper creates a missing tag, so a tag that appears before the row is published is not proof.

A made-up token is refused before any of that work. It needs no model and no GitHub. Close and Close anyway need GitHub for the tag. Complete-answer and a confirm that starts a check need the model. Preparation attaches the model id when settings exist and does not refuse when they do not, so the made-up token still fails in the database with no model call.

## Refusals

The shared write pipeline runs first, in the same order as open: 405 with no `kind`, 401 with no `kind`, 400 `invalid-request` for a non-object body, 400 `invalid-request` for a project id that is not a uuid, 502 `refused`, 403 `account-deactivated`, 409 `no-account`, and 403 `refused` for an account type other than volunteer or NGO. The route then refuses 400 `invalid-request` when the project, kind, token, or request is missing or the kind is not one of the seven.

The database then checks, in order. The account must be active. An empty request id is `invalid-request`. A token that is not `kind|target|revision|version` is `invalid-request`, and this is the made-up token. A token whose numbers do not fit, or whose kind does not match the body, is `invalid-request`. No PRD row is `invalid-request`. Pending or diverged is `not-yet`. No role is `forbidden`. The NGO administrator may only complete an answer, and the Dev may take every other kind; the wrong person is `forbidden`. A repeated request id for another actor or another kind is `invalid-request`. A request id already used by a turn is `invalid-request`. A closed PRD is `closed`. The same request id from the same actor and kind returns the earlier result.

Posting a question then requires a current revision (`stale`), and `prd_question_post` requires the Dev, an open PRD, a question for the NGO (`invalid-request`), the offered row version (`stale`), and a ready question (`not-ready`). Completing an answer requires the offered question (`invalid-request` or `stale`), no open follow-up (`follow-up-open`), at least one NGO message (`invalid-request`), no open turn in that side chat (`busy`), and funds (`funds`). Confirming a topic requires a topic target, the current revision (`stale`), a section in this PRD (`invalid-request`), no completion-check gap, a ready section (`not-ready`), ready dependencies (`not-ready`), and a stored version (`invalid-request`). A confirm that starts a check also needs the main chat, no open turn there (`busy`), and funds (`funds`). The database detail for that gap is `gap`, which is not a known HTTP kind, so the response kind is `refused` at 409. Reopening a topic uses the section transition: a topic target, the current revision (`stale`), a section in this PRD, and a confirmed section (`not-confirmed`).

Close, Close anyway, and Keep working go through the close action. The caller must be the Dev (`forbidden`). The PRD must be open and not closed. An open turn blocks Close and Close anyway (`busy`). Close requires a token aimed at `close` for the current revision (`stale`) and a current completion check (`invalid-request` when the check has not been run). Close anyway and Keep working require a token aimed at the current ask (`stale`). Any other kind that reached this branch is `not-yet`. A database `kind` above is HTTP 409, except a `gap` detail, which is HTTP 409 `refused`. A failure that is not a five-character SQLSTATE is 502 `refused`.
